# Security review of the time-currency blockchain (November 2026)

Scope: everything that runs in a protocol-4 network: the ledger rules, the node application, staking, the Bitcoin bridge with auction, treasury and registration, the proof and storage code, the light-client verifier, the wallet, the SDK and the gateway. The new version-5 engine is covered in its own section.

How it was done: five independent line-by-line reviews, one per area, each asked to find ways to steal, create or destroy currency, forge proofs, halt the network or deny service. I then read the code behind the findings that mattered most for the new engine. Nothing was tried against a live network. The table says for each finding whether I confirmed it myself.

## Bottom line

- No way was found to spend someone else's currency, to create or destroy currency, or to show a wallet a false balance or a false payment without the validators' signatures.
- The supply rule (bank + balances + stake + auction reserve = seconds since genesis) is enforced on every block and re-counted from scratch by the audit command. All recounts in the AWS runs passed.
- The serious findings are about availability (ways to fill blocks or the waiting queue for free), about punishing misbehaving validators, and about the Bitcoin bridge, which is not safe for real bitcoin yet. The lab network only accepts Bitcoin's test mode, and the code refuses to enable real receipts.
- Ten findings in the existing system are fixed (eight in the version-5 engine, one in the verifier build, one in the wallet's light client). The rest are listed as open, with the fix I recommend. Four of them must be closed before any launch with real value.
- The new code was itself reviewed independently three times. No consensus-safety or forgery problem was found; 17 robustness problems were found and fixed (see "Independent review of the new code").
- The engine now lets an account separate the key that signs in from the key that spends, and recover from the theft of either (see "Account security"). A stolen sign-in key moves nothing; a stolen spend key moves at most a daily limit; neither can stop the owner from replacing it. These rules were reviewed independently three more times; the last review found two serious weaknesses in how they met the waiting queue and the fee, which are fixed.
- The wallet now has screens for these rules, an alert service tells owners in time what is waiting on their accounts, a ceremony builds the genesis of a production-profile network that every operator checks for itself, and the deployment kit runs the new engine (see "Wallet screens and alert watch" and "Starting a production network"). Each was reviewed independently two or three times, until no finding above Low was left. The alert watch ran against a live network on 18 November (see "Preparing a first version"). The wallet screens, the ceremony and the kit have not run outside tests.
- For a first version, the network can now change its own rules by a vote of its validators, nodes can join without replaying every block, and integrators and the public have an HTTP API, explorer pages and a test-network faucet (see "Preparing a first version"). Each part was reviewed independently two or three times. Every first review found defects serious enough to block the part, and all of them are fixed. On 18 November an upgrade was activated on a live network of seven validators on AWS, a node joined that network from a snapshot, and the API, the faucet and the alert watch ran against a live network: every scripted step passed. On 19 November a real browser used the wallet, the faucet page, the explorer and the sample shop on a live network for the first time: it found four defects, among them a payment signed by one long key press and an explorer that loaded in no browser; all four are fixed (see "In a real browser"). The same day the deployment kit ran for the first time with Docker, two remote signers and the lease controller, on eleven machines: as it stood it could not start, six defects were fixed, and then 23 of 25 steps passed (see "The deployment kit, rehearsed"). Not run yet: any browser but Chrome, a production genesis, and anything with real operators.

Severity: Critical = loss of funds possible; High = serious harm, or cheap denial of service; Medium = limited harm or needs unusual conditions; Low = hardening.

"Confirmed" = I read the code and agree. "Reported" = from the reviewer, not independently confirmed by me.

## What was found sound

- Signatures cover every field of an action, including network, account, number and authority epoch. Replays and cross-network reuse fail.
- Failed actions leave no trace: every change is staged and published only if all rules pass.
- All arithmetic on amounts is overflow-checked; the release build keeps overflow checks on.
- Guardian recovery: thresholds, delays, freezing, cancellation and the one-vote-per-guardian rule hold.
- Staking keeps currency conserved across bonding, delegation, exit, reward and penalty. Validator-set changes are deterministic and limited per step.
- The light client checks validator signatures with CometBFT's own vote encoding, validator-set hashes, time and height. A state proof is tied to the signed application hash.
- The wallet vault uses a memory-hard password function and authenticated encryption with a non-extractable key. No remote code is loaded.

## The version-5 engine

It runs the same protocol-4 rules with a different way of doing the work. Four rules changed on purpose (A1, A5, S1, and a larger block: 4 MiB of transactions instead of 1 MiB), so all validators of a network must run the same engine.

How its correctness was established:

- Every block of a random workload (260 blocks, 13 kinds of action, about 190 deliberately invalid ones) is executed by the unmodified protocol-4 engine, by the new engine, and by the new engine with its fast paths switched off. All three must accept and reject the same transactions and reach the same state hash and the same metadata bytes. A scripted test covers guardian recovery end to end.
- The new in-memory Merkle tree is compared with the JMT library the old engine used: same root after every batch, byte-identical proofs, and the JMT verifier accepts them.
- The answers a wallet reads (state proofs, block history proofs) are byte-identical to protocol 4's on the same chain.
- Restart is tested by killing the node after a snapshot and replaying later blocks; by restarting from genesis; and under concurrent queries, mempool checks and snapshots.
- 112 tests in the engine (111 on Windows, where the Unix-socket test does not apply), 28 in the verifier, 111 in the client, gateway and wallet. On AWS the engine's tests run again on Linux, in release mode, before any validator starts with the binary built there.

What is new and therefore deserves the most scrutiny:

1. **State lives in memory; disk holds snapshots.** After a crash the node loads its newest snapshot (checksummed, and its Merkle root recomputed from the rows) and CometBFT replays the blocks after it. A node therefore depends on CometBFT keeping its blocks. Block pruning in CometBFT must stay off, or be kept behind the oldest snapshot.
2. **Signature cache.** Only successful, strict verifications of the exact transaction bytes are remembered, keyed by the full SHA-256 of those bytes. Batch verification is not used because it accepts a slightly different set of signatures.
3. **One execution per block.** The result of validating a proposal is reused when that same block is finalized. The key covers height, time, block hash, the voters and every transaction.
4. **One-block receipts.** A wallet now accepts a payment once the block that contains it is final, using the rule that validators reject any block in which a transaction fails. This rests on the same assumption as every light-client proof: fewer than one third of the voting power is faulty.

Known limits of the new engine:

- Memory grows with the number of accounts: about 2 KiB per account, plus the last 32 versions of whatever each block changed. One million accounts measured at 8.4 GB with 128 retained versions, before that number was lowered to 32.
- A snapshot rewrites the whole state. At very large state sizes it should become incremental.
- Validators run without CometBFT's transaction index. The gateway finds a payment by reading new blocks. Looking up a payment long after the fact needs the gateway's own index, which is not built yet.

### Independent review of the new code

After writing the engine and the one-block receipts I had three separate reviewers read the new code line by line, each with the code only and no summary from me: (1) the Merkle tree, snapshots, signature cache and evidence check; (2) the node application, its concurrency, the transfer fast path and the mempool state; (3) the one-block receipt in the verifier, gateway and SDK.

Verdicts:

- Reviewer 1: no input that yields a wrong state hash or proof, no way to have an invalid signature accepted, no way to forge evidence.
- Reviewer 2: no consensus-safety bug. No input on which two honest nodes decide differently, no way for a block to be committed with another block's result, no difference between the transfer fast path and the reference rules.
- Reviewer 3: no way for a gateway to make a wallet accept a payment that is not in a finalized block of its chain, or other bytes than the ones it asked about.

They found 17 robustness problems, none of them a way to lose funds. Fixed, each with a test where a test is possible:

| Found | Fix |
|---|---|
| A status query during a snapshot write could hold up block commits for as long as the write took. | The snapshot height is read without any lock. |
| A damaged snapshot file stayed in place and could push good files out of the retention set. | Damaged files are set aside when a good one loads; the file just written is never removed; a stray file under a snapshot's name is replaced, not trusted. |
| Memory reserved from an unchecked count in the snapshot header. | Bounded reservation. |
| Retained versions were limited by count only. | Limited by changed rows as well; freed off the commit path. |
| The decoded-account cache was emptied whenever it filled (the 1M-account slowdown). | Two bounded generations; a block's accounts are loaded on all cores before execution. |
| Oversized input was hashed before it was refused. | Refused first. |
| All answers of a batch of requests were held in memory before being written (hundreds of large proof answers could exhaust memory). | Each answer is written as soon as it exists. |
| The mempool state kept account rows read on behalf of rejected transactions. | A refused transaction leaves nothing behind; the state has a hard bound. |
| Accounts were loaded for transactions before their signatures were known to be valid. | Only for correctly signed ones. |
| Disk syncs of the history file ran under the exclusive lock. | They run under the shared lock; only the swap of the head is exclusive. |
| A failed thread start leaked a connection slot. | The slot is returned. |
| After the consensus engine reconnects, the application's idea of pending transactions was stale. | It starts again from the committed head. |
| The deployable gateway's allow-list blocked the calls the block watcher needs. | Allow-list extended, with a test. |
| A wallet could retry at network speed for 45 seconds after certain answers. | It always backs off, and gives a held request a deadline. |
| The gateway kept whole blocks in memory without a size bound and rebuilt the transaction tree per request. | Bounded by size, freed when idle, tree built once per block. |
| Older wallets received the new receipt form by default and failed on it; a durable export could be handed the short form. | The new form is opt-in; exports require the durable form. |
| The short receipt did not use the next block's result hash even when it had it. | Checked whenever the next header is part of the proof. |

Not fixed, by decision or for lack of time:

- The new rules still report application version 4, so nothing stops someone from mixing old and new validators; such a network would halt at the first block that uses a changed rule. Before any shared network the new rules need their own version number in the node, verifier, SDK and gateway.
- Admission of pending transactions relies on CometBFT's re-check after each block (its default). Do not switch it off.
- A receipt that no wallet asked for while its block was recent can only be served later if the node or the gateway keeps a transaction index. Receipts a wallet did wait for are archived by the gateway.
- The verifier function for short receipts trusts the checkpoint its caller passes, like the other verifier functions. The SDK passes its own verified checkpoint; someone calling the verifier directly must do the same.
- A damaged stored checkpoint in a wallet cannot be replaced through the import form.

## Account security: separate keys for signing in, spending and recovery

In protocol 4 one password unlocks one key that both signs website logins and spends. A single managing key can cancel a recovery, replace the guardians and remove every other device at once, and a stolen spending key can move the whole balance in one payment. The version-5 engine adds rules that an account can adopt to end all three (kinds 70 to 77, `v5/src/security.rs`; reference in `v5/README.md`). Accounts that do not adopt them keep the protocol-4 rules.

**Three kinds of key.** Every key of an account that has adopted the rules has exactly one role.

| Key | What it is for | What it can do alone |
|---|---|---|
| Sign-in | Proving who you are to websites and apps | Nothing on the chain. It cannot pay, freeze, cancel or change a key |
| Spend | Approving payments | Pay up to a daily limit, fees included. Start a larger payment or a raise of the limit; both wait in the open and can be cancelled. Add and remove sign-in keys, at once. Freeze the account. Cancel what is waiting |
| Recovery (two or more: for example a printed sheet, a passphrase, a second device, a trusted person) | Repairing the account | Freeze the account. Cancel what is waiting. Nothing else: one recovery key is one proof, and two are needed |

**Two proofs decide everything else.** The spend keys together count as one proof and each recovery key as one. Replacing keys, changing the limit or the waiting periods at once, lifting a freeze and paying above the limit at once need as many proofs as the account's threshold, which is at least two.

- With a spend key among them the operation happens at once: the owner is there with a second proof.
- With recovery keys only, the one thing they can ask for is a new set of keys. It waits, the account is frozen meanwhile, whatever the old spend key had started is dropped, and a key of the new set finishes it. Calling it off takes the threshold of proofs again. A thief who holds only the spend key therefore cannot stop it, and an owner who still has the spend key and one recovery key can stop a hostile one.

**What a stolen key costs, and the answer to it.**

| Stolen | The worst that can happen | What the owner does |
|---|---|---|
| Sign-in key | The thief signs in to websites as the account until the key is replaced. No currency moves and nothing on the chain changes | Replaces it with the spend key alone, in one action, at once. Open website sessions end with it |
| Spend key, copied | The daily limit leaves, and what refills of it until the owner reacts: at most twice the limit in any 24 hours. A larger payment waits and can be cancelled. The thief can also sign in as the account, because the spend key manages the sign-in keys | Freezes with their own copy of the spend key or with any recovery key. Then the spend key and one recovery key put a new spend key in place, at once |
| The device, with both keys | The same bound | Freezes with one recovery key, which also makes websites refuse sign-ins. Two recovery keys put new keys in place after the wait |
| One recovery key | Nothing moves and no key changes. The thief can keep the account frozen, at one fee per half freeze period | The spend key and another recovery key replace the stolen one at once, which ends the freeze |
| Two proofs, one of them the spend key | The account | Nothing. Whoever holds the owner's proofs is the owner; no scheme without a central party can do better |

An owner left with a single proof cannot recover either. A wallet should therefore set up at least three proofs when the account is created: the spend key and two recovery keys. If an account is frozen, or a replacement of its keys is waiting, and the owner did not do it, a key has leaked. The safe answer does not depend on knowing which: the spend key and one recovery key replace every key at once.

**What carries these guarantees.**

- The daily limit is an allowance that refills evenly over 24 hours and never holds more than one day's worth. Fees count against it, and so do staking and merchant payments.
- A freeze stops every action of a spend key that would lower the balance, and drops what was waiting, so nothing goes through the moment the freeze ends. Incoming payments still arrive. A freeze names the freeze count and the version of the settings it was signed for.
- Freezing, cancelling, root operations and finishing a replacement do not use the account's nonce. A thief who holds the spend key can use up nonces as fast as blocks are made, and could otherwise keep the owner's protective actions out for as long as the daily limit pays the fees. Each protective action is tied to a counter instead, so it is included once and never again.
- In the waiting queue (mempool) these protective actions are judged on the last block alone, not on what else is waiting. Nobody who holds one key can keep the owner's freeze or cancellation out of the queue with an action of his own.
- Protective actions are accepted during a validator safety hold. A freeze, a cancellation and a recovery by recovery keys cost the fee or, if the account has less, what it has, so an emptied account can still be frozen and recovered. Every other operation with two proofs costs the full fee, so an empty account cannot fill blocks for free.
- An approval names the network, the account, the version of its security settings, an expiry, the operation and everyone who approves. It cannot be used twice, for another operation, or with another set of approvers.
- A key that joins an account signs its acceptance of its role there, so nobody can attach a key that someone else holds.
- A replacement survives the removal of a sign-in key it meant to keep: that key is left out. A thief who holds the spend key cannot void a recovery by removing sign-in keys.
- Every payload has exactly one accepted form.
- Websites that use the login library let such an account sign in with a sign-in key only, and not while it is frozen. They read the account's security settings through the wallet verifier, which demands a proof of the settings or of their absence.

**The sign-in key was first given more power, and that was a mistake.** In the first version a sign-in key could freeze the account and cancel what was waiting, and removing a sign-in key had to wait. Reading the finished rules against the requirement that a stolen login must be repairable with the spend key alone, I found that whoever stole a sign-in key could cancel its own removal, keep the account frozen so that the spend key could not even ask for the removal, and go on signing in meanwhile. The final rules give a sign-in key no power on the chain at all, which makes it the cheapest key to lose and lets the spend key replace it at once. What is given up: a device that holds only a sign-in key is no longer a panic button. Freezing takes the payment approval or one recovery key.

**How it was checked.**

- 24 scenario tests on the real engine (`v5/tests/security.rs`) play each kind of key alone and together, including as a thief: the daily limit with fees, waiting payments, raising and lowering the limit, a stolen login replaced at once, a stolen spend key replaced over the thief's resistance, a replacement that survives the removal of a login key it keeps, a hostile replacement stopped by the owner, approvals reused, moved or stretched, an emptied account, a thief who keeps the nonce busy, a thief who tries to keep the owner's actions out of the waiting queue, a validator safety hold. Every accepted block is also executed with the fast paths off and by a proposer, and all three must agree; every refusal is checked on all three paths.
- 10 unit tests cover the arithmetic of the limit (at most twice the limit in any 24 hours, no gain from rounding, no overflow) and pin the stored encoding.
- A node-level test reads the settings as a wallet does, with proof, before and after a restart from a snapshot.
- The wallet library (`client-v4/account-security.mjs`) is tested byte for byte against actions the engine accepted, and the login rule against a login service.
- The end-of-run recount (`--audit`) validates every account's security settings against its keys.
- Three independent reviews, each by a reviewer who was given the code and no summary from me: two of the first version, one of the final one. None found a way to forge an approval, to act without holding a key of the account, or to make two honest validators disagree. The third did find a way for a thief who already holds the spend key to get more than the daily limit, by keeping the owner's cancellation out of the waiting queue until a large payment had waited long enough; it is the first row of the table below. The third reviewer also ran about 14,000 random blocks through proposer, validator and reference path (same root every time), a sweep of 592 actions signed by a sign-in key or a stranger (all refused), and wrote proofs of concept for what follows. The same reviewer then ran those proofs of concept against the fixed code: none reproduces. That pass found one flaw the fixes had introduced, which is fixed and tested as well.
- On AWS a wallet took an account through 18 steps of these rules on a network of four validators in Paris and Virginia (campaign `tc-v5-sec5`, 14 November; node SHA-256 `c90f68a2032029c7176077669410aeaeb110942ddde2e117a8b4c97e0130ac2c`, built there from the source as it stood at 14:53 UTC on 14 November, after its 112 tests had passed on Linux; the build includes the optional fee setting described below, switched off as on every network that does not set it. Changes made to the source after that time, such as the fee amount becoming a network setting, are not covered by this run). It adopted the rules, ran into the daily limit, replaced a stolen login with the spend key alone, froze with a recovery key, lifted the freeze with two proofs, cancelled a waiting payment, and replaced a stolen spend key with two recovery keys after the wait. All 18 steps went as the rules say. Every answer was verified by the wallet with the security settings proven, and the login rule was checked against that verified state at each stage. Afterwards every validator recounted its ledger from scratch; all four recounts passed, and all four validators stopped at the same block with the same fingerprint. `node campaign/report-v5.mjs --campaign tc-v5-sec5` prints the steps. Four earlier runs passed the same check: `tc-v5-sec1` to `tc-v5-sec3` on earlier versions of the rules, and `tc-v5-sec4` on these rules before the fee setting was added.

| Found | By | Fix |
|---|---|---|

Long enough, and a waiting payment goes through | Third review (high) | Protective actions are judged on the last block alone; one of each kind per key waits at a time; what carries an expiry is admitted only if it stays valid for 30 more seconds |

| The settings were validated against the keys only in the recount | First two reviews | Validated before every write as well |
| The rules module could have replaced any field of an account, and any rule module could write security settings | First two reviews, third review | Only keys, nonce and authority epoch may change; only the security rules write the settings |
| An account that had adopted the rules could not withdraw as someone's guardian | First two reviews | Withdrawing is allowed, and free |
| A payload could be written in more than one way | First two reviews | One accepted form |
| A raise of the limit that was noticed late gave too little allowance for the time before it | My tests | The raise takes effect at the moment it was due, whenever the settings are next read |
| A thief holding the spend key could use up nonces and so keep the owner's freeze out of blocks | My review | Protective actions carry no nonce |
| A freeze could be included again after it had been lifted; so could a cancellation | My tests | Each names a counter that only grows |

**Known limits.**

- Nothing on the chain tells an owner that a payment or a replacement of keys is waiting. The waits only protect an owner who looks, or who is told. The alert watch (`deploy/watch`, below) tells them. An owner who runs none, or whose watch cannot see the chain in time, is protected only by looking.
- Whoever holds a spend key can sign in as the account and sign its owner out, because the spend key manages the sign-in keys. This is the price of letting the spend key repair a stolen login.
- A stolen spend or recovery key can keep the account frozen, and with it signed out, until two proofs replace it. Each freeze costs the account one fee. Lifting a freeze without replacing the key that placed it lets that key freeze again at once.
- By starting payments and cancelling them, a spend key can make the account pay in fees up to twice what the daily limit lets it move: each start is paid inside the limit, each cancellation outside it.
- A daily limit below the fee leaves the spend key unable to do anything alone, and whoever holds a spend key can lower the limit that far at once. Two proofs set it again.
- Staking counts against the daily limit, and there is no two-proof path for staking above it. The way is to raise the limit, which waits. A validator owner's repair of its own collateral counts as well and is refused while the account is frozen, which matters during a validator safety hold: an owner account of a validator should weigh this before adopting the rules.
- A frozen account can still withdraw matured stake into its own balance: the engine checks the freeze only when something leaves the balance. Nothing leaves the account, and the wallet refuses it anyway.
- One waiting period (`delay_seconds`) serves both for payments above the limit and for a replacement by recovery keys alone.
- Approvals stay usable by any holder of a spend or recovery key until they expire or the settings change. Wallets should date them short. Approvals for a payment can be used only in the last hour before they expire. A key's acceptance of a role never expires.
- An account with less than one fee can be frozen and recovered by its recovery keys, but it cannot call off a replacement or act at once with two proofs until someone sends it the fee. This matters for an account whose value is staked rather than liquid, if two of its recovery keys are in the wrong hands.
- A refused root operation costs a node up to 17 signature checks and its sender nothing. Only a holder of a spend or recovery key of the account can cause it.
- In the waiting queue one paid protective action can be accompanied by others that exclude it and leave after the block without paying: at most four per key and 32 per account.
- The 30-second margin assumes that blocks keep arriving. After a stall longer than that, an ordinary action dated just past the margin can again be admitted and never included. Protective actions are not affected.
- During a validator safety hold a stolen sign-in key cannot be removed, because that takes an ordinary action. A freeze still works and stops sign-ins.
- An account that has adopted the rules cannot act as a protocol-4 guardian for another account; it can only withdraw.
- The rule that a frozen account does not sign in is applied by websites that use the login library, not by the chain.
- The settings of an account are public: its limit, what is waiting, whether it is frozen.
- The third review tested the waiting-queue weakness and its fix at the engine's admission interface, not by racing transactions on a live network of several nodes.

**Wallet screens and alert watch (16 November 2026).**

- **The wallet** (`web-v4/wallet/security-flows.mjs`, `security-ui.mjs`).
  - *Securing an account:* a login password, a payment password, a printed recovery sheet, and a passphrase the wallet generates. The passphrase has 72 bits and its key is derived with Argon2id at 256 MiB: its public key is on the chain, so anyone can test guesses against it.
  - *Then:* paying within the limit, waiting payments, paying at once with a recovery proof, freezing, an inbox of what is waiting, staking with the spend key within the limit, and adding a second browser.
  - *The emergency paths:* someone has my login, someone has my payment key, someone has my recovery sheet, I lost my device.
  - *The vault* keeps the sign-in and spend keys under different passwords, with each key's role bound into its encryption. No backup file can carry a spend key.
- **The alert watch** (`client-v4/security-watch*.mjs`, `deploy/watch`).
  - It reads each watched account's verified state through the light client. It tells the owner, by a signed webhook and a local feed, about waiting payments, limit raises, replacements, freezes, key changes and operations approved by several keys. Each alert gives UTC times and the action to take.
  - It also says when it cannot see an account in time to be useful, and when it has lost its memory.
- **Reviews.** Each was reviewed adversarially by a reviewer given only the code, and fixed, until no finding above Low was left. The reviewers' tests are now part of the suites.
  - *The wallet,* twice: 14 findings, then 4. The serious ones:
    - another tab could delete freshly made keys after the account was secured;
    - two flows let the login and payment passwords end up the same;
    - a leaked recovery sheet could not be replaced.
  - *The watch,* three times: 16 findings, then 7, then 3. The serious ones:
    - one dead webhook delayed every owner's alerts;
    - a webhook receiver could exhaust its memory;
    - queued alerts could reach another owner's webhook after a change of configuration;
    - a gateway holding back state could hide a payment until it was ready.
- **Not verified.** The wallet screens had not run in a real browser when this was written. On 19 November Chrome ran those for adopting the rules, paying within and above the limit, and freezing (see "In a real browser"); those for a second browser, for recovery, for replacing keys and for unfreezing have still not run in one. The alert watch ran against a live network on 18 November 2026, for minutes: as a running service it reported a waiting payment and a freeze, and in the upgrade rehearsal its code reported a scheduled and a cancelled upgrade (see "Preparing a first version"). It has not run for days, or for a real owner.
  - The limits are listed in `web-v4/wallet/README.md` and `deploy/watch/README.md`.
  - The main ones: a phone with little memory may fail the passphrase derivation (the person finishes on a computer).
  - On a laboratory network with waits of a minute, the watch must check at least four times per waiting period to warn in time. Production waits are at least two days.

## Privacy

Nothing in the new engine changes what is public. It is worth stating what that is:

- Accounts are pseudonymous: a chosen name and public keys. Balances, transfers and guardian settings of every account are public, as on Bitcoin, and easier to follow because accounts are reused.
- A gateway sees the internet address of the wallets that use it and which accounts they ask about. Wallets verify every answer, so a gateway cannot lie, but it can observe.
- No identity documents, phone numbers or emails are on chain or required.
- Recovery keys are bare public keys. Nothing on the chain says whether one is a sheet of paper, a passphrase or a friend, or who that friend is. Recovering an account involves no company and no identity check.
- The security settings of an account are as public as its balance: its daily limit, payments that are waiting, whether it is frozen.

Stronger privacy (hidden amounts, unlinkable payments) is a separate design step. It can be added later without weakening anything here, but it is not in this version.

## Fees paid on to validators

Added on 14 November 2026, after every measurement above. None of them used it, and nothing changes for a network that does not set it.

- The setting. A genesis may carry `fees_to_validators_ppm`. That part of the fees of a block then joins the new time shared by the validators who signed the block, and one rule pays both. Without it fees stay in the bank, which bounds what a network can sustain (see "Before any launch with real value", item 4). The mechanism is in `v5/README.md`.
- What it leaves alone. The supply rule: the fees wait inside the bank until they are paid, and the row that records them (`pos/fee_pool`) may never exceed the bank. A network without the setting has the same bytes, roots and network id as before; the differential tests against the protocol-4 engine run that case and pass unchanged.
- Independent review. One reviewer read the change with the code only and ran its own tests. It found no way to create or destroy currency, to make two nodes disagree or to stall the chain. It found one weakness in the design, which is removed: the first version paid the share of a validator whose signature was missing to the others in later blocks, so three validators of four gained by leaving the fourth out. Fees are now treated exactly like new time: that share stays in the bank and nothing is carried over. Four smaller points were taken as well. The share applies to the fees of a whole block, not to each fee, so a small share no longer rounds to nothing. Zero cannot be written, so a network without the rule has one genesis. The hook that counts a fee has no silent default. The engine refuses a block in which the protocol-4 rules moved anything but a fee into the bank. A second reviewer then read the reworked rule and reported no serious finding. Its four minor points were taken: the row is bounded by what one full block can charge; the recount output of a network without the setting is unchanged; the claim about a signature that is left out is stated exactly (below); and its test of that claim, which uses no model of the reward rule, is part of the suite.
- How it was checked. 26 tests in `v5/tests/fees.rs`, `fees_model.rs`, `fees_node.rs` and `fees_genesis.rs`: each rule case by case; random blocks on starting and on staked validators, with delegators, exits and a jailed validator, compared after every block with an independent recomputation on the proposer, validator and reference paths; every class of fee and of other bank income; mempool admission with and without the rule; a node stopped with fees owed and restarted; before every random block, that what a set of signers is paid is the sum of what each is paid alone; the forms of the setting that are read and refused. 111 engine tests pass in all (Windows).
- What stays true by design. A validator gets back its own share of the fees it pays, and validators acting together get all of them back at a setting of one million; a lower setting keeps a part out of their reach. What a missing signer would have received stays in the bank, so the long-run limit rises from about 200 transfers a second to about 200 divided by the share of voting power that misses blocks. It does not disappear. In the block that pays, what a signer receives does not depend on who else signed. Over many blocks a validator that is always left out earns nothing and falls behind the others in stake; that was already so for new time, and fees add to it.
- Not done. It has not run on a multi-node network: `campaign/bootstrap-v5.mjs --fees-ppm 1000000` is ready for that. The amount of the fee is still fixed.

## All new time to validators, and no bitcoin auction

Under the protocol-4 rule, four fifths of each second's new time leaves the bank only when someone bids bitcoin for it. With no bids, it stays in the bank. People could therefore get new time only by holding bitcoin, and the network depended on the bitcoin bridge, which is not safe for real bitcoin (C1, C2).

On 14 November 2026 the user chose to drop the auction. A network can now pay all of its new time to the validators who sign its blocks and, through them, to the people who stake with them. The genesis setting is `all_new_time_to_validators`; the design and formats are in `v5/README.md`. The user chose no share for development.

The setting is off by default, so every network without it keeps the protocol-4 rule, bytes and network id. The differential tests still compare those networks with the protocol-4 engine block by block.

**What changes on such a network.**

- Validators and their stakers receive up to 86,400 seconds of new time a day instead of 17,280, shared by voting power. Within each validator the protocol-4 split applies: owner and delegation pool, with a commission of at most 20% of the pool's part.
- The bitcoin actions (kinds 40 to 42, treasury governance 60 to 63) are refused, the SDK refuses to quote a bitcoin bid, and the wallet offers staking instead of the auction. Findings C1 to C8 cannot arise on such a network, and item 1 of "Before any launch" does not apply to it.
- In the long run, new time can pay the fees of about 1,000 transfers a second instead of about 200, before any fee is paid on to validators.

**The security question it raised, and the answer.** A starting validator's voting power is lent to it by the bootstrap rule and does not grow with its rewards. If all new time goes to validators, someone who keeps staking what it earns, and buys whatever the starting validators sell, grows by up to the whole issuance while the lent power stands still. Given enough time, it could outvote them. Another session, working on the stake hand-over rule (S2), pointed this out before the change was built.

The answer: while the bootstrap lasts, nineteen twentieths of a starting validator's own reward are added to its stake, and one twentieth is paid out.

This applies only to networks without the stake hand-over rule. With that rule, which the production profile requires, nothing is bonded for the starting validators. The rule keeps them above half of the votes by itself (see "Stake hand-over rule (S2)"). The worst case is then the one described there: one buyer of everything they are paid can come near half of the votes before the hand-over, but never reach it.

- *The first version bonded all of it.* An independent review showed why that fails. Nobody holds time at genesis, so nothing would have been spendable for the whole bootstrap, about 90 days in production. Nobody could have paid the fee to report a validator that signed twice: evidence is only accepted for 14 days, so double signing in the first 76 days could never have been punished. Nobody could have revoked a stolen key or given anyone their first seconds. On a network with seven or eight starting validators, one or two that never signed would also have blocked the end of the bootstrap for good. The review confirmed both with tests against the engine, and both are tests now.
- *Why a twentieth.* Worst case, in the production profile (20 starting validators, one minimum bond of lent power each, issuance one minimum bond a day, calendar fade of 90 days): one buyer acquires everything the starting validators are paid and stakes all of it, compounding.
  - It ends the bootstrap with about 12 to 15% of all stake. The upper figure is reached by delegating to the starting validators rather than running its own validator. If a fifth were paid out, the same buyer would reach about 46% of the votes, over the third that can stop the network. With nothing paid out it would hold nothing, but then nothing would work, as above.
  - The bound ends with the bootstrap. From then on all rewards are paid out. If the starting validators then sold everything they earn to one buyer, it would reach a third of the stake around day 119, half around day 159 and two thirds around day 238. Their stake from the bootstrap cannot be withdrawn while they validate, so new rewards are their only income, and selling is the natural case. After the bootstrap, the network is as safe as the spread of its stake, as any proof-of-stake network is.
- *At least five starting validators.* With four, one slashed validator leaves fewer clean validators than the roster needs, and the validator safety hold then stops every ordinary action until a new validator registers. Nobody would hold the time to register one.

**Reviews.** The design was reviewed independently twice, by a reviewer given the code and nothing else, who tested every claim against the engine. The first review found no fault in the arithmetic or consensus and none on networks without the setting. It found the two problems of the first version described above, plus smaller ones that are fixed: the SDK still quoted bitcoin bids, the harness could start a network with too few validators after paying for the machines, and the wallet text was inaccurate. The second review confirmed the fixes, refined the worst case from 12% to 12 to 15%, pointed out that the bound ends with the bootstrap, and found the four-validator stall that led to the minimum of five. Proposer, validator and reference paths agreed on every block of both reviews, and the supply rule and the recount held throughout.

**Tried on a live network.** Campaign `tc-v5-iss1` (14 November) built the current source on AWS as node SHA-256 `9dc6f6ba946801826c360172b49b37dd335cacaadc8efdcc667fc198887418b9`; its 144 engine tests passed on Linux first. It then ran seven validators in Paris and Virginia with the setting on.
- Wallets there verified every payment, all under a second (median 318 ms in Paris, 449 ms in Virginia).
- The 18 steps of the account-security check all went as the rules say.
- All seven validators recounted their ledgers from scratch: every recount passed, and the six that stopped at the same block have the same fingerprint.
- At the recount, 251.4 seconds had passed since genesis. Validators and their stakers held 222.9 s of it, 89%: 165.9 s spendable and 57.0 s staked, almost all of it from the starting validators' first minute, when their power was still lent. The bank held 28.5 s: shares of validators that missed blocks, rounding, fees and registration charges.
- On a network without the setting (campaign `tc-v5-sec5`), validators held 18% of the time issued and the bank 82%.

**Known limits.**

- The starting validators receive the network's first months of new time. In the production profile that is about 7.8 million seconds over the first 90 days, while nobody else validates, all paid out to them under the stake hand-over rule. Without the rule, about 7.4 million would be staked for them and 0.4 million paid out. That is about a quarter of the supply after one year and 2.5% after ten. Who they are, and what they pass on to independent validators, decide how fair the launch is and how soon the hand-over comes.
- Block time and the validators' clocks. Under CometBFT's time rule whoever holds more than half of the signing power sets block time (a proposer with more than a third can too, by leaving honest votes out of its block), and each block issues up to 60 seconds. Pushing the clock forward would mint that new time for the pusher and bring forward anything that waits for time: the fade, the end of the bootstrap, unbonding. It is bounded: CometBFT 0.38.26 refuses a block dated `block_time_tolerance` (60 seconds by default) or more ahead of a validator's own clock, and since 16 November the node narrows that to 30 seconds (`--clock-tolerance-seconds`, see `v5/README.md`, "Block time and this node's clock"). What remains is a one-time advance of up to the tolerance, as long as the validators keep their clocks by NTP.
- What does not reach a validator stays in the bank and never leaves it:
  - time beyond 60 seconds between blocks, for example during a halt;
  - the share of validators that did not sign;
  - rounding;
  - slashed stake;
  - the part of the fees not paid on to validators.
- Holders who do not stake lose share to those who do, as fast as the supply grows: by 100% in the second year, about 10% in the tenth, 1% in the hundredth.
- A starting validator that signed once and was then dropped may be left with a stake smaller than the two fees it needs to unbond and withdraw; someone has to send it a fee.
- On laboratory networks, voting power counts whole seconds of stake, and changes to it are rationed. Starting validators' stakes can therefore drift far apart: in one review run three of seven held 64% at the end of the bootstrap. In the production profile, growth stays far below the rationing limit; that was checked on paper, not simulated.

## Stake hand-over rule (S2)

A network sets it with `stake_handover: true` in its genesis; the production profile requires it. The rule, its numbers and its limits are in `v5/README.md` ("The stake hand-over rule"). In short, the starting validators keep more than half of the votes until independent stake has held a target for fourteen days. The target is forty bonds plus a fifth of all time issued. Their own stake never counts toward it. They then hand over at the pace of the churn limit.

**How it got here.** Four designs, each reviewed independently with tests against the code:
- *First design.* Starting validators faded against staked stake. Stake that the 30% cap kept out of the roster still counted; stake brought for a few hours ended the bootstrap for good; seven bonds that bonded their rewards took the network by waiting. One stranger's delegation could pin an operator's exit.
- *Second and third designs.* Only stake seated in the roster in force counted, the starting validators filled the gap to the target, and the target had to hold for fourteen days.
  - Their review found that stake held by a starting validator with no funding counted as seated but gave nobody a vote (critical).
  - It found that the starting validators left as soon as the target was reached. Whoever then held the target held every vote during the hold, and could date its blocks ahead to end the hold early (high). A later review of the clock check found that CometBFT 0.38.26, the version the project uses, already refuses blocks dated 60 seconds or more ahead of a validator's clock, which bounds that attack on a real network; the staking model the review used could not see it.
  - It also found that a few remaining starting validators could not fill the gap, and that exits waited for their group move.
- *Fourth design* (this one).
  - Seated stake is independent stake only.
  - The starting validators keep more than half until the end, counted against what everyone else asks to stake, so they rise first.
  - The end needs seven funded independent validators in force.
  - The share grows by a fifth of the time issued, not a quarter; at an eighth, stake that bonds its rewards would have gained on the target by waiting.
  - On a network that pays all new time to validators, nothing is bonded for the starting validators, because independent stake can only come from what they are paid. The session that built that setting proposed this.
  - The attacks of the earlier reviews are tests that the attack fails: `pos/tests/handover.rs` and `pos/tests/review*.rs`.
  - With the rule off, a random workload of 40 runs gives the same results and the same serialized bytes as the code before the change (`review_rule_off_differential.rs`).

**What it rests on.** The hold is counted in block time. CometBFT refuses a block dated `block_time_tolerance` (60 seconds by default) or more ahead of a validator's own clock, and the node's clock check narrows that to 30 seconds. So block time cannot run ahead of the honest validators' clocks, and the hold cannot be shortened, as long as validators keep their clocks by NTP. Keeping more than half means that no block is final without the starting validators. The target is the price of a third of the votes, which can halt the network.

## Starting a production network

Two tools make it possible to start a network with the production profile and real operators: a genesis ceremony, and the deployment kit for the new engine. `deploy/PRODUCTION-V5.md` gives the order of work.

**Genesis ceremony** (`tools/genesis-v5.mjs`).

How it works:
- Twenty operators each make a signed entry from their own key enrollment.
- A coordinator collects the entries and writes the ceremony: chain id, genesis time and fee choices.
- Every operator rebuilds the genesis, finds its own entry unchanged, and pins the hash it computed itself.
- Every input is public and the build is deterministic.

What protects it:
- Each entry is signed by the operator's consensus key over the chain id, so a coordinator cannot change anyone's owner account or commission.
- Input files must be in one canonical form, so a key written twice cannot show one value and parse as another.
- Keys the node would refuse are refused, points of small order included. This is checked against the node's own library on 2,108 keys.
- The bitcoin, treasury and auction sections that the format requires carry keys derived from a hash, which nobody holds.

`v5/tests/production_genesis.rs` starts the node from such a genesis with twenty validators and runs blocks on it.

It was reviewed independently twice. The first review found that entries were not authenticated and that a key written twice in a file could hide a substitution. Both are fixed, with the rest.

**Deployment kit for the new engine** (`tools/release-v5.mjs`, `deploy/`).
- The protocol-4 kit (source-allowlisted releases, digest-pinned images, a runtime guard with an externally signed signer lease, a mandatory remote signer) now also builds and runs `time-node-v5`.
- Version-4 releases are unchanged byte for byte.
- An engine is bound to its network by the signed lease and by a marker written on both volumes, so a release of one engine cannot start on the other's network data.
- Reviewed independently twice. Nothing above Low remained after the first review, and the Lows are fixed.

**Not verified.**
- No Docker build of the new image, no run on several hosts with a remote signer, and no ceremony with real operators have been done.
- A network started this way is a rehearsal: the engine accepts only development chains and reports that public launch is not allowed.

## Preparing a first version (17 and 18 November 2026)

The owner decided that a first version launches what exists: payments, sign-in, staking, the account security rules, the wallet and the alert watch. Later features come as upgrades of the running network. This section covers what was added for that.

Each part was built on its own branch and reviewed by a reviewer who was given the code, not the author's conclusions, and asked to break it. It was then fixed and reviewed again. The reviewers' tests are part of the suites.

**Changing the rules of a running network** (`docs/design/upgrade-mechanism.md`, `v5/src/upgrade.rs`, `spec/protocol-4.md`).

How it works:
- Owners of validators signal support for a next version (action kind 80). When signals hold four fifths of the voting power, a plan is scheduled, at least 21 days ahead. If support falls under three quarters before the start, the plan is cancelled.
- The first block dated at or after the start time is the last one under the old rules. A program that implements the new version continues. A program that does not executes that block, saves its state, and stops with a message that says what to install (exit code 4). It never executes a block under rules it lacks.
- A version never changes what an existing kind of action does. New behaviour is a new kind.
- Wallets, servers, the alert watch and the explorer learn the version in force, and any plan, only from proven state and signed headers. A client that does not know the version in force stops and says that it needs an update.
- Operators can also agree on a height at which every node stops (`--stop-after-height`), for an emergency.

Reviews:
- *The design,* before any code. Sound with changes; no way to split the network was found.
- *The engine,* twice. No split was found, and a network on which nobody signals has the same state roots as under the engine certified before. Two rules changed after the reviews:
  - A validator safety hold cancelled a pending activation, so one validator with a minimum bond could cancel any upgrade by getting itself jailed at the start time. A hold now postpones the activation, for up to an hour.
  - A jailed supporter left the support but stayed in the total. Whoever stole one supporter's consensus key could then cancel a plan with thin support by signing twice. A jailed validator is now left out of both.
- *The clients* (verifier, SDK, servers, wallet, watch, deployment kit), three times. The serious findings:
  - a gateway could make a client report that an update is required, by shaping its answer as a JSON array. That report is now set in one place only, from the verifier's own refusal of a signed header;
  - whether a network's nodes answer the question about upgrades was learned from a gateway's error text. It now comes from the trust data the client pins, and such a client asks with every read, so a gateway cannot leave the answer out;
  - the alert watch held back its other alerts while it waited for the upgrade read.

Limits:
- Until the hand-over, the starting validators hold more than half of the voting power. No upgrade is scheduled without them, and while they hold four fifths they schedule alone.
- The 21 days protect only operators and users who watch. The node warns in its log and its status; the alert watch reports a scheduled and a cancelled plan.
- A node admits and proposes a signal only for a version its own program implements. So the release that implements a version must be running on validators before anyone can vote for it.
- When the rehearsal below ran, no shipped tool could send a signal: its test harness built the bytes. The SDK and the wallet can now (see "Voting from the wallet"), and a test shows that the SDK builds the same bytes as the engine's own signed examples.

**Voting from the wallet** (`client-v4/time-sdk.js`, `web-v4/wallet/upgrade-signal*.mjs`, `web-v4/wallet/signing.mjs`).

What it is:
- The SDK builds, signs and decodes the signal, and reads from proven state what an owner needs: the version in force, each plan, every validator's signal, and the share of the votes against both thresholds.
- The wallet has a tab for an account that owns a validator. Whoever decides which hash owners support decides the network's rules, so the tab never fills anything in: the owner types the version, the hash and the start time from the release announcement, and the wallet compares them with what proven state holds.
- The alert watch tells an owner when the signal of their validator changes. A stolen spend key can vote, and the answer to that (freeze, then replace the key) only works for an owner who is told.
- A signed signal stays usable until another action of the account is in a block. The wallet says so when an owner discards one, and says it if a discarded signal was included after all.

Review: once, independently. The signal's bytes matched a copy of the engine's decoder on 40,000 altered payloads, and the wallet's count matched a copy of the engine's on 4,000 generated sets of validators. What it found, all corrected:
- when a gateway refused a read, its error text appeared under the form as if the wallet had written it, and could carry a hash ready to paste;
- a quoted gateway answer could carry such a hash as well;
- the wallet said a discarded signal dies when the account signs another action, which is too early;
- a share the wallet could not check was shown in the review without saying so (80% where the network counted 60%);
- nothing told an owner about a signal they did not send;
- seven lesser faults, and a gap in the tests: the lines of the wallet page that decide which key signs which kind of action were not tested. They are now in a module with tests.

Not verified:
- The reviewer did not read the corrections; the lead checked them against the reviewer's tests.
- No browser has opened the tab. In particular, whether a held Enter key can confirm the review must be checked there; the review now needs a box ticked first. (On 19 November a browser showed that a held Enter key did confirm a review without such a box, an ordinary payment. That is fixed for every review, with or without a box; the tab itself has still not been opened in a browser.)
- No node has taken a signal signed by the SDK outside tests.

**Joining without replaying every block, and deleting old blocks** (`v5/src/statesync.rs`).
- A node can start from a snapshot of the state that peers offer (CometBFT state sync). It accepts the state only if its root is the application hash that its own CometBFT verified for that height.
- `--keep-blocks` lets a node delete old blocks, but never fewer than the last 2,000,000: CometBFT needs them to judge evidence.
- Reviewed twice. The first review found that a peer could stop a joining node with one oversized chunk, and that a forged snapshot made the node use 46 times the snapshot's size in memory before refusing it. Both are fixed: the root is computed in one pass before any tree is built, chunk and frame sizes are bounded, and a node that has executed blocks never restores.
- Limits, all in `v5/README.md` ("State sync and pruning"):
  - For about 23 days after its restore, such a node cannot judge evidence about heights before its snapshot. If a block carries such evidence, it stops and must sync again. Validators that restored within that time should hold less than a third of the voting power.
  - Its recount says that it did not verify the history before the snapshot.
  - Gateways, the API and explorers need a node that keeps every block and was synced from genesis.

**HTTP API and block index** (`client-v4/indexer.mjs`, `client-v4/api.mjs`, `docs/integration-guide.md`).
- For exchanges, shops and wallets: status, blocks, an action by its hash, an account's payments, submission of signed actions, and a stream of events.
- What comes from the index is not proof. Every answer says how to verify it, and the guide's recipes credit a deposit only after the integrator's own light client has verified it.
- Reviewed twice. The first review blocked it:
  - following the guide could pay a withdrawal twice, because a lost answer led to signing a replacement;
  - one stream request could freeze the service;
  - deposits made through one of the account security actions (kind 75) did not appear.

**Explorer pages** (`web-v4/explorer`).
- Pages the API can serve, where anyone looks up a block, an action or an account. The visitor's browser follows validator signatures from the block the page trusts and checks what the service says.
- A figure the page could not check carries the words "Not checked, the service's word" in front of it.
- Reviewed twice. The first review found that the page said "no such account, checked" from the service's status code alone, and two more ways to show the service's word as checked. The second found three lesser faults: blocks older than 14 days were said to be beyond proof when they are not, an answer without proof was worded as a fact, and loading the page's own files could use up a visitor's request allowance.

**Faucet for test networks** (`client-v4/faucet.mjs`).
- It gives small amounts on test networks and refuses any other chain. It holds a spend key only, within a daily limit set on the chain, counts its own limits in proven block time, and freezes its account if it sees a waiting payment or a raise of the limit that it did not make.
- Reviewed twice. The first review blocked it: a node that answered "refused" while keeping the bytes was paid outside every limit; the faucet stopped for good after 64 grants on a node without a transaction index; and its README understated what a stolen faucet key can do (start a waiting payment of any amount, which goes through unless it is cancelled in time).

**An open-source project.**
- The tree is under version control. The licence is Apache-2.0. There is a security policy, a contribution guide, governance rules and a code of conduct.
- `tools/licenses.mjs` lists the licence of every dependency (`THIRD-PARTY-LICENSES.md`) and fails on one that is not on the allowlist.
- `tools/export-public.mjs` makes the public copy: it copies only the files named in `public-manifest.json` into a new directory, and refuses private keys, cloud credentials, account numbers, e-mail addresses, paths of a developer's machine and documents with entries still to fill.

- `tools/ci-checks.mjs` is the one list of the repository's checks. The workflow for GitHub starts every check through it.
- `docs/audit-package.md` says what an external audit is asked to look at.

**Signer leases** (`docs/design/signer-lease-controller.md`, `deploy/lease-controller`, `deploy/lease-agent.mjs`).

What it is:
- The deployment kit runs a validator only while a file on its host holds a fresh lease: a short statement, signed by an authority the host pins, for that validator's consensus key, release, genesis and engine. The purpose is that one consensus key never signs on two hosts at once.
- Nothing in the repository issued such leases. A reference controller now does. An agent on each validator host keeps the lease file fresh, and the operator has commands to give a key to a host, move it, and approve a release for an upgrade.
- The kit's guard changed with it. A validator runs until the last lease that verified expires. It is then told to stop within 5 seconds, and its consensus process is killed within 15, measured on the wall clock and on a clock that cannot be set back.

What it claims, under five stated assumptions (clocks within five seconds of true time, one controller for one authority key, no stolen key, a file system that keeps what was synced, one machine for one host):
- for one key, two leases to two different hosts are never valid at the same moment, and the second is first valid a stop time after the first ended;
- a lease to another host carries a higher token, and tokens never go down.

Reviews: independently twice, then a third round of corrections that the lead checked against the reviewer's tests. Inside the assumptions, neither review found two valid leases for one key or a forged lease. What they did find, all corrected:
- *First review.*
  - A controller started while its clock was behind skipped its waiting time once the clock was corrected, and two hosts then held valid leases.
  - After a lost state a new controller could issue a lower token than the old one.
  - Someone on the network path could freeze a key by replaying a recorded request.
  - The changed guard could stop a healthy validator after a clock step or a stall of 13 seconds, and the time it took to stop a validator after its lease ended was not bounded.
  - State files put back under a running service were followed without the waiting time.
  - Several sentences claimed more than the code gave.
- *Second review.*
  - At a start, "this lease still runs" was judged from a number that a start on a wrong clock writes. With a restored copy of the state, that gave two more routes to two valid leases.
  - The guard counted a lease's remaining life on the wall clock only, so a host clock set back kept a validator alive for that long.
  - Seven lesser faults.

What a lease does not do:
- It is checked by the guard every five seconds, not by the signer at each signature. A signer that is given a key without the record of what the last signer signed, or whose state was copied or restored, can sign twice, and no lease sees it.
- The kit's lease format carries the words "every signature". The controller writes them only when the operator declares, host by host, that the signer enforces it. No signer known to the project does, so either that wording is relaxed or a check at each signature is built. That is the owner's decision.
- A controller that stops takes its validators down within about four minutes, and each must be started by hand. The documents recommend several controllers, none serving a third of the voting power, never two for one key.

Not verified:
- Everything ran under tests and on one machine: on Windows, and once on Linux (18 November, campaign `tc-v5-final1`: 110 tests, none skipped). The three tests that Windows cannot run passed there: a real process that ignores the stop signal is killed, and the lease file and the key file have the intended permissions.
- Nothing ran with CometBFT, a remote signer, Docker, or two machines with their own clocks.

**The compiled verifier on Linux.** Linux built a `.wasm` file that differs from the committed copy, which had been built on Windows: 143 bytes longer, from the same source with the same toolchain. The glue files (`.js`, `.d.ts`) were the same. The two files, compared side by side, show why:

Neither can be set by the build script. What was done:

- On another system the build script replaces the compiled copy only when asked with `--local`, and says that such a copy must not be committed.
- The workflow's job for this check is no longer allowed to fail.

What follows from it: on Windows nobody can check on their own machine that the `.wasm` file is what the source builds. That check is made on Linux x86-64. Linux on ARM and macOS were not measured; the build script treats them like Windows.

## Validators from outside (21 November 2026)

The owner asked that the explorer's Validators page say how to join as a validator, with the script to run and how it works. `testnet/README.md`, "Validators from outside", says how it is built.

**What the rules allowed already, and what was missing.** Registering a validator has been open to any account since protocol 4: a signature of the validator key over the network, the account, the key and the commission, and a bond (one second on a laboratory network such as the test network, a day of seconds on a production one). The wallet had a form for it, in the words of the laboratory. **What was built.**
- **The page.** "Run a validator" on the explorer's Validators page: how it works in eight short points (two keys, the bond, votes, pay, being offline, signing twice, stopping, who decides), what is needed, four steps with the three lines to type, what the script does, and the network's files with their hashes. The network's own facts come from an optional `join.json` next to the page, which the API serves when it is set up with them (`explorer_join`). Every value is held to one strict form on both sides, the two outside links are made only from addresses that passed, and without the file the page gives the general explanation.
- **The script** (`testnet/join.sh`), written to be read before it is run. It downloads the node program, CometBFT and the genesis file from the network's own address and stops unless each has the SHA-256 written in it; makes the validator key on that machine; connects out to the entry node and listens on the machine only; starts two systemd services; and prints the registration text. It knows no key or password of an account. The services write the network's values into it, each in one strict form, because strangers run it as root.
- **An entry node.** One more machine: no validator, P2P open to anyone, RPC on the machine only. The five validators stay closed to everybody but each other and it.
- **The downloads**, handed out by the proxy under the main page's address. The node program is the certified one, by its hash; with this it is public for the first time, as a compiled program. - **The wallet's validator panel** in plain words, with one plain answer for a text that is not a registration of this account, and what it says of the validator taken from the chain (in the set, in line for it, without a bond).
- **Checks.** `launch.mjs --join-check` starts a machine that does what the page says, with the public addresses only, while the services machine plays the owner: it registers the validator with the text the script printed, counts the validator's signatures in the forty blocks after it joined the set, looks for the owner's pay, and takes the bond out again. ## Names that look alike (22 November 2026)

The owner asked for a rule that refuses a new account name when it looks like a name that exists. `v5/README.md`, "Names that look alike", says how it is built. The rule itself was decided beforehand; this section says what was built, what was found on the way, and what is not covered.

**Why.** A payment goes to a name. Someone who registers `paypa1` beside `paypal`, or `al_ice` beside `alice`, can pass for the other account: in a request for payment, on a website that greets `@name`, or in a list of past payments, where the victim picks the wrong line (address poisoning). Uppercase letters, letters of other alphabets and spaces were already impossible: a name is 2 to 15 bytes of `a-z`, `0-9` and `_`. What was left is inside that alphabet.

**The rule.**
- Two names look alike when they have the same skeleton. The skeleton of a name: every `_` is removed; `0` is read as `o`, `1` as `l` and `w` as `vv`; then, in one pass from left to right, `rn` is read as `m` and `vv` as `w`.
- A network sets the rule with `distinct_names: true` in its genesis. Its state then keeps one row per name, under the name's skeleton, starting with the genesis accounts.
- A genesis in which two names look alike, or a name is made of underscores alone, is refused.
- A new name is refused if its skeleton has a row, or is empty. The refusal gives the existing name: "the name paypa1 is too close to the existing name paypal".
- The production profile requires the setting, as it requires the stake hand-over rule. The laboratory profile takes both.
- The setting is off unless the genesis says otherwise. A network without it has the same bytes, state roots and network id as before.

**Where a name is refused, and what that costs.** A name is created by one action, the reveal that follows a sponsored registration. The sponsor's action carries only a commitment, so nobody can judge the name before the reveal: not the chain, and not the registration service that pays. A refused look-alike is therefore handled like every refused reveal before it. Nothing changes in the state. The commitment stays until it expires, a day at most. The sponsor's charge and fee are not returned. A test makes the same steps for a look-alike and for a name that is simply taken, side by side.

**What it does not cover.**
- Softer look-alikes: one changed letter, `i` for `l`, `b1nance` for `binance`. They are registered. They are left to a wallet's warning, which is the wallet's own work and is not part of this change.
- `vw` beside `wv`: found while building, and closed before any network used the rule. As first decided, the rule read `vv` as `w` but not `w` as `vv`. So `vvv` and `wv` were one name to the rule and `vw` another, although it looks the same; any name with a `w` next to a `v`, or with two `w` in a row, had such a twin. The rule now reads every `w` as `vv` first and then makes the same pass. The 28 first test vectors keep their values and five more hold these cases (`vw`, `wv`, `vwv`, `ww`, `vvvv`). A rule like this cannot change once a network that matters has started, so any further change must come before that.
- Names from before. The rule protects the names of a network that had the setting from its first block. It cannot be switched on later: the setting is part of the network id, and names registered without it may look alike already. The public test network of 20 November does not have it and will not get it.
- Taking a name first. Whoever registers `paypa1` first keeps `paypal` out. That costs one registration, the same as taking `paypal` itself did before. On a test network a faucet pays for registrations, so there it costs nothing.
- Knowing before paying. A wallet cannot yet ask, with a proof, whether a name is too close to another. It learns of it when the reveal is refused, after the sponsor has paid. See "Not built".

**What was built.**
- Engine: the skeleton and the rows (`v5/src/names.rs`), the setting and the genesis checks (`genesis.rs`), the check at the reveal and the recount (`engine.rs`). The recount requires one row for every account on a network with the setting, and none on a network without it.
- SDK: `TimeSDK.nameSkeleton(name)`, and `TimeSDK.distinctNames(state)`, which reads the setting from a verified state.
- Genesis writers: the production ceremony writes the setting and refuses two operators' names that look alike, naming both. Every network the AWS harness starts with a node built from the tree has the setting, the kit rehearsal included.
- The harness's load tools named their accounts by index in base 36, where index 1 is `1` and index 21 is `l`: the second would have been refused. They now use 32 symbols without `0`, `1`, `m` and `w`.

**Not built.**
- The proven read for wallets. It needs a field in the node's state query, the same field in the gateway and in the light-client verifier, and the compiled verifier built again on Linux, where the repository's check compares it byte for byte. It could not be finished on the machine this was built on.
- The test-network launcher does not switch the setting on. It starts a node program certified before the rule, by its hash, and that program refuses a genesis that carries the setting. The launcher now keeps the choice in the record of each launch, so that running a launch again never asks for another genesis than the first run. The choice stays off until a program built from this tree is certified. *One was certified on 23 November (`tc-v5-final9`), and a test network launched or reset since then gets the setting (`testnet/README.md`, "The four settings of a genesis").*
- The specification `spec/protocol-4.md` is unchanged. It lists the row namespaces and says that no other row exists, and it lists the genesis settings. Both lists lack the new entries. The file's hash is the specification hash of version 4, which the engine and two test fixtures pin, so changing it is a decision of its own.
- The engine still calls itself 0.7.0. Two programs now carry that number: the certified one, which refuses a genesis with the setting, and this one. They cannot split a network: they agree on every network without the setting, and the older one cannot start on a network with it. The number should change before a release. (It changed to 0.8.0 with the next section's two settings.)
- No wallet or explorer change. Both were being changed by someone else at the time.

**How it was checked.**

The 28 test vectors; every name of up to five characters over the letters the rule touches; the forms of the setting; the genesis; 24 look-alikes refused and 14 distinct names accepted, some of them softer look-alikes; names of underscores; two look-alikes in one block and in the waiting queue; the state after a refusal, beside the refusal of a name that is taken; proofs of a row and of its absence; a recount of six damaged states; the report of the recount command with and without the rule; a node through its mempool, a proposal, a restart, and a second node that joins from a snapshot. Proposer, validator and reference paths agreed on every block.
- Three programs compute a skeleton: the engine, the SDK and the ceremony. Beyond the shared vectors, the engine is compared with the ceremony on 6,000 names, and the ceremony with the SDK on 86,420, most of them made of the letters the rule touches.
- Unchanged without the setting. Before any engine file was touched, a run that registers eleven accounts on two networks, look-alikes among them, was recorded block by block: network id, state root, metadata hash. The engine with the rule gives the same values. The earlier recorded roots (`tests/golden.rs`) and the block-by-block comparison with the protocol-4 engine (`tests/differential.rs`) pass unchanged.
- JavaScript: the SDK and the ceremony against the vectors; the harness's genesis bytes against the node's; 120,000 load account names on each of eleven chain ids with no two alike; the launcher's record of a network from before, which asks for the same genesis options as before and writes nothing for a chain that exists.
- One existing test changed: the production genesis in `v5/tests/handover.rs` now also carries the new setting, since the profile requires both.

**Not verified.**

- The Linux build and the Linux test run were not made. *Made on 23 November: see "Run on AWS and in a real browser (23 November 2026)".*

## Waits that survive a stop, and accounts protected from the start (22 November 2026)

Two rules for account security, each a setting of a network's genesis. `v5/README.md` says how they are built ("Waits that survive a stop", "Accounts protected from the start"), and `spec/settings.md` specifies them. This section says what the gaps were, what was built, what was tested, and what is not verified. The production profile requires both settings.

### Waits that survive a stop

**The gap.** The account security rules make things wait so that an owner can cancel in time: a payment above the limit, a raise of the limit, a replacement of the keys. A freeze lasts for a set time. All of these were compared with the chain's time. A chain of this kind can stop for hours or a day. When it starts again, the next block carries the real time. Every wait has then run out while no owner could send anything. Whoever can stop the chain could defeat the waits. The upgrade rule already protected its own notice: a plan is cancelled in a block dated more than an hour after its parent. The account rules had nothing like it.

**The rule.** `waits_survive_stops: true`.
- A stop is the part of the gap between a block and its parent that is longer than one hour, the same hour as in the upgrade rule. (On 23 November the clock got a threshold of its own, five minutes, before any network used the setting: see "Service records, and a shorter threshold for the waits clock". This section describes the rule as it was built on 22 November.)
- The chain keeps the total of all stops as one number in its metadata, `stopped_micros`. The block after a long gap adds to it. That is one addition per block, whatever the number of accounts.
- The active clock is the chain's time minus that total. A block moves it by the time since its parent, and by an hour at most.
- Everything the account rules store and compare is on the active clock: when a waiting payment, a raise and a replacement are ready, until when a replacement can be finished, until when a freeze lasts, when a key may freeze again, and whether a validator's owner is frozen when upgrade signals are counted.
- The daily allowance refills on the active clock too. On the chain's time a stop of a day would hand a thief with the spend key a second full limit in the first block, with no moment in between for the owner to freeze.
- Staking, the hold on stake that leaves, the stake hand-over and the notice of an upgrade are unchanged.

**One thing was decided differently from the first idea.** The dates that keys sign stay on the chain's time: the expiry of a freeze, and of the approvals of a root operation. A signature says until when it may be used. On the active clock, approvals for a large payment that were dated for one hour would still be good a day later, after a stop, when their signer thinks they are dead. On the chain's time a stop can only shorten what a signature allows, and the owner signs again. The price: a freeze that an owner signed in advance and left with a watch service can lapse during a long stop.

**The attacker's questions, and the answers.**
- *Can validators make waits last for ever by dating blocks far apart?* No. Each block moves the active clock by up to an hour, so blocks dated a week apart end a three-hour wait after three blocks. A gap cannot be faked by dating a block into the future: a node refuses a proposal dated more than 30 seconds ahead of its own clock (`app.rs`, `process`), and CometBFT refuses one 60 seconds ahead.
- *Can a stop still shorten a wait?* Yes, by up to one hour each time. The first hour of a gap counts, because the chain cannot tell a stop from a slow block before the hour has passed. A wait with less than an hour left is over after any stop. Production waits are at least two days.
- *How few blocks can a wait be squeezed into?* One for each hour of the wait. A chain that is let run for a moment once an hour uses up a two-day wait with 48 blocks. Someone who can stop the chain at will, and let it run at will, can still do that. A lower threshold than one hour would raise the number of blocks. It was kept at the hour the upgrade rule uses. (Lowered to five minutes on 23 November: 576 blocks for a two-day wait.)
- *Who can undo the rule?* Whoever sets block time: more than half of the signing power, or just over a third when it proposes. After a stop such a group can date the next blocks an hour apart, and each hour counts. Honest validators date blocks by their own clocks, so the stop shows as one gap.
- *Validators that leave an owner's cancellation out of blocks.* The rule does not help. The waits run while blocks are made, whoever makes them.
- *The first block after genesis.* Its gap is counted from the genesis time. Validators that start six hours late leave a stop of five hours, and nothing waits yet.
- *A node restored from a snapshot or by state sync.* The number is in the metadata row, under the state root. A test restores a node at a height between two stops and compares it with the node it came from.
- *A wait asked for before a stop and read after it.* Stored on the active clock, so it is due when the chain has run for the whole wait. Tests check the exact microsecond for a payment, a freeze and a replacement.
- *A total that is wrong.* The recount adds up the stops among the block times the state holds. For the first fourteen days of a chain that is every block, and the sum must equal the number. Later it must not exceed it.

**What clients show.** A moment in a security row is not a date any more. A client that compares it with the chain's time shows a payment as ready, or a freeze as over, too early by the total of the stops, and the chain then refuses.
- The SDK reads the number from verified state (`TimeSDK.stoppedMicros`, `securityNow`) and turns a stored moment into a date (`securityDeadline`), which is the earliest possible one while further stops can come.
- The login service and the SDK's count of upgrade signals use the clock.
- **The wallet did not yet when this section was written.** It was right until the first stop on a network with the setting. The wallet was being changed by someone else and was not touched. (Then the alert watch and the faucet did not either. All three do now: `client-v4/security-watch.mjs` and `client-v4/faucet.mjs` read the total of stops from verified state, and since 23 November the wallet does too, `web-v4/wallet/security-flows.mjs`, `waitsOf` and `momentOf`: in Chrome on a laboratory network on 23 November, where the chain did not stop, and across a stop on a stand-in chain only.)

### Accounts protected from the start

**The gap.** An account adopts the security rules with an action that costs a fee, and a new account holds nothing. So nobody could be protected from the moment of sign-up: every account began with one key that could do everything. The owner accounts of the starting validators began that way too, and the runbook told operators to protect them "in the first days".

**The rule.** `protected_registration: true`.
- A registration can carry the set of keys and the policy that the adopting action takes (kind 45). It takes the place of the reveal after a sponsored registration and costs nothing more. The account exists with its keys in their roles from its first block. A registration without a set stays valid.
- The set is judged by the same code as the adopting action. A test sends thirteen bad sets through both and requires the same refusal, word for word.
- The account has no number yet, so each key accepts its role for the registration key that will create it. That acceptance is good for nothing else.
- **The commitment names the set.** The sponsor pays for a hash of the name, the salt and the set. A registration with other keys, another limit or another wait does not match it, whoever signs it, and neither does the protocol-4 reveal. So nobody who sees a registration on its way, and nobody who gets hold of the registration key after the commitment, can take the name with keys of their own, or with one key that can do everything.
- The registration key is the account's identity key and no key of the account, unless the set lists it.
- A genesis can list accounts that start with a set (`protected_accounts`). The ceremony requires it of all twenty owner accounts: a payment key, a login key and two recovery keys, a daily limit, and waits of two days or more. An entry without them is not made, and the consensus key signs them with the rest of the entry.

**What it does not do.**
- A wallet must build the registration with the set. The SDK has the functions; when this section was written the wallet did not use them. It does since 23 November (`web-v4/wallet/signup.mjs`), and did so in Chrome on laboratory networks that day (see "Run on AWS and in a real browser (23 November 2026)").
- When this section was written, the HTTP API and the explorer had no name for kind 45. They have one now: the SDK names it `register_protected` (`TimeSDK.KINDS.register_protected`), the API gives that name (`client-v4/api.mjs`, `kind_name`), and the explorer puts such an action into words.
- Until the sponsor has paid for the commitment, the registration key decides everything: the name, the keys, the policy. A key's acceptance names its role, not the policy.
- If a commitment lapses, whoever holds the registration key can pay for another one, with other keys.
- A refused registration costs a node up to nine signature checks and its sender nothing. It needs a paid commitment to exactly that set.
- A protected account takes three to five times the bytes of a plain one (with four to eight keys), for the same registration charge. This is an estimate from the row formats, not a measurement.
- The list of protected genesis accounts is part of the metadata row, which every proof for a wallet carries: about ten kilobytes more for twenty accounts.
- The engine does not require that a starting validator's owner account is protected. The ceremony does.
- An owner account of a validator now lives under a daily limit from the first block. Staking counts against it, and so does the repair of the validator's own collateral, which is refused while the account is frozen (see the known limits of "Account security").
- The ceremony does not check that an operator holds the keys it names. A wrong key harms only that operator.

### What was built

- Engine: the two settings and the genesis list (`genesis.rs`), the number in the metadata row, the clock and kind 45 (`engine.rs`), the rules (`security.rs`), the recount, and the report of `--audit`. The program is now `time-node-v5` 0.8.0: it knows settings that 0.7.0 refuses in a genesis. The two cannot split a network, because a 0.7.0 node cannot start on a genesis that carries either setting, and on a network without them both follow the same rules.
- SDK: the readers and the date helper, the commitment, the acceptance and the registration (`client-v4/time-sdk.js`, `account-security.mjs`). The login service reads a freeze on the active clock.
- Ceremony: every owner account starts protected. A new command makes one key file at a time. The runbook says what each operator prepares.
- `spec/settings.md` specifies `distinct_names` and the two new settings. `spec/protocol-4.md` is unchanged, and its hash does not cover the new file.

  - *Waits:* the number block by block; a waiting payment, a freeze, a raise of the limit and a replacement, each across a long gap and a short one; a replacement that lapses after exactly seven days of chain; several stops; a stop in the first blocks; signed dates; a thief who stops the chain for three days, with and without the rule; what a stop still takes; a frozen validator owner's signal after a stop; the recount of five damaged states; a node through its mempool, a restart and state sync.
  - *Registration:* the account and its first block; what it can and cannot do there; thirteen bad sets through both actions; ten registrations that do not match their commitment; an acceptance moved to another registration or to an account; two registrations of one name; a genesis with protected accounts and fourteen wrong ones; the production profile; a node through its mempool, a restart and state sync.

## Found by fuzzing (22 November 2026)

Fuzz targets were written for the engine, staking and the proof verifier (`docs/fuzzing.md`). Writing them found two defects, before any campaign had run. Fixing those two found a third of the same kind. This section says what they were, what an attacker could do with each, how they were fixed, what was tested and what is not verified.

**The cause.** Votes, headers and validator keys arrive as JSON and are read with the types of the `tendermint` crates (0.40.4). Two readers under those types do not refuse every text they cannot read. On some texts they panic, and a panic ends the program.
- The base64 decoder (`subtle-encoding` 0.5.1). It makes room for its result from the length of the text without the `=` signs at its end: three bytes for every four characters. Then it writes three bytes for every four characters but the last one to four, whatever those characters are, and for the last ones one byte fewer than there are before the first `=`. A text with more `=` signs at its end than base64 has, such as `A========`, gets room that is too small. A text whose last characters begin with `=`, such as `=` or `AAAA=A`, makes it write "minus one" bytes. A signature exactly as consensus writes it, with one `=` added, is such a text.
- The date reader (`tendermint-proto`, with `time` 0.3.55). It converts every date to UTC with a call that panics when the result leaves the years the library knows. One kind of date does that: the last day of the year 9999 with an offset behind UTC, such as `9999-12-31T23:59:59-00:01`, which is a moment in the year 10000.

**F2 and F3 in the engine: one transaction stopped every node it reached.** Evidence of double signing (action kind 20) carries two votes, and anyone may send it. The engine read the two votes before it checked anything about them and before it took the fee. A vote with such a signature (F2) or such a timestamp (F3) made the node panic, and a node's panic hook ends the process. It happened at the mempool, so the transaction never had to be in a block: each node that received it stopped, and a node that was started again stopped again when a peer sent the same bytes. In a proposal it stopped every validator that judged the proposal. The sender needed an account with a key that may spend, and that account's next nonce. It needed no balance, because nothing was charged, and the nonce was never used up, so the same bytes worked again and again.

**F1 and F3 in the verifier: a gateway or a node could put a wallet's verifier out of use.** A light block, a receipt or a state proof with such a signature, such a validator key or such a header time made the proof verifier panic. In WebAssembly a panic is a trap. The JavaScript around the compiled verifier caught the trap and went on with the same instance, and an instance that had trapped about 116 times failed on every answer, honest ones too, until the page or the process was started again. A gateway, or a node behind an honest gateway, could do this to every wallet and service that asked it. Nothing false was verified: the verifier failed, it did not accept.

**The fix.**
- Two rules, one for each reader, in one file: `pos/src/untrusted.rs`. Each says for a text exactly whether its reader would panic: no more and no less. A text on which a reader only returns an error is left to the reader. `verifier-v4/src/untrusted.rs` is the same file byte for byte, because the verifier is built from its own folder; a test compares the two.
- Engine. The evidence type cannot be read from JSON without the check any more (`pos/src/evidence.rs`). A vote reaches the two readers through two of its fields, the signature and the timestamp. Evidence with such a text in one of them is an error, like any other malformed vote. The engine reads evidence through that type at the mempool, when it proposes and when it judges or executes a block, so all three refuse such evidence in the same way: before the fee, with no change to the state or to the sender's nonce. No file of the engine itself changed.
- No rule of the network changed, and no genesis setting is needed. The check refuses a text only where the program panicked before. A node that panicked did not admit the transaction, did not propose it, did not vote for a block with it and did not execute it, so no block of any network holds one. For every other text the same reader runs as before and gives what it gave. In particular the decoder takes base64 without its padding, and the date reader takes an offset: evidence written that way was accepted and still is. A stricter rule (padding required, UTC only) would have been simpler to state and would have changed what a block may hold. A node with the fix and a node without it agree on every block; the one without it can still be stopped.
- Verifier. Everything from outside comes in through one function, `parse` (`verifier-v4/src/lib.rs`). It now looks at every text in the JSON before any type reads it and refuses the whole input if one text would stop a reader. Validator records are looked at once more where they are read. Honest answers are not touched: base64, with its padding or without, and every date that can be converted are never refused. The verifier is stricter here than the engine: it refuses such a text in any place of an answer, also in a place no reader would decode. An honest answer holds none, because the hashes, numbers, names and chain ids of these networks have no `=` sign.
- JavaScript (`client-v4/proof-verifier.mjs`, which the wallet, the explorer, the servers and the SDK load). It keeps the same two rules and refuses such a text before the compiled verifier is called. `spec/untrusted-text-vectors.json` holds 547 texts with what the Rust rules say of each, and a test holds the JavaScript to them. And after any trap, whatever its cause, the instance is thrown away: the next call gets a new one, and calls that were waiting for the old one take the new one.

**What was tested.**
- The rules against the libraries themselves, by letting the library read each text where a panic is caught: every text of up to nine characters over `A`, `=` and a space, of up to thirteen over `A` and `=`, texts with characters of several bytes, a signature with every ending of up to six characters, about 40,000 dates around the edge, and 5,760 random texts of up to 95 characters in a build without debug assertions, like a released program. The base64 rule and the decoder agree on every text. The date rule names every date the reader panics on and none that it reads.
- Engine: a node is given such evidence, with each of four texts in each of the two votes. Its mempool refuses it and says why, its proposal leaves it out and keeps a payment that was offered beside it, a proposal that carries it is rejected, and the state root and the sender's nonce and balance are what they were. Evidence with the signature written without padding and the time written with an offset is then accepted and jails the validator; the network goes on and the recount passes. The engine suite has 293 tests (292 before) and passes.
- Staking crate: each of 21 values (the texts above, and other texts, numbers and empty things) in every place of the two votes: nothing panics. The vote type of the library, read alone as before, still panics on these texts; the test says so if a later version of the library stops doing that.
- Verifier: each such text in every place that holds a text of a real state proof, a real receipt, a light block and a stored trust: no panic, and a refusal that names the text. 52 tests (44 before).
- JavaScript, with the compiled verifier that is committed, which is still the build from before the fix: such a text is refused before the compiled verifier is loaded. With the rule switched off, 130 answers in a row trap the committed verifier, each costs one instance, and the honest answers between them and after them verify. The other tests of the wrapper pass unchanged.
- The same JavaScript tests with a verifier compiled on this Windows machine from the fixed source, which was not kept: the compiled verifier refuses each text itself, with the rule switched off, without a trap.
- The fuzz targets no longer leave any input alone. Each ran on its kept inputs and 300 generated ones, and the three that read text from outside on 2,000 each. The inputs of the three findings are kept as regression inputs (`fuzz/findings/`).

**Also built.** The fuzz target for parsers now also sends queries to a node (a path, a height and any bytes), as anyone who reaches a node's RPC port can. Nothing was found there.

**Not verified.**
- The compiled verifier in `web-v4/shared/verifier` is not rebuilt. Its bytes are defined by a build on Linux x86-64, which this machine cannot make. Until it is rebuilt there (`node tools/build-verifier.mjs`) and the check `verifier-build` passes on the new file, the compiled verifier still traps on these texts, and only the JavaScript around it protects a wallet. Any program that calls the compiled verifier without `client-v4/proof-verifier.mjs` is not protected. *Rebuilt on Linux on 23 November (`tc-v5-final7`) and committed in `47ac60b`; `verifier-build` passed on it in `tc-v5-final8` and `tc-v5-final9`: see "Run on AWS and in a real browser (23 November 2026)".*
- No fuzzing campaign has run. The targets ran for minutes on one Windows machine, as tests, on inputs that nothing steered. The campaign mode (`campaign/README.md`, "Fuzzing") has not run on AWS. *A campaign of a quarter of an hour ran on AWS on 23 November (`tc-v5-fuzz1`, no crash), and one of six hours was started: see "Run on AWS and in a real browser (23 November 2026)".*
- Other panics in the libraries. The readers a vote, a header, a commit and a validator record go through were read, and these two were found. Nobody has read all of the `tendermint` crates, the date library or the JSON library for this.
- A node built with debug assertions has one more panic in the base64 decoder (it stops where it wrote fewer bytes than it made room for). Released programs are built without them and return those bytes; the rule follows the released program.
- An instance that is thrown away stays in memory, because a loaded module cannot be unloaded in a browser or in Node. One megabyte and more is lost with every trap. With the rule in the JavaScript no known text reaches a trap; a new kind of trap could be used to fill a wallet's or a server's memory until it is restarted.
- Nothing ran on Linux, and no independent reviewer has read the change. *It ran on Linux on 23 November, in the repository's checks and in the fuzz campaign; no independent reviewer has read it.*

## The emergency fix path (22 November 2026)

The owner asked for the emergency path of the upgrade mechanism to be finished: what validators do when a fault in the rules must be fixed sooner than the 21 days of notice allow. `docs/emergency-fix.md` is the operator's procedure; `v5/README.md`, "The fix release and its switch", says what the engine does; `docs/design/upgrade-mechanism.md`, section 20, says what was decided where the design was silent.

**The rule that did not change.** There is no faster vote. A plan still needs four fifths of the voting power, three quarters to stay scheduled, and 21 days. A fast lane would turn the theft of signalling keys into a change of rules within hours. An emergency is a new program that operators install themselves.

**What existed.**
- The design (section 10 of the design document): validators agree on a height, stop there, and restart on a fix release that carries a one-time switch (action kind 81).
- The stop at a height (`--stop-after-height`), which ran once on a network, on 18 November.
- Kind 81 as a reserved kind: the release refuses it everywhere, and stops at a decided block that carries it.
- Nothing that executes a switch. No procedure for operators. No answer to a fault that stops every node in the middle of a block.

**What was built.**
- *The switch.* A program can carry a switch: one network, one version, one place. This release carries none. A fix release proposes exactly one block after the agreed height, which holds the switch and nothing else, and accepts no other block there. The block changes what an empty block changes, and the version.
- *What the fix release refuses.* A decided block at its switch height that is not its switch block: it stops, and executes nothing. A state that is past that height and still under the old version: it does not start on it.
- *The agreed root.* A node flag, `--expect-root`, with which a node goes on from a height only on the state the validators agreed on.
- *A stop in the middle of a block.* A node that fails on a decided block now says which block it was and which state it is left at, in words that operators can compare. A fix release can name that one block and the state before it, execute it, and end it under the new version.
- *A rehearsal build that can be a fix release,* and that has one deliberately faulty rule, so that both cases can be rehearsed on real machines. No release build has either.
- *The procedure* for three kinds of fix, with what must be ready beforehand and what must never be done.
- *A cloud rehearsal* (harness mode `v5emergency`): both cases from end to end on two networks of seven validators, each step recorded with how long it took.

**What was found on the way.**

| | Found | Now |
|---|---|---|
| E1 | **A validator started by the deployment kit cannot start again on a chain that stood.** The kit's CometBFT configuration refuses to join consensus when the validator's key signed one of the last 100 blocks. After a coordinated stop, or after a stop in the middle of a block, every validator did, and the chain makes no new blocks. Read from CometBFT's source; the kit rehearsal of 19 November had seen it for one validator of four. | Not fixed. The kit is unchanged. It is the first item of what is missing in the procedure, and it blocks kit operators from finishing either emergency. *Fixed on 23 November: the kit's resume order (`56ff823`; `deploy/README.md`, "A chain that stood"), run once on seven validators in `tc-v5-kit-7` (see "Run on AWS and in a real browser (23 November 2026)").* |
| E2 | The design's switch names no network. A release runs on more than one network, and a production fix release would have demanded a switch block at the same height of a test network. | A switch names its network. On any other it does nothing. A test runs it. |
| E3 | The design assumes that a height can be agreed before the fault stops the chain. A fault that makes a decided block fail on every node leaves no such time, and the block is final. | A fix release can name that block. See the limits below. |
| E4 | A node that failed on a decided block printed the failed check and nothing about where it stood. Operators would have compared nothing. | It prints the block's height and hash and the state's height and root, then fails as before. |
| E5 | The test harness's agent restarts a node that ends with a failure. A node that failed on a decided block would have been started again in a loop. | The agent holds such a node and keeps its last lines. A real supervisor must be told the same; the kit does not restart. |
| E6 | The fault amount of the rehearsal's faulty rule was first 81 seconds. An owner account on a network that is minutes old holds far less. | 0.081081 seconds. |

**Who can do what with it.**
- *Whoever holds stolen signalling keys:* nothing new. The switch reads no signal.
- *A third of the voting power:* halt the chain, as before. It cannot force a switch.
- *Two thirds of the voting power:* decide a switch block if they all run a program that has it. They could run other software before. What is new: nodes that did not install it stop at that block, and say why, instead of following.
- *One operator or one proposer:* cannot stop a node and cannot switch anything.
- *Whoever can get a program onto two thirds of the voting power:* everything, at once, without notice. That is the price of an emergency path, and the reason each operator verifies a fix release by hand. The project has no signed announcements yet.

**Limits that software does not remove.**
- The height, the root and the release are agreed between people. The programs check what they are told.
- The faulty rules run until the switch. Nothing is rolled back.
- A block that was decided stays decided. Wallets take a payment in a final block as paid. So a fix release that repairs a block executes every transaction in it, or none: it cannot leave a harmful one out without misleading wallets.
- Wallets and servers get no notice of an emergency switch. Software that does not know the new version stops until it is updated.

**How it was checked.**

- Engine: 18 new tests, 310 in all on the release build, passing on Windows. Through the ABCI calls, with four validators and a stand-in for consensus: the stop by half and by a quarter of the power, the agreed root, two and three of four on the fix release, the program that was not replaced, a fix release for a wrong height, a block that was decided and not executed.

- Harness: the planning code and the whole scenario against stand-in chains, agents and builder; the builder's lines run in a real shell with stand-ins for AWS and the compiler.

**Not verified.**
- **Nothing has run on real machines.** Not the switch, not the handshake that hands a stopped node its block again, not the stop in the middle of a block, not the rehearsal itself. The rehearsal's README lists what its first run must show. *All of it ran on 23 November, by the test harness, on two networks of seven laboratory validators, twice: see "Run on AWS and in a real browser (23 November 2026)".*
- **No outside review.** Every earlier change to the rules in this document was reviewed independently at least once, and each first review found a fault. This one was read by its author only.

## Service records, and a shorter threshold for the waits clock (23 November 2026)

Two changes to the engine, both settings of a network's genesis that no network has used yet. `v5/README.md` says how they are built ("Service records", "Waits that survive a stop"), and `spec/settings.md` specifies them (sections 3 and 5).

### Service records

**Why.** The project may later give a say only to validators and stake with a long, clean history ("registered six months, signed 95% of the blocks in that time, never punished, counted by stake that has itself been in place six months"), and to accounts of a certain age. The chain kept none of the facts such a rule would measure. A validator's row had no registration time, no count of blocks signed and no history of punishments. A delegation was a validator and a number of shares, with no age. An account had no creation time. The rows of each block are cleaned up after fourteen days. Records that start with a later upgrade could never know what came before it. So a network can now keep them from its first block, as data that no rule reads.

**The setting.** `service_records: true`, written last in the genesis, after `protected_accounts`. A network without it keeps its bytes, network id and state roots. The production profile requires it, and the ceremony writes it.

**What is recorded.**
- *Registration.* For each owner account, when it first registered a validator and when it last did, as a height and a chain time, and the consensus key of the last registration. For each consensus key, which owner registered it and when. The staking rules have no change of key: a new key is a new registration of the same owner, which keeps the owner's first registration, counts and punishments. Another owner account starts a record of its own and inherits nothing.
- *Blocks signed.* Per validator and per week (seven days of chain time; sixty seconds in the laboratory profile, whose other periods are short as well): blocks it was in the set to sign, blocks whose commit carries its signature, blocks it proposed, and signatures it left out of the commits of the blocks it proposed. The week in progress is one row for all validators, written once per block. When a week ends, each validator's counts join its own row, which keeps the last 53 weeks one by one, the older ones as one sum, and the sum of all. So the share signed over the last six months or the last year can always be read, long after the blocks are cleaned up.
- *Who proposed the blocks without its signature.* Per validator and week, the number of such blocks by proposer.
- *Punishments.* One row per slash, by an evidence action or by misbehavior CometBFT reported, under the owner account and the height, never removed; the owner's row counts them, and the key's row says when. Retiring and registering again, under another key, keeps them.
- *The age of stake.* For each validator's own bond (in microseconds) and each delegation (in shares of the pool), lots: one per week in which stake came in.
- *Accounts.* For each account, the block that created it: genesis, a reveal (kind 2) or a registration with a set of keys (kind 45).

**The rules for the age of stake, and why.**
- *Out from the newest lot*, when the stake is unbonded (from then on it is no longer stake, though it waits fourteen days to be withdrawn). What the old lots then hold is exactly what has been in place without a break: the lots older than N weeks never hold more than the least the position held during those N weeks. A test checks this for every N and every position of a scripted run on three networks. Stake added last week cannot count as old because older stake sits beside it. Taking the oldest first instead would make an owner lose the age of all its stake by adding a little and taking a little out.
- *Moving is out and in.* The staking rules move stake between validators only by undelegating, waiting fourteen days, withdrawing and delegating. Stake that moves, in a circle or not, arrives new. There is no operation that splits or merges positions, and none that hands a position to another account.
- *Rewards in a pool* raise the worth of every share, so they carry the age of the shares that earned them, pro rata; nobody can direct them to a lot. *Rewards bonded into a starting validator's own bond* (only on a network that pays all new time to validators without the stake hand-over rule, which the production profile cannot be) are new stake in the lot of their week.
- *A slash* takes the own bond and its lots. A slash of a pool lowers the worth of every share and leaves the lots as they are.
- *Bounded.* Whenever a position changes, the lots older than 53 weeks are merged into one, which keeps the week of the newest of them, so that it never looks older than it is. A position holds 55 lots at most.

**What it costs.** Counted in rows a block writes, on the same head with and without the setting (`tests/service_records.rs`, `what_the_records_cost_in_rows_written`):

| Block | Rows the records add |
|---|---|
| Any block | 1 (the week's tally) |
| Each payment | 0 |
| Each signature a commit leaves out | 1 |
| The first block of a week | 1 + 1 + one per validator that was in the set or proposed in the week that ended (7 in the test), and the missed row of a week that leaves the 53 kept |
| A bond, an unbond, a delegation or an undelegation | 1 |
| A validator's registration | 3 (its record, its key, its bond) |
| A punishment | 3 (the punishment, the owner's record, the key), and a fourth when a bond of its own goes |
| A new account | 1 |

The tally holds at most one entry per candidate (256), and a candidate that was in the set cannot be replaced within a week (it stays a candidate for fourteen days after it last voted), so the row stays below about 30 KB.

Measured with `time-bench-v5` on one Windows machine with 20 threads: 100,000 accounts, blocks of 10,000 payments, 20 measured blocks; the program before this change, and after it with the setting off and on (`--service-records`).

| | Before, off | After, off | After, on |
|---|---|---|---|
| Root at the last height (193) | `40655eef…` | the same | `8517e089…` |
| A block of 10,000 payments as a validator, median | 288.3 ms | 282.1 ms | 281.5 ms |
| Payments per second of the node's own work: validator, proposer | 34,685, 22,166 | 35,617, 22,924 | 35,594, 22,543 |
| A block never seen before, median | 209.0 ms | 206.1 ms | 205.7 ms |
| An empty block, mean of 134 | 12.10 ms | 12.54 ms | 13.53 ms |
| Rows of the state | 400,986 | 400,986 | 501,060 |
| Snapshot | 92.1 MB | 92.1 MB | 100.0 MB |
| Full recount | 5.77 s | 5.64 s | 5.98 s |

Runs of one program differ by two to three percent; with 10,000 payments a block the records are below that. An empty block costs about one millisecond more, in the worst case: the 134 blocks were sixty seconds apart, so on this laboratory network each opened a new week and rolled the records of all four validators. The state grows by one row per account and a few per validator. With the setting off, the program after the change reaches the same root as the one before it.

**What it does not prove: the proposer question.** A proposer chooses which signatures go into the commit its block carries. The records count exactly what the commits carry, and a missing signature cannot be told from a vote that never came. Validators that propose a share `p` of the blocks can push a rival's signed share down by up to `p`; in a test, two proposers of seven leave out more than a quarter. The records name the proposer of each block in which a signature is missing, which shows a proposer that is slow, badly connected or censors openly. **They cannot show one that hides it.** Reading CometBFT 0.38.26 (`state/validation.go`): the proposer a block's header names is only checked to be a validator of the set, "we can't actually verify it's the right proposer because we don't know what round the block was first proposed". A proposer can name any validator of the set, and so put the signatures it left out on someone else, or spread them until they look like the rival's own downtime. A test does this. Knowing who really proposed would need the round of each decided block and CometBFT's order of proposers, which the engine does not follow. So a later rule can trust `in_set` and `signed` as counts of what the chain carried, must allow for the share of blocks a hostile group proposes, and can use the named proposers to excuse misses, never to blame.

**The attacker's questions, and the answers.**
- *A group of proposers pushes a rival below a threshold.* Possible, by up to the group's share of proposals, as above. The records cannot tell this apart from the rival's own downtime if the group names other proposers.
- *Washing a punishment by retiring and registering again.* No: the punishment stays with the owner account, through any number of registrations and keys (tested). *By moving the validator to another owner account.* A validator cannot be moved. An operator can register a fresh owner account, which starts with no punishment, but also with no registration time, no blocks and no stake history, and needs a bond of its own. The chain cannot link two accounts of one operator.
- *Stake that looks old by moving it in a circle, splitting and merging positions, or through rewards.* No (tested for the circle, both with another validator and the same one; positions cannot be split or merged; rewards as above). What the records say is old is never more than what stayed in place.
- *Bloating the state with lots.* A position holds 55 lots at most, and a new lot needs an action of the owner (a fee) in a new week; positions are already bounded per owner (64) and per validator by the staking rules. The records add one row per position, of at most about 2 KB. Account rows cost a registration each, key rows a registration with a bond, punishment rows a slash. A validator that leaves the set keeps its last 53 weeks and their missed rows (at most 54 rows of at most 257 entries) until it is in the set again.
- *A stop.* Records are on the chain's time, not on the clock of the waits: a week without blocks has no counts, and stake and registrations age during a stop, as the stake stayed locked and the validator registered. The first block after a long stop ends the week in progress and rolls every record on to it.
- *A snapshot restore and state sync.* The records are rows under the state root. A node that joins by state sync has the same rows and the same recount (tested).
- *The emergency switch block.* It is counted like any block, with its proposer (tested). A block a fix release repairs is counted as it is executed.

**How it was checked.**
- Before any engine file was touched, a scripted run of 52 blocks on three networks was recorded block by block (`v5/tests/records_unchanged.rs`, `v5/tests/stake_script/`): validators register, bond, take stake out, retire and register again with a new key, delegations come and go, two starting validators are punished, blocks leave signatures out, accounts are registered, the chain stands still for fifteen days and for three hours. ### A threshold of its own for the waits clock

**The gap.** `waits_survive_stops` counted as a stop only the part of a gap beyond the hour of the upgrade rule. So every stop still shortened every wait by up to an hour, and whoever could stop and restart the chain 48 times could run out a two-day wait.

**The change.** The clock now has its own threshold: five minutes (`security::STOP_THRESHOLD_MICROS`), in both profiles. The upgrade rule keeps its hour. A two-day wait now takes 576 stops and restarts. The recount counts stops with the same threshold. No network used the setting while it had the hour, so nothing is migrated.

**The laboratory profile** uses the same five minutes. The threshold has to tell a stop from a slow block, and that depends on CometBFT's timeouts, which the laboratory networks share with production; a rehearsal of a stop then shows what a production network does. The lowest wait the laboratory profile allows (30 seconds) is below any threshold that can tell a stop from a slow block, so no laboratory value would protect it.

**What five minutes means for a network that works.**
- A chain makes a block every second or so, also with no traffic: CometBFT makes empty blocks unless `consensus.create_empty_blocks` is off, and the deployment kit sets an interval of one second. A round that fails costs seconds. A height takes five minutes only when more than a third of the voting power, or the network between the validators, is gone, and then nobody can act either.
- **What can slow the waits when nothing is wrong:** a network that turns empty blocks off, or sets `create_empty_blocks_interval` above five minutes, and has a quiet hour, counts five minutes of it. Its waits then last longer in real time than they say. The engine cannot tell such a network from one that stops. Every network the project's tools start makes empty blocks every second.
- The first block after genesis carries the genesis time. Validators that start late show it as one stop in the second block, before anything can wait.
- A clock that jumps forward by more than five minutes on most validators shows as a stop of the jump less five minutes, once; the waits then end later by that much.

**How it was checked.** The tests that pinned the hour pin five minutes (`tests/waits_survive_stops.rs`, `tests/emergency_safety.rs`). New: a gap of exactly five minutes is no stop, five minutes and a microsecond is a stop of a microsecond, and a wait with a microsecond left ends exactly when it should after gaps of five minutes, five minutes and a microsecond, and an hour; a gap of an hour is a stop of 55 minutes; a wait of three hours is over after 36 blocks five minutes apart, a week apart or an hour apart. The emergency tests count the stand before a switch block once, on the new threshold.

**Still on the hour when this was written, in folders this change did not touch.** Both points below were corrected later on 23 November: the harness's check expects a stop less five minutes and passed against a real stop of nine minutes (see "Run on AWS and in a real browser (23 November 2026)"), and the sentences say five minutes.
- The harness's check of a real stop (`campaign/lib/security-check.mjs`, `STOP_CHECK`, and `campaign/lib/genesis-settings.test.mjs`) expects the chain to count a stop less one hour. Against this engine its step "the state counts the stop beyond its first hour" fails, and the payment that waits across the stop, asked for with a delay of the stop less five minutes, comes due about an hour after the restart instead of minutes after it. It must be changed before it runs again.
- Sentences and comments that say a stop of more than an hour: `client-v4/README.md` (twice), `client-v4/time-sdk.js` and `client-v4/faucet.test.mjs` (a comment each), `deploy/api/README.md`, `deploy/faucet/README.md`, `deploy/watch/README.md`, `deploy/PRODUCTION-V5.md` (twice) and `web-v4/wallet/README.md` (twice). The clients read the total of the stops from verified state and do not compute it, so their code is right with either threshold.

## Before any launch with real value

1. Bitcoin bridge: pinned starting block (C1) and bound proof depth (C2). Not needed on a network that pays all new time to validators, which has no bitcoin bridge (see "All new time to validators, and no bitcoin auction").
2. Automatic use of the double-signing evidence that CometBFT reports (the rest of S1): built. Every validator must keep its clock by NTP: one that runs a minute or more behind refuses honest blocks, and CometBFT stops it.
3. Starting-validator power that fades against real stake, not the calendar (S2): built as the stake hand-over rule (see "Stake hand-over rule (S2)"). What it still needs is the starting validators' launch plan: on how many providers they run, when their operator stops them, and whether each holds a bond of its own from the first block: without one, what is staked with them adds no votes, and stake from outside counts against their lent power alone (see "Validators from outside", V1).
4. A decision on fees. Under the protocol-4 rule fees go to the bank and are not paid out again. One fifth of a second per second reaches circulation as validator rewards and the other four fifths only when someone buys them at the bitcoin auction, so the network can pay for about 200 transfers per second in the long run from rewards alone, and 1,000 at most, whatever the software can process. The engine now has a network setting that pays fees on to validators instead (see "Fees paid on to validators"). Still to decide: whether to turn it on and at what share, and how the amount of the fee itself is set, which is a constant today.

14. Waits that survive a stop, and accounts protected from the start: the production genesis must carry `waits_survive_stops: true` and `protected_registration: true`. The engine refuses a production genesis without either, and the ceremony writes both and protects every owner account. Neither can be added to a network afterwards. Before that genesis is made: have both rules read by an independent reviewer; keep the validators making empty blocks at least every five minutes (the threshold of the clock since 23 November), or the waits run slower than real time; run the wallet's reading of the active clock on such a network after a real stop; and rehearse the ceremony with the operators' own four keys each (see "Waits that survive a stop, and accounts protected from the start"). On 23 November both rules ran on laboratory networks of seven validators, one of them with a real stop of nine minutes, after which the API and the alert watch passed their checks of the clock; and the wallet signed up protected accounts and read the clock in Chrome, on such a network that did not stop (see "Run on AWS and in a real browser (23 November 2026)").
15. Fuzzing: a campaign of the fuzz targets for hours, and its findings fixed. On 23 November a quarter of an hour ran on Linux without a crash, and a run of six hours was started; the compiled verifier was rebuilt on Linux from the fixed source, and refuses by itself the texts it trapped on (see "Run on AWS and in a real browser (23 November 2026)"). A few minutes of writing the targets found a transaction that stopped every node (see "Found by fuzzing").
16. The emergency fix path: have the engine's part and the kit's resume order read by an independent reviewer; make a fix release that the release tool and the kit take (`docs/emergency-fix.md`, section 4); publish a key for release announcements and a private security contact; collect a contact for every validator and test it; and have the operators themselves rehearse `docs/emergency-fix.md` on a test network (see "The emergency fix path"). Its rehearsal ran on real machines on 23 November, and the measured times are in the procedure (section 12); the deployment kit got a way to start a chain that stood and the flag for the agreed root, which ran once on seven validators, on the release that had stopped (see "Run on AWS and in a real browser (23 November 2026)").
17. Service records: the production genesis must carry `service_records: true`. The engine refuses a production genesis without it and the ceremony writes it. The records cannot be added to a network afterwards: whatever happened before they began is lost for good. Before that genesis is made: have the records read by an independent reviewer, above all the rule for the age of stake, which cannot change once a network has started; run them for weeks on a network of several nodes (on 23 November they ran for minutes on laboratory networks of seven validators, whose week is sixty seconds, and each validator's recount, which checks them, gave one root; no step read them); and decide whether a later rule will need to know who really proposed each block, which the records cannot tell (see "Service records, and a shorter threshold for the waits clock").
