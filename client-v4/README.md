# V4 client and application SDK

This candidate uses a real changing CometBFT validator set, independently verified in Rust/WASM. Its genesis explicitly requires proportional reward version one; earlier reward-zero staging networks and reports remain historical and are not accepted as current authority. It remains a private Bitcoin **regtest** network. Mainnet Bitcoin receipts and public launch are disabled.

Install and serve the SDK, WASM and trust manifest through your own trusted distribution. An RPC supplies data; it cannot choose executable verifier code, initial validators or a replacement checkpoint.

```js
import { readFile } from 'node:fs/promises';
import './time-sdk.js';
import * as verifier from './proof-verifier.mjs';
// Provision this file independently of the gateway you are verifying.
const trust = JSON.parse(await readFile('./pinned-time-v4.json', 'utf8'));
const client = TimeSDK.createClient({ gateway: 'https://your-rpc.example', trust, verifier });
const { state } = await client.getVerifiedState({ names: ['alice'], include_pos: true });
const alice = state.accounts.find(a => a.name === 'alice');
```

The returned account set is a selection, never a complete account registry. `bank + liquid_total + pos_assets_total + auction_reserve_total == elapsed microseconds` checks authenticated aggregate counters. It does not independently recount every account or reexecute the entire Bitcoin, PoS or treasury state machine.

`getVerifiedState()` accepts `names`, `ids`, `public_keys` (eight each, sixteen combined), `owners`, `candidates` (sixteen each), `epochs` (eight), `blocks` (sixteen positive heights starting at one), and boolean `include_pos`, `include_bitcoin`, `include_policy`. Proofs have a 256-entry budget. Split larger selections into separate verified requests.

Trust advances using official Tendermint verification: signed validator and next-validator hashes, more than two-thirds current signatures, and more than one-third trusted voting-power overlap for a skipped header. Insufficient overlap triggers bounded bisection; it never grants authority. Announcements at H affect the actual Comet set at H+2. State version H-1 is queried explicitly and bound to the already certified header H.

Fresh account authority requires a header no older than 45 seconds, with at most ten seconds future clock drift. The seven-day trusting period is shorter than the fourteen-day unbond/slash window. An expired anchor fails before fetching a new RPC header. Obtain an independent checkpoint, verify its full block hash through a separate authenticated channel, then use `client.importTrustedCheckpoint(checkpoint, fullExpectedHash)`. A Bitcoin inclusion proof alone cannot authenticate an arbitrary Time history.

Checkpoint storage is part of the local trust boundary. Protect it against tampering, rollback and deletion; a higher local checkpoint is an authenticated local anchor, not a transcript replayed from genesis each time. Clearing browser data loses both its vault and its remembered highest checkpoint. An independently authenticated current checkpoint may then be required.

The operator equivalent is an offline command; stop the gateway before replacing its checkpoint file, then restart it:

```powershell
node production/client-v4/checkpoint-refresh.mjs --manifest pinned-v4.json --checkpoint independent-checkpoint.json --independent-hash FULL_64_HEX_HASH --output merchant-checkpoint.json
```

New registrations use paid, per-device commitments rather than a global free pending-name array. A funded sponsor signs kind44 and pays the registration fee plus ordinary transaction fee. The new device first signs `sponsorConsentBytes()` binding the network, sponsor, its public key, name commitment and expiry. A sponsor receives no spending or management authority. The new device reveals its name/salt in a later finalized block using kind2. The laboratory provides a rate-limited local sponsor; production wallets must explicitly choose a funded sponsor service or another supported funding route. The old free kind1 is rejected on V4. Selected `public_keys` proofs authenticate the corresponding `registration/commit/` row, including its absence; the SDK exposes only those proved commitments in `state.name_commits`. On a network with `protected_registration` the registration can carry the account's keys in their roles instead (kind 45, `client.registerProtected`: "Three settings a network may have for account safety" below).

Accounts use random Ed25519 device keys. Passwords encrypt the local vault with Argon2id and AES-GCM; they are never blockchain signing keys or login credentials sent to websites. Device approval or previously configured guardian recovery is required for a new key. Guardian requests allow seven days of approval coordination; quorum starts the full configured recovery delay, at least two days in the production profile. Portable encrypted backups preserve the same device key, require the existing password, prove current device membership, and never overwrite an existing vault. Revocation affects every copy of that key. P-256 passkeys are not drop-in Ed25519 signers. `external-signer.mjs` supports explicit Ed25519 byte-signing transports and verifies each returned signature; it makes no universal hardware compatibility claim.

Bitcoin receipt kind41 uses `{epoch, policy_revision, receipt:{network, block_hash, transaction_hex, vout, expected_sats, merkle_proof_hex}}`; satoshis are a decimal string and bytes are lowercase hex. `compactBitcoinReceipt()` checks the supported 240KiB transaction/4KiB Merkle-proof budget and emits the compact wire. Funding applications must check the signed Bitcoin transaction and worst-case proof/action size **before broadcasting the Bitcoin payment**. The bridge's broader parser limit is not a promise that a 1MiB transaction fits this wire. `getBitcoinBidQuote()` provides the fresh receiving script and exact TIMEBID1 OP_RETURN commitment; this candidate returns REGTEST quotes only and refuses new funding while treasury rotation is pending. Already-included old-policy Bitcoin payments can be admitted during the native one-day grace period if all cutoffs and auction deadlines still hold. Pending transactions mined after the old Bitcoin-height cutoff remain ineligible. Cross-chain timing is not atomic; no infallible credit or refund is promised.

Website integration uses `TimeSDK.requestWallet({walletOrigin, request})`: `login` signs a short-lived exact-origin challenge; `payment` requires separate approval of account, recipient, amount and exact nonce-bound reference. The merchant backend must independently verify current account/device authority and finalized payment evidence. `server-auth.mjs` implements challenge consumption, CSRF, recovery freezes, and exact-order settlement. `order-store.mjs` stores orders in indexed SQLite with WAL/FULL durability and a unique settlement hash. Login sessions intentionally require reauthentication after a backend restart.

`createV4Servers()` binds only literal loopback and accepts only loopback peer connections. By default it uses local HTTP origins. To place the candidate behind a separately provisioned local TLS proxy, explicitly pass `publicOrigins: {wallet: 'https://wallet.example', merchant: 'https://app.example'}`. Origins must be canonical, distinct HTTPS origins; the app checks their exact Host and Origin and emits Secure, HttpOnly, SameSite cookies. `walletListenOrigin` / `merchantListenOrigin` report the private HTTP upstreams; `walletOrigin` / `merchantOrigin` report the public logical origins. It never trusts X-Forwarded headers for a decision and never enables wildcard CORS; with `trustedProxies: ['127.0.0.1']` (the address of your own reverse proxy on this machine, which must set `X-Forwarded-For` to the address it was reached from) it reads the right-most address of that header for its limits only, to count each caller's requests apart ("Limits" below). See [the Nginx example](nginx.example.conf). Certificate provisioning, DNS and external deployment are separate operator actions; none are performed by the tests. The actual private-CA TLS test verifies state proofs, login cookies, hostname/origin rejection and failure with an untrusted CA, using per-request CA configuration without changing global TLS validation. It requires durable checkpoint and order paths. Orders use `ordersPath + '.sqlite'`. A nonempty old JSON order file is rejected pending an explicit migration; it is never discarded silently. Independent production operators, certificate operations, RPC/witness endpoints, storage backups, supervision and monitored deployment remain operational requirements. The transport adapter does not turn a same-machine regtest network into a public-funds network.

**Limits** (`GATEWAY_LIMITS` in `server.mjs`). Each origin takes 50 requests a second that ask the node or a store (every `/api/` route and every POST) and 1000 of its page's files. Without `trustedProxies` that is for everybody together: every request comes from 127.0.0.1 and nothing tells two callers apart, so the reverse proxy in front must hold each caller well below it. With `trustedProxies`, each caller (an IPv4 address or an IPv6 /64) has 15 a second with a burst of 300, a /48 30 with a burst of 600, and everybody together 1000 a second of work and 4000 of files, out of reach of any one caller's burst. Those rates leave room for a household or an office behind one address; what keeps one caller from crowding out the others is the line of checks. The light client checks one step at a time for both origins, and every step of a request, with the verifier's own checks, waits in a fair line (`callers.mjs`, `createFairLine`): the caller (and the /48) with fewest checks under way goes first; one caller may hold half the line, one /48 three quarters; when the line (256) is full, the caller that asks most is refused, not the one that comes next; a place waited for over 8 seconds is refused. Without `trustedProxies` the line is first come, first served. A refusal that may be asked again is `429` (`RATE_LIMITED`, too many from this caller) or `503` (`GATEWAY_BUSY`, too many from everybody), with `Retry-After` in whole seconds from 1 to 30 and the body `{"error":"<fixed sentence>","code":"RATE_LIMITED"|"GATEWAY_BUSY","retryAfterSeconds":<the same number>}`: `{"error":"Local request limit reached","code":"RATE_LIMITED","retryAfterSeconds":1}` and `{"error":"The gateway is checking many requests just now. Try again in a few seconds.","code":"GATEWAY_BUSY","retryAfterSeconds":2}`. `verificationLine()` says what the line has seen. The gateway can verify about 68 reads a second with eight at once on a laptop's i9-12900H (16 ms one at a time), which makes about 15 a second for the gateway on the test network's t3.medium beside the other services. The pages are served with a `Permissions-Policy` that turns off what they do not use (the wallet's own origin may use WebAuthn), and the wallet's with `Cross-Origin-Opener-Policy: same-origin`, except `/approve`, the window a website opens and talks to. Only the files of each page's folder (no test, no other spelling of a name) and the four SDK modules are served.

Public receipt evidence is archived durably and rebound to fresh canonical history before reuse. The current JMT root authenticates a network/size-bound RFC6962 history frontier; bounded inclusion paths authenticate the old H and H+1 header hashes and absolute timestamps. Recent raw history rows may be pruned without weakening that proof. The separate append archive still grows with chain history and needs storage operations and backups. An archive file does not grant its own trust, and retained evidence must be reanchored with a currently trusted light client. Live stake exits use authenticated retained release clocks, so pruning an old history archive cannot make a mature exit depend on an archive provider. Self exits still wait for actual removal plus fourteen days. Archived inactive candidates retain existing claims but cannot accept new delegation or self bond.

The security inbox records recovery and authority changes when an account is queried. It provides durable observations, not delivery guarantees while every watcher is offline. No email, SMS or push provider is contacted.

Run the client checks from `production`:

```powershell
node --test client-v4/*.test.mjs web-v4/wallet/wallet.test.mjs web-v4/wallet/backup.test.mjs
$env:RUSTUP_TOOLCHAIN='1.99.1'; $env:CARGO_BUILD_JOBS='1'
.\tools\cargo.ps1 test --manifest-path verifier-v4/Cargo.toml --lib
```

The dynamic verifier fixtures contain real deterministic test-only Ed25519 quorum signatures, changed committees, JMT membership/absence and historical receipt evidence. They contain no wallet or validator private keys. They are adversarial regression tests, not a mathematical proof that no implementation bug exists.

## Account security on the version-5 engine

`account-security.mjs` is the wallet's side of the engine rules that give each key of an account one role: sign-in, spend or recovery. It builds the payloads of kinds 70 to 77 in their one accepted form and the bytes a key signs to accept a role or to approve a root operation, and it reads a security row (the remaining daily allowance, frozen or not). It holds no key and talks to no network. The rules and the reasons for them are in `../AUDIT-2026-11.md`; the formats are in `../v5/README.md`.

To read the row, pass `include_security: true` in a state selection. The verified state then carries `security`, a list with one entry for each selected account that has adopted the rules. The verifier demands a proof of each row or of its absence, so a gateway cannot hide one. The protocol-4 node refuses the flag.

Login rule for websites (`signInRefusal`, applied by `createLoginService`): an account that has adopted the rules signs in with a sign-in key only, and not while it is frozen. An account with a key that holds both powers cannot have adopted the rules; it signs in as before, with one state read. Any other account is read a second time with `include_security`, and the login is refused if that proof is not available.

## Alerts for wallets

A notification carries no information; the chain does. Three parts, none of which adds anything to the chain's rules:

- `touches.mjs` says, from an action's bytes alone, which accounts it touches (sender, payee, an account a guardian names, a validator's owner) and which it may wake: the account whose keys or security rules it changes or on which it starts a wait. A payment wakes nobody.
- The API sends a wallet whose page is open a hint, `GET /v1/touches?account=N`: "this account was touched at height H", not proven, with nothing else in it (`../deploy/api/README.md`, "Hints for wallets"). Nothing is kept or sent again.
- `alert-push.mjs` (the process: `../deploy/alerts/`) wakes a closed wallet with a browser push whose content is the constant `{"v":1}`, after it verified the block. It keeps the address list and its VAPID key, and checks who subscribes with the login proof above (`verifyLogin`).

The wallet works out what to say from one verified state of its account (`../web-v4/wallet/alerts.mjs`); its service worker (`sw.js`) shows only "Open your wallet to check your account.".

## Three settings a network may have for account safety

A network's genesis may carry `distinct_names`, `waits_survive_stops` and `protected_registration` (`../spec/settings.md`; the production profile requires all three). Each comes with every verified state, in the metadata row, and is read from there, never from a gateway: `TimeSDK.distinctNames(state)`, `TimeSDK.waitsSurviveStops(state)`, `TimeSDK.protectedRegistration(state)`. On a network without a setting nothing below changes, here or in code built on this SDK.

### Names that look alike (`distinct_names`)

The network refuses a new name whose skeleton (`TimeSDK.nameSkeleton`) is that of a name that exists: `paypa1` beside `paypal`, `al_ice` beside `alice`. The reveal (kind 2) and the registration that carries a set of keys (kind 45) are refused alike, after the sponsor has paid: a proven read of the skeleton row is not available to wallets yet (`../v5/README.md`, "Names that look alike").

- **A wallet:** the refusal names the existing name ("the name paypa1 is too close to the existing name paypal"). It comes through a gateway: take the name in it only as where to look, compute both skeletons yourself, and read that name from proven state before you say so to the person (the wallet does: `web-v4/wallet/app.js`, `nameRefusal`). Softer look-alikes (`b1nance` beside `binance`) are registered: warn about them yourself.
- **A shop or an exchange:** credit by account number and by the payer's number, as before. A name alone never decides whom a payment is from.

### Waits that survive a stop (`waits_survive_stops`)

The moments a security row stores are then moments on the clock of the waits, the chain's time less the total of its stops (`state.stopped_micros`): `ready_elapsed_micros` of a waiting payment, of a raise of the limit and of a replacement, `expires_elapsed_micros` of a waiting replacement, `frozen_until_elapsed_micros` and `allowance_elapsed_micros`. After a stop of more than five minutes, read on the chain's time, a freeze looks over and a payment ready while the chain holds the opposite.

- Compare every such moment with `TimeSDK.securityNow(state)`, and pass that as `nowElapsedMicros` to `account-security.mjs` (`allowance`, `frozen`, `signInRefusal`). Never with `state.time_micros` less the genesis time.
- Show one as a date with `TimeSDK.securityDeadline(state, moment)`: while `earliest` is true the date is the earliest the moment can come, and a later stop moves it. Say "not before".
- What a key signs stays on the chain's time on every network: the expiry of a freeze, of the approvals of a root operation, of a sponsor's consent, of a payment reference.
- Over HTTP, `GET /v1/accounts/{number}/state` gives the same clock with the row: `security_clock` (`../deploy/api/README.md`).
- In this repository the login service (`server-auth.mjs`), the SDK's count of upgrade signals, the alert watch (`security-watch.mjs`: dates "at the earliest", events with `earliest: true`), the faucet (`faucet.mjs`), the API, the explorer and the wallet (`web-v4/wallet`, README "The clock of the waits") read this clock.
- The status of upgrade signals carries what dates the end of an owner's freeze: `waits`, `{rule, stoppedMicros}` of the state it was read from (`signalStatusOf`, `getSignalStatus`).

### Accounts protected from their first block (`protected_registration`)

A registration can then carry the account's keys in their roles and its policy: kind 45, `TimeSDK.KINDS.register_protected`. Like a reveal it has no sender, uses a commitment a sponsor paid for (kind 44) and pays nothing. The API and the explorer name it; its bytes do not carry the new account's number, so read that from a state proof by name.

**Signing up protected.** `client.registerProtected({sponsor, name, salt, registration, keys, dailyLimitMicros, delaySeconds, freezeSeconds, threshold, waitMs})` (`time-sdk.js`, where the comment above the function is its full description) does the whole sign-up and returns `{account, security, receipt, sponsorReceipt}` once a verified state shows the account with exactly these keys and this policy.

- `sponsor` is `{account, ask(body)}`: the wallet's `registrationSponsor()` gives it, for the gateway's own sponsor and for a registration service such as a test network's faucet. Leave it out when the chain holds the account or this key's commitment already: no sponsor is asked then. Left out when the chain holds neither, the call throws code `SPONSOR_REQUIRED` before anything is signed; call again with one. `registration` is the new registration key `{publicKey, privateKey}`, which becomes the account's identity key. `keys` is `{signin, spend, recover}`, each a list of `{publicKey, privateKey}` (the acceptance is signed there) or `{publicKey, proof}` (signed elsewhere, `acceptRegistrationRole`). `threshold` is `'2'` unless given.
- The steps: check the setting in a verified state (otherwise error code `PROTECTED_REGISTRATION_UNAVAILABLE`, before anything is sent: register with the reveal); sign every acceptance and check each; compute the commitment of the name, the salt and the set (`protectedNameCommitment`); sign the sponsor's consent to that commitment; ask the sponsor; wait for the verified receipt of its action and check that it pays for exactly this key, this commitment and this expiry (`SPONSOR_MISMATCH` otherwise); wait for the commitment in a verified state (`COMMITMENT_MISMATCH` for another one) and for a later block; sign and submit the registration; read the account and its security row back, by proof.
- **When a consent can no longer make an account.** The registration key's consent to a sponsor is dated `TimeSDK.sponsorConsentExpiry(state)` on the chain's time: five minutes ahead of the state the SDK read, or the network's longest lifetime of a registration less twenty seconds if that is shorter, and never less than a minute (`SPONSOR_CONSENT_MAX_AHEAD_MICROS` is the most, five minutes). The chain takes a sponsor's action only before that moment, and the commitment it makes lasts until then. `onConsent({expiresElapsedMicros, publicKey, commitment})`, optional, is awaited before the consent is signed and any sponsor asked, so that a wallet can keep the moment first; if it throws, nothing is signed or sent. Once the chain's time has passed the latest such moment and a verified state shows neither the account nor a commitment of the key, nothing of that sign-up can reach the chain without the registration key signing again (`web-v4/wallet`, README "Letting a kept sign-up go").
- **What the sponsor sees:** the registration key's public key, the commitment, its expiry and the consent. Never a private key, the name, the salt or a key of the set: the commitment hides them until the registration.
- **Why it cannot put its own keys on the account:** the chain takes the sponsor's action only with the registration key's consent to that very commitment; the commitment is a hash of the whole set, the name and the salt; the chain creates the account only from a registration that matches it, signed by the registration key. A sponsor that pays for another commitment is refused by the chain; one that names another action is refused here, before the registration is signed. `protected-signup.test.mjs` plays a dishonest service that tries each way, and the account ends with the newcomer's keys or is not made.
- **Called again** after an interruption, it goes on from what the chain shows: a commitment there is not paid for twice, and the registration is the same bytes.
- **The registration service** changes nothing: it pays for a commitment it cannot read, of either kind of registration. The newcomer pays nothing.
- On a network without the setting, register with the reveal (kind 2), as before.

## Large payments: confirm with your own node

The light client accepts what validators holding more than two thirds of the voting power signed. It checks their signatures and the Merkle proofs; it does not run the transactions. Validators above two thirds who agreed to cheat could therefore sign a block with a payment the rules refuse (money the payer never had, for example), and the light client would accept its receipt. A full node runs every block itself, so it refuses such a block and stops: the time-node-v5 application stops at the first block it cannot execute. Before shipping goods for a large payment, also ask a full node you run yourself.

**Running the node.** A CometBFT full node with the time-node-v5 application (see `../v5/README.md`) that is not a validator (it signs nothing), started from the network's `genesis.json` obtained independently, like the trust manifest, with peers you trust. In its `config.toml`:

- `[tx_index] indexer = "kv"` (recommended; validators run with `"null"`): the node finds a transaction by its hash. Without an index the check reads the block instead.
- `[storage] discard_abci_responses = false` (the default): the node keeps the results of each block, which the check reads when the index cannot answer.
- `[statesync] enable = false` (the default): sync from genesis. A node started from a state-sync snapshot takes the state at the snapshot on the validators' word and runs only the blocks after it.
- `[rpc] laddr = "tcp://127.0.0.1:26757"`: RPC on a loopback port of the shop's machine (a second node there needs its own ports). Reach a node on another machine through an authenticated tunnel; never expose its RPC publicly.

**Settings.** Pass `ownNode` to `createOrderService` or `createV4Servers`; for the deployed gateway, `own_node` in its settings file (`../deploy/gateway/README.md`).

```js
ownNode: { url: 'http://127.0.0.1:26757/', chainId: 'time-devnet-v4-…', aboveMicros: '1000000000', timeoutMs: 5000 }
```

- `url`: the node's RPC address. Or instead `rpc`: a function `(method, parameters) => result` like the gateway's, answering `/status`, `/tx`, `/block` and `/block_results`. Either way it must reach your node directly, never through the gateway: the light client checks what the gateway serves, and this check must not depend on it. `createV4Servers` refuses its own `rpc` function here, but that is only a sanity check: it compares the function itself and cannot recognize a function that wraps the gateway.
- `chainId`: the network the node must report. Required with `createOrderService`; `createV4Servers` sets it from the pinned manifest.
- `aboveMicros`: orders of this amount or more need the node (default `'0'`: every order). Smaller orders settle on the light client alone, as before. The threshold applies to each order by itself: many orders below it, however much they add up to, all rest on the two-thirds assumption alone.
- `timeoutMs`: the longest one check may take (default 5000, from 100 to 60000).
- `retryAfterMs`: after the node could not confirm a payment, the same order and payment are refused at once for this long, without a new light-client proof (default 2000, from 0 to 60000).

Without `ownNode` the checks are the same as before.

**What is checked.** For an order that needs it, `fulfill` verifies the light-client receipt as before, then asks the node:

- `/status`: the node is on the network of the trust manifest and above the payment's block H. It has then accepted block H+1, whose header commits to the results of block H; it accepts that header only when those are the results of its own execution.
- `/tx?hash=0x…`, or when the index cannot answer, `/block?height=H` and `/block_results?height=H`: the same transaction bytes and hash, at height H, with result code 0.

The settled order records the checks: `confirmedBy: ['light-client', 'own-node']`, or `['light-client']` below the threshold or without `ownNode`. Orders settled by earlier versions have no `confirmedBy`.

**When the node is behind, down or disagrees**, `fulfill` throws and the order stays unsettled: call `fulfill` again later with the same hash. An order that needs the node never settles on the light client alone. The error's `code` tells the cases apart:

- `OWN_NODE_UNAVAILABLE`: the node did not answer within `timeoutMs`, cannot be reached, is behind (still syncing, or stopped at a block it refused) or no longer keeps the block. Retry later; read the node's log if it lasts.
- `OWN_NODE_MISMATCH`: the node answered and contradicts the receipt: another height, other bytes, a result code other than 0, a block without the payment, another network. Do not ship; find out why. This is what an attack by a validator majority looks like. The order service reports it through `onAlert` (by default a JSON line on the error log, with the order, the payment hash, the node's address and the reason) and keeps it on the order in `ownNodeMismatches`, which a later settlement keeps too.

Over HTTP the refusal is a 400 answer with `error`, the fixed first half of the refusal ("Own node has not confirmed the payment; the order stays unsettled, retry later" or "Own node contradicts the light-client receipt; the order stays unsettled"), and this `code`; the reason, which can name the node and quote it, goes to the gateway's error log (`onRefusal`). No answer of the gateway carries a file path, an address of the machine or of a node, or a node's words, except the node's reason for refusing a submitted action (`/api/submit`), which the wallet reads and shows as its gateway's words. The demo blog page (`web-v4/merchant`, the sample shop page before it; "The demo blog on the second origin" below) asks again every five seconds for five minutes after any refusal or failure (the node, the light client, the shop's rate limit, the network), tells the buyer not to pay again, and keeps each paid order and its transaction in a list in the browser (with the paying account; the 20 newest, for 7 days), so that reopening the page, or signing in again as that account, finishes the settlement. Signing in as another account meanwhile stops the requests and keeps the payment. Only answers that mean the payment is wrong for the order (`OWN_NODE_MISMATCH`, a payment that does not match the order, a transaction used elsewhere) are not asked again; the order is then dropped from the list.

Payments are checked outside the shop's order queue: issuing other orders does not wait for a slow node. Requests for the same order and payment share one check, at most 32 checks run at once and later ones wait their turn; only storing the result is queued, after the order is read again.

**Still assumed.** Your node's software and machine: it applies the rules as the time-node-v5 code implements them, bugs included. Its genesis file. That validators above one third do not sign two conflicting chains while your node is cut off from honest peers: a full node tells a valid block from an invalid one, not which of two valid conflicting chains the rest of the network follows. For orders below `aboveMicros`, the two-thirds assumption alone. Whoever stops your node or the network delays large settlements; they cannot force one.

## The demo blog on the second origin

`createV4Servers` serves on its second origin (`merchant` in the code) a demo blog, `web-v4/merchant`: a person reads the posts, signs in with the wallet, writes short posts, deletes their own, and can support the blog with 0.1 seconds through the order routes above (`/api/order`, `/api/order/settle`, unchanged). The page is also the example of adding "Sign in with Time" to a website.

- `GET /api/posts`, public, newest first, 50 at a time (`?before=ID` for older ones): `{posts: [{id, accountId, name, text, createdAt, supporter}], more, limits: {maxChars, perAccount, hours, keep}}`.
- `POST /api/posts` `{text}` and `POST /api/posts/delete` `{id}`: with the session cookie, the `X-CSRF-Token` of `/api/session` and the website's own `Origin`, checked as for `/api/order`. The author is the session's account with the name the chain gives it; the time is the server's. Without a session `401`; a refused text `400`; the 21st post of an account in 24 hours, or the 61st of everyone together in an hour, `429`; another account's post `403`; a post that is not there `404`. A body with any other field is refused. `POST /api/logout` deletes the session as it is kept, without reading the chain.
- A post is plain text: trimmed, 1 to 500 characters (Unicode code points), line breaks allowed; every other control character, and the characters that change the direction of text, are refused, and so are a letter with more than 4 combining marks and more than 16 characters that take no room (zero width spaces and joiners; a joiner inside an emoji is not counted). The page puts it on screen with `textContent` only, and a post cannot paint outside its own box.
- Orders: an account has at most 3 orders waiting for their payment at once (`429` beyond); asking again for the same item while its open order still reserves the account's next nonce, with a minute left, gives that order back. An order nobody paid is deleted a day after it expired; a payment made in time settles it until then.
- Sign-in challenges are kept by nobody: each travels in its prelogin cookie with a MAC under a key made at start, and a nonce is remembered only while a proof for it is checked and, after a sign-in with it, until it expires. A restart makes the sign-ins under way start again.
- `supporter`, on each post and on `/api/session`: the account has an order that this server settled, and `fulfill` settles one only after it verified the payment (`order-store.mjs`, `paidBy`).
- Storage: `blog-store.mjs`, SQLite at `ORDERS_PATH.blog.sqlite` beside the orders, WAL with full sync, one transaction per publish or delete; a crash loses at most the request being written. A post stays a week whatever comes after it; after that, the newest 500 are kept. When everyone together has published 60 in the last hour, a post is refused: nobody's post is deleted to make room. The 20 posts of an account in 24 hours are counted from a record of publishes that deleting a post does not shorten. The file belongs to one network id, like the orders database.

## When the network changes its rules

A network changes its rules by a new protocol version, which its validators schedule on the chain at least 21 days ahead (`../docs/design/upgrade-mechanism.md`). What that means for code built on this SDK:

- **Two numbers are written "4".** The first version of a network is in its genesis and trust manifest (`trust.app_version`) and in the gateway's `/api/network` (`protocolVersion`). It never changes: a trust manifest is not reissued for an upgrade. The version in force is `state.protocol_version` of a verified state. The verifier checks it against the header the validators certified, so no gateway can report another one. Decide by the second, never by the first.
- **A coming upgrade** is read from proven state. Pass `include_upgrade: true` in a selection: the verified state then carries `upgrade`, which is `null` when the row `upgrade/state` is proven absent and otherwise the row (`plan`, present while a plan is scheduled, and the validators' `signals`). `client.getUpgradeStatus()` returns `{version, scheduled, known}`: the version in force, the plan or `null`, and whether this build implements the scheduled version (`true` when nothing is scheduled). A proof that leaves the entry out is refused. It is never read as "no plan"; show "could not check" instead.
- **`UPGRADE_REQUIRED:`** begins the message of the error that the verifier and the SDK raise for a version they do not implement: this build implements versions 4 to 4. The light client's checkpoint keeps advancing across such an upgrade; states and receipts of the new version are not read. Order issuance and logins (`server-auth.mjs`) fail with the same message, passed on unchanged. The remedy is a newer release of this software, nothing else.
- **Test the code, never the words.** That error carries `code` `'UPGRADE_REQUIRED'`, which is set in exactly two places: `proof-verifier.mjs`, on a refusal the compiled verifier itself threw, and the SDK's own version check (`requireKnownVersion`). `TimeSDK.isUpgradeRequired(error)` tests it. An error that repeats what a gateway said never has the code, whatever JSON value the gateway sent (a string, an array, an object): it is one string, marked `gateway: true`, and prefixed "The gateway reports: " when it names `UPGRADE_REQUIRED`. Show "update this app" or raise an alert for the code only, and put none of an error's text on such a screen: the wallet shows its own words (`web-v4/wallet/actions.mjs`, `upgradeRequiredScreen`).
- **Whether the nodes answer that question is part of the network's pinned trust data.** A trust object with `nodes_report_upgrades: true` says that the network's nodes answer `include_upgrade` (time-node-v5 0.7.0 and later).
  - *Where it lives.* In the trust object itself, beside `chain_id` and `app_version`. That object is the one thing every client already installs from a source independent of the gateway: the wallet's `/trust-manifest.json`, `manifest.trust` of `createV4Servers`, and `trust` in the alert watch's settings. A field beside it in the network manifest would reach none of them without a second thing to pin. `tools/genesis-v5.mjs` writes it for a production network, and the manifest a participant checks carries it.
  - *Who reads it.* A client made from such a trust object (`createClient`) adds `include_upgrade` to every verified read from the first one, whatever the selection says, and has `client.nodesReportUpgrades === true`. `createV4Servers` does the same for every state it verifies for a login or an order. The wallet and the alert watch take it from the same object.
  - *What it gives.* A gateway cannot single the question out. A read that it holds, refuses or answers without the entry fails as a whole, and there is no read without the question to fall back to. Nothing is learned from a gateway, and no code decides anything by the text of a gateway's error.
  - *Its form.* `true`, `false` or absent; anything else is refused (`TimeSDK.nodesReportUpgrades(trust)`). The compiled verifier does not read the field: it only makes a client ask for more. A `true` on a network whose nodes cannot answer fails every read, it does not hide a plan.
- **A network that does not say so** (a trust object from before the field, a laboratory network on older nodes) leaves the question to the caller. `getUpgradeStatus({timeoutMs})` fails after `timeoutMs` (20 s unless set) with an error marked `timeout: true`, and `getVerifiedState(selection, {timeoutMs})` takes the same limit. Once a node of the network has answered with the entry, a client that a person looks at can ask for it in every read (`include_upgrade: true` in the regular selection), as the wallet does on such a network: a held question then stops the wallet instead of hiding a plan. A service that must not be stopped or delayed by the question asks it apart and reports when it goes unanswered, as the alert watch does. Until then show a failed question as "could not check" for as long as it lasts, in the same words whatever the gateway said: a gateway can choose its words to look like an older node. The test-network builder (`../campaign/lib/genesis.mjs`) does not write the field: a test network on 0.7.0 nodes needs `nodes_report_upgrades: true` in its `manifest.trust` to get the stronger behaviour.
- **`known`** means this build implements the scheduled version under exactly the scheduled specification (`TimeSDK.IMPLEMENTED` lists each version with its specification hash; `TimeSDK.knowsPlan(plan)`).
- **Servers get the same notice as wallets.** `createV4Servers` reads the proven plan a minute after start and every ten minutes (`upgradeCheck: {firstMs, everyMs}`), and while a version it does not implement is scheduled it writes a JSON line `UPGRADE_SCHEDULED_NOT_IMPLEMENTED` with the version and the start time (`onUpgradeNotice` replaces the log). `servers.checkUpgrade()` asks at once. On a network that does not declare that its nodes report upgrades, a node that predates the question is reported once as `UPGRADE_STATUS_UNAVAILABLE` and everything else works as before. On a network that declares it, the server verifies no state against such a node. `createV4Servers` returns `nodesReportUpgrades`, and the gateway's start line (`deploy/gateway/start.mjs`) prints it as `nodes_report_upgrades`, with a warning line `UPGRADE_REPORTS_NOT_DECLARED` when the pinned manifest does not say so.
- **The alert watch** (`../deploy/watch/README.md`) sends `upgrade_scheduled`, `upgrade_cancelled`, `watch_outdated` and `watch_ready`, and on a network that does not declare it, `upgrade_question_unanswered` and `upgrade_question_answered` when a question that was answered before no longer is, and is again. On such a network it asks the question apart from its account checks.
- **A receipt asked for across an activation.** A gateway checks every receipt with its own verifier before it serves it. A gateway that does not implement the new version refuses there and answers with the verifier's sentence, which to this SDK is a gateway's words: no code. So when a receipt request fails, or `waitReceipt` runs out, the SDK looks for itself: one verified read of the current state, given 10 seconds at most (`ownCheckMs`, 1 to 60 seconds). If its own verifier refuses that state, `waitReceipt` and `exportReceiptEvidence` throw that refusal, with `code` `'UPGRADE_REQUIRED'` and the `hash` of the transaction whose outcome this software can no longer learn. In every other case they throw the first error unchanged. Nothing a gateway says decides which, and the code is still set in the same two places (`upgrade-receipt.test.mjs`). Keep the signed bytes: a release that implements the version reads the receipt.

## A validator's upgrade signal (action kind 80)

The owner account of a validator supports a plan for a change of the rules, or withdraws its support, with one action (`../docs/design/upgrade-mechanism.md`, sections 3.1 and 5; the rules are `../v5/src/upgrade.rs` and `../spec/protocol-4.md`, section 6). The SDK builds, signs and reads that action, and reads from proven state what an owner needs to see before sending one. The wallet's Validator signal tab is built on it (`../web-v4/wallet/README.md`).

- **The action.** `TimeSDK.KINDS.upgrade_signal` is 80. Its payload is one of exactly two byte strings.
  - `TimeSDK.signalSupport({version, spec, activateElapsedMicros})` gives `{"activate_elapsed_micros":"D","spec":"H","version":"D"}`: support this plan. `D` is a decimal string without leading zeros, `H` is 64 lowercase hexadecimal characters.
  - `TimeSDK.signalWithdrawal()` gives `{}`: withdraw.
  - `buildAction`, `signAction` and `decodeAction` refuse every other form before anything is signed: another key, a number that is not a decimal string, a leading zero, a hash in capital letters. The SDK writes the bytes itself and does not leave them to a JSON encoder.
  - `upgrade-signal.test.mjs` compares the bytes, signature included, with two signals the engine wrote and accepted (`../v5/tests/fixtures/upgrade-state.fixture.json`).
  - Kind 81 is reserved for an emergency release. The SDK neither builds nor reads it.
- **Which key signs.** A key of the owner account that may spend (`can_spend`): the one key of an account that has not adopted the account security rules, or a spend key of one that has. A sign-in key and a recovery key cannot signal. The action takes the account's next nonce and costs the network fee. For a secured account the fee counts against the daily limit, and a frozen account cannot send it. `client.perform({kind: 'upgrade_signal', ...})` and `client.submit(tx)` take it like any other action.
- **The status.** `client.getSignalStatus(accountId)` returns, from proofs this client verified:
  - the version in force, the scheduled plan, and whether a validator safety hold is on;
  - the validator set in force and each announced set, and every validator with its voting power and its signal;
  - each plan that a validator of those sets names, with its supporters and its tally: the supporting power and the total in every set, the lowest share, and whether that share reaches four fifths (`schedule`) and three quarters (`keep`). The comparison is the engine's, in whole numbers;
  - for the account: whether it owns a validator candidate that is not archived, its entry, when it may change its signal again, why its signal does not count now (`stopped`: `'frozen'` or `'recovery'`), its balance, and the keys that may sign.
  - `TimeSDK.signalStatusOf(state, {account})` computes the same from one verified state that was read with `ids` and `candidates` for the account and `include_pos`, `include_upgrade` and `include_security`.
- **What one proof cannot hold.** Whether another validator's signal counts depends on its owner account (frozen, or in a recovery) and, during a safety hold, on which validators are jailed. One proof holds eight accounts and sixteen candidates.
  - `getSignalStatus` reads the rest in further proofs, each verified, a few blocks after the first. `heights` names the first and the last block. The validator sets and the signals are always those of the first.
  - A further read that fails, more than `maxReads` of them (16 unless set), or `timeoutMs` (30 seconds unless set) leaves facts out. The status then has `complete: false`, and a tally that depends on a missing fact has `exact: false`. Its sums are then a count the network may not share, in either direction. An unread supporter is counted, so the share can be higher than the network's. During a safety hold an unread jailed validator that does not support the plan stays in the total, so the share can be lower. `schedule` and `keep` are then `null`: neither is known. Say neither as fact.
  - Without a hold the SDK takes no validator of those sets to be jailed. That is the staking rule's own statement (`pos::Summary::safety_hold`), not something each read proves again.
- **Before signing.** `TimeSDK.judgeSignal(status, intent)` applies the engine's checks to a status, in the engine's order. `intent` is `{version, spec, activateElapsedMicros}` or `{withdraw: true}`. It returns the payload to sign, or the rule that refuses it:
  - `not_owner`, `recovery`, `frozen`, `fee`: the account cannot send it now;
  - `version`: a plan names the version after the one in force;
  - `start_too_soon`, `start_too_far`: a new plan starts from the notice (21 days, and the 30 seconds a node adds at admission) to the farthest start (120 days), counted from the proven block. Only the scheduled plan may be nearer;
  - `no_change`, `interval`, `table_full`: it must change the entry, at most once per interval (10 minutes), and the row holds 256 entries.
- **What cannot be judged from proven state.**
  - A node admits a signal of support only for a version and specification hash its own program implements. That is the node's policy, not a rule, and no proof shows it: the node's refusal arrives as a gateway's words. A release-1 node admits no signal of support at all. Send through a node that runs the release.
  - A secured account's daily limit must cover the fee (`account-security.mjs`, `allowance`).
- **What the SDK does not know: which plan is the right one.** The version, the hash and the start time come from the release announcement. Do not take them from a gateway, and do not fill them in from what other validators signalled: any owner of a validator can signal any plan.
- **Not verified.** No signal built by the SDK has been sent to a live network. The upgrade rehearsal on a real network sent its signals from the test harness, whose bytes a harness test compares with the SDK's.
