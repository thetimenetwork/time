# Protocol 4 operator software

This is a **private devnet candidate**. Public monetary operation and mainnet receipt acceptance remain disabled in Rust genesis validation and in this bundle. There is no monetary enable switch. A package, a test suite, twenty keys, or twelve Bitcoin confirmations cannot establish independent operators or guarantee security.

## Release and Linux build

Use Node 26+, Docker with a Linux daemon, and 20 GiB free disk. `tools/release-v4.mjs` creates a NEW directory containing an exact source allowlist and a deny-by-default Docker context. It never adds `.local`, `.tools`, targets, wallets, cookies, runtime databases or enrollment keys. Added symlinks, traversal paths, secret filenames and private PEM material are rejected. Keep runtime directories outside the release context. The manifest binds every source, image digest, supplied Linux binary and selected evidence report; the SPDX inventory describes locked dependencies, not completed license/vulnerability review.

```sh
node tools/release-v4.mjs --out releases/candidate-001 \
  --rust-image rust@sha256:VERIFIED_64_HEX_DIGEST \
  --go-image golang@sha256:VERIFIED_64_HEX_DIGEST \
  --runtime-image node@sha256:VERIFIED_64_HEX_DIGEST
node releases/candidate-001/context/deploy/build.mjs build releases/candidate-001 time-v4:candidate-001
```

Rust image must contain 1.99.1, Go image 1.27.3, and runtime image Node 26+, glibc, CA roots and the bookworm `useradd/groupadd` utilities. All image inputs require immutable digests; empty/mutable tags are refused. The build checks CometBFT v0.38.26 module checksum and commit, applies the checked-in dependency pins, builds with locked Rust dependencies, and runs only version smoke checks. Pin the resulting image digest in `TIME_IMAGE`; sign its registry digest, manifest, SBOM and evidence with your external release authority. Version smoke is not multi-host validation, a reproducible-build ceremony or remote-signer testing.

`node deploy/verify.mjs deploy/results/NEW.json` repeats the operator suite on the host and in a network-disabled Linux container, validates Compose's missing-configuration refusal, and records source hashes. `node deploy/audit-comet.mjs RELEASE_DIRECTORY LOCAL_IMAGE` extracts only the public Comet binary and runs checksum/commit-pinned official govulncheck in the pinned Go image; `node deploy/audit-comet-source.mjs AUDIT_DIRECTORY` supplements the custom unversioned main module with exact source-version/package-graph checks against every returned Comet advisory. Both preserve complete findings and hashes without suppression flags. A database scan covers published advisories for its precise scope, not every defect or the whole platform.

## Enrollment and namespace

On an offline operator enrollment host, run `node deploy/keygen.mjs /secure/NEW-operator-directory`. The command uses OS CSPRNG Ed25519, exclusive creation, and Linux modes 0700/0600. It prints public identifiers only. `consensus-enrollment.json` contains the consensus secret for import into the externally managed signer; keep it off the validator and build host, then follow the signer's audited import/erasure policy. `node-identity.json` is a separate P2P identity. JavaScript cannot guarantee erasure of every runtime copy; a hardware-native key ceremony is preferred. Windows ACLs must be managed separately; Unix mode bits are not an ACL guarantee there.

Create an independently reviewed Comet genesis with the public bootstrap keys and valid protocol-4 `app_state`. The root launcher demonstrates a local fixture; its known keys and one-host topology are not an operator ceremony. Every operator independently pins the exact genesis SHA256, chain ID, network ID, release ID and peer keys. Put genesis, settings, release manifest, pinned trust policy, signer lease and P2P identity in `/etc/time-v4/operator` owned by UID 10001. Only the signer enrollment directory contains the consensus secret. Do not mount it into the validator or app.

Copy `settings.example.json` and fill every placeholder. At least two pinned sentry peers are required. Configure independent sentries on separate hosts from their generated default Comet config using `sentry.toml`; replace placeholders, verify P2P IDs out of band, and keep RPC/ABCI private. The validator has no host-published ports and makes outbound P2P connections to these peers. Apply host firewall egress rules to permit those peers and required operator services only. Sentry redundancy is an availability measure, not proof of stake independence.

Compose shares the validator network namespace with app and signer. ABCI 26658, RPC 26657, signer 26659 and Prometheus 26660 bind loopback. Only sentries expose P2P publicly. Containers run without capabilities, as UID 10001, read-only except dedicated data volumes, and stop on failures. `TIME_IMAGE` and `REMOTE_SIGNER_IMAGE` must both be digest pinned; run `deploy/build.mjs check-env` before `docker compose -f deploy/compose.yaml up --abort-on-container-exit`. The systemd example assumes this bundle at `/opt/time-v4` and a reviewed environment file under `/etc/time-v4`. Docker-socket access is privileged; the unit's hardening is not a sandbox around Docker.

## Mandatory remote signer boundary

This repository does **not** implement a remote signer/HSM. Supply an independently reviewed signer image compatible with Comet's remote private-validator protocol and connect it to `tcp://127.0.0.1:26659` from the shared namespace. There is deliberately no local file-validator fallback. The signer must persist height/round/step/sign-bytes/signature atomically, refuse conflicting signatures, and consult an exclusive monotonic fencing authority **at every signature**, including after a network partition. A PID file, a filesystem lock or a signed lease checked only at startup cannot prevent signing from cloned hosts.

The runtime guard additionally requires an externally signed short lease scoped to the exact genesis, chain ID, key and release, and verifies it again every five seconds. A child may run until the expiry of the last lease that verified and is told to stop within five seconds of it. The remaining life of a lease is also counted on the monotonic clock from the moment it verified, so a clock that is set back afterwards does not lengthen it. A verification that refuses what it read (a lease that has ended, is for another key or release, or comes from an authority that is no longer pinned) stops the child at once; one that cannot read its files, or does not return, stops nothing before that expiry. A consensus child that still runs ten seconds after it was told to stop is killed (`leaseWatch` in `operator.mjs`). The signer container is not under this guard: it signs for whoever listens on `127.0.0.1:26659`, so a lease reaches it only through the end of the CometBFT process. The signer itself must refuse signing requests for any other chain ID. This limits stale instances but does not replace per-signature enforcement. A crash leaves a local process-lock file; never remove it until the former process is stopped and its signing authority lease is revoked. Do not run two instances with the same consensus key, use automatic VM cloning, or automatically restore signer state.

Attestations are JSON `{issuer,payload,signature}`. Signature is standard base64 Ed25519 over UTF-8 `TIME-OPERATOR-ATTESTATION-V1` followed by a zero byte followed by canonical sorted-key JSON of `payload`; only integers, booleans, null, strings, arrays and objects are accepted. Trust policy pins `{id,organization,public_key_hex,roles}` independently of the attestation. A `signer_lease` payload contains `kind`, `release_id`, `genesis_sha256`, `chain_id`, `validator_public_key_hex`, `signer_identity`, `fence_domain`, decimal-string `fence_token`, `lease_id`, `enforcement:"EVERY_SIGNATURE"`, `issued_utc`, and `expires_utc`. Lifetime is at most five minutes. Keep lease and trust files writable by the external controller, read-only inside containers. This format authenticates the authority's claim; source review and fault tests must establish actual enforcement.

**A reference controller for these leases.** `deploy/lease-controller/` is a service that an operating organization runs on a host of its own to issue signer leases. `deploy/lease-agent.mjs` is the agent that keeps the lease file fresh on a validator host: it asks, checks every answer with this guard, and renames a finished file into place. `deploy/lease-controller/README.md` is the operator's guide; `docs/design/signer-lease-controller.md` is the design, with what is promised and on which assumptions.
- The controller never issues leases for one consensus key to two hosts so that both are valid at the same time, also across its own crashes and restarts. That holds under the conditions its design states (section 4): every clock within five seconds of true time, one controller on one state directory for an authority key, no key stolen. It does not hold for a lease file that is copied to a second machine together with the settings: the guard cannot know which machine it runs on.
- It refuses a lease for the other engine, for a release nobody approved, and for a host that is not the key's holder. A key moves to another host only by an operator's command and after a wait.
- It is not a signer and does not make one unnecessary. Everything in the first paragraph of this section still applies: the lease is checked by the guard every five seconds, not by the signer at every signature.
- It cannot know what a signer enforces. It writes `enforcement:"EVERY_SIGNATURE"` only for a host whose operator declared that in the controller's config, and marks every lease `enforcement_basis:"OPERATOR_DECLARATION"`. Read "The declaration about the signer" in its README before writing that declaration.
- Its leases carry four fields more, which the guard ignores: `host_id`, `request_nonce`, `renew_by_utc` and `enforcement_basis`.
- It ran once beside CometBFT 0.38.26 and two remote signers on several machines, in the kit rehearsal on AWS: `deploy/lease-controller/README.md`, "What the rehearsal showed".

## Backup, restoration and monitoring

Stop the operator cleanly before copying the Comet and application volumes; snapshot them as one coordinated checkpoint. Include the application's adjacent `.history/leaves.bin` and `.history/nodes.bin` archive in that checkpoint; the authenticated current root/count remains in the ledger, but historical inclusion proofs need the append-only local archive. Never splice archive files from a different checkpoint. Keep encrypted, access-controlled backups off the build context. Never discard the remote signer's live anti-double-sign journal. Run `time-node-v4 --devnet --db BACKUP.redb --audit` offline on a preserved copy: this validates the full JMT, directory bijection, supply and extension invariants. Reconcile Comet height/app hash, authenticated history count/root and signer state before any restart.

`node deploy/restore-check.mjs BACKUP_ATTESTATION LIVE_FLOOR TRUST EXPECTED_CONTEXT` refuses signer H/R/S rollback, conflicting state at the same position, old fence tokens, wrong network/key/release, or a floor older than 60 seconds. Both signed payloads include `fence_domain`, decimal-string `height/round/step/fence_token`, `sign_bytes_sha256`, `signature_sha256`, timestamps and expected context; roles are `signer_backup` / `signer_floor`. Passing is a preflight only: acquire a NEW fencing token from the live authority and prove the old lease cannot sign. The tool never copies, unlocks or starts a signer.

`node deploy/operator.mjs probe SETTINGS` checks local freshness, protocol, GC pressure, mode, metadata supply identity and the Bitcoin pause flag. `node deploy/monitor.mjs SETTINGS` exposes `/ready` and Prometheus `/metrics` on loopback 26661. These HTTP diagnostics are unauthenticated operational observations, not wallet balance proofs or a full supply recount. Monitor missed blocks, peers, consensus round growth, clock offsets, disk/free space, GC backlog, signer lease freshness (`node deploy/lease-agent.mjs status CONFIG 120` exits with code 2 when the installed lease has under two minutes left) and Bitcoin stale/deep-reorg earning pauses. Alert and stop for signing uncertainty; do not automatically wipe state or bypass guards. An operator and dependency maintenance process remain necessary.

## External candidate gates

`node deploy/launch-check.mjs RELEASE TRUST ATTESTATIONS GENESIS_SHA256` reports outstanding gates until separately pinned authorities sign scope-bound evidence for independent security review, operator independence/control and stake concentration, Linux multi-host fault testing and remote-signer fencing. Release authors cannot self-attest these independent gates. A signed roster must include at least four distinct organizations and consensus keys; the current production PoS profile separately requires twenty bootstrap organizations and its stake thresholds. More keys on one host are not independent control. No gate is marked passed by the packager or by a local test run. Even when signed evidence is present, the result remains a candidate and public funds stay disabled.

## Version-5 engine (`time-node-v5`)

The same kit builds, releases, runs and checks `time-node-v5`: the protocol-4 ledger on the version-5 engine (`v5/README.md`). Every validator of a network runs the same engine, so a v5 release starts a NEW network with its own volumes; it never takes over a v4 network or its volumes. Everything above applies unless this section says otherwise. v4 releases are unchanged: same packager output and release identity for the same inputs, same `compose.yaml` and `time-v4.service`.

**Engine selection.** A v5 manifest carries `"engine": "v5"`; a manifest without the field is v4. The field is part of the release identity, so it cannot be added or removed without changing `release_id`, and kits older than this one reject v5 manifests (identity mismatch). The pinned release decides everything else: `build.mjs` picks `deploy/Dockerfile.v5` and checks `time-node-v5 --version` for exactly `time-node-v5 0.10.0 protocol=4 devnet-only publicLaunchAllowed=false`; `operator.mjs` starts `time-node-v5`; the probe requires `"engine":"v5"` in `/status`. A v4 node behind a v5 pin, or the reverse, is not ready.

**The signer lease names the engine.** A v5 release runs only with a `signer_lease` whose payload also carries `"engine": "v5"`, so the external controller signs the pairing of engine, release, genesis, chain and key. A v4 lease carries no `engine` field (its format is unchanged), and a v4 release refuses a lease that has one. A controller that fences a v4 network must never sign a v5 lease for that network's genesis: the guard cannot tell a v4 genesis from a v5 one, because both engines read the same genesis format. The reference controller (`deploy/lease-controller/`) binds its state to one genesis and one engine at its first start: it then refuses a request and a release of the other engine (`WRONG_ENGINE`), and refuses to start with a config that names the other engine for that genesis.

```sh
node tools/release-v5.mjs --out releases/v5-candidate-001 \
  --rust-image rust@sha256:VERIFIED_64_HEX_DIGEST \
  --go-image golang@sha256:VERIFIED_64_HEX_DIGEST \
  --runtime-image node@sha256:VERIFIED_64_HEX_DIGEST
node releases/v5-candidate-001/context/deploy/build.mjs build releases/v5-candidate-001 time-v5:candidate-001
node deploy/verify.mjs --engine v5 deploy/results/NEW-v5.json
docker compose --project-name time-v5-private-devnet -f deploy/compose.v5.yaml up --abort-on-container-exit
```

**Release.** The allowlist adds `v5/Cargo.toml`, `v5/Cargo.lock` (v5 is its own workspace and lockfile), all `.rs` under `v5/src` and `v5/tests` (including `tests/common`), `campaign/lib/genesis.mjs` (read by `v5/tests/fee_genesis_bytes.rs`), `tools/genesis-v5.mjs` when it exists (for the coming `v5/tests/production_genesis.rs`), `tools/release-v5*.mjs` and a frozen v4 manifest used by the tests. It keeps `v4` and `v2`: `v5/Cargo.toml` depends on `timecurrency-v4` for its tests, and Cargo resolves the lockfile with it. `Dockerfile.v5` uses the same digest pins, Rust 1.99.1 check and CometBFT v0.38.26 module pins as v4, but compiles offline: `cargo fetch --locked` runs in its own step, then `cargo build --manifest-path v5/Cargo.toml --release --frozen --bin time-node-v5`; Go downloads and verifies modules, then builds with `GOPROXY=off` and `-mod=readonly`. The compile steps still run with the network available. Cargo and Go fetch nothing there, but a dependency's build script could still connect. `RUN --network=none` on those two steps would close that once the pinned Docker is known to support it; it is not used yet. (`deploy/Dockerfile` for v4 is unchanged and still builds with the network available.) The combined distribution (`node tools/release-v5.mjs distribution NATIVE NEW_OUT`) refuses a native release of the other engine. Both distributions now ship `client-v4/account-security.mjs` and `client-v4/own-node.mjs`, which the gateway imports; this changes the v4 distribution identity, not the v4 release identity. The gateway's settings may carry an optional `own_node: {rpc_url, above_micros, timeout_ms}`; `rpc_url` must be a literal loopback origin and differ from `native_rpc_url` (see `deploy/gateway/README.md`).

**Compose project and unit.** Run v5 only with `deploy/compose.v5.yaml` (project `time-v5-private-devnet`) or the `deploy/time-v5.service` unit, which passes `--project-name time-v5-private-devnet` to both `up` and `down`. The unit runs `down` from `ExecStopPost` as well as from `ExecStop`: systemd skips `ExecStop` when the main process fails by itself, which `up --abort-on-container-exit` does whenever a container fails, and in the kit rehearsal the containers of such runs stayed; a signer container left running in the network namespace of a validator container that had ended then failed every later start (`can't get pubkey`). In the next rehearsal (`tc-v5-kit-5`) `ExecStopPost` removed the containers and the network after each of three runs that failed by themselves. After `systemctl stop` the unit shows `failed`: `docker compose up` ends with status 143 on `SIGTERM`, and the unit does not list 143 as a success; that is the normal end of a stop, not a fault. Its own project gives it its own `consensus` and `ledger` volumes. It differs from `compose.yaml` only in:
- the project name;
- a read-only mount of the ledger volume at `/data/ledger-view` in the validator container;
- `init: true` for the three Node containers (validator, app, monitor), so SIGTERM reaches them at once, and for the signer. A program that installs no handler for SIGTERM ignores it as process 1 of a container: in the kit rehearsal tmkms 0.15.0 ran on for the whole 30 s of its `stop_grace_period` after `docker stop` and signed 18 more heights before Docker killed it, while Cosmos-KMS, which handles the signal itself, ended in a second. With an init process a stop reaches either signer;
- explicit `stop_grace_period` values;
- the `tmpfs` entries are quoted (`["/tmp:rw,noexec,nosuid,size=32m"]`). Unquoted, YAML splits the entry at its commas into four, and Docker refuses to create the container (`invalid mount path: 'noexec' mount path must be absolute`); `docker compose config` accepts it. The v4 `compose.yaml` still has the unquoted form;
- a volume `signer-state`, mounted read-write at `/signer-state` in the signer container only. The signer's root file system and `/signer` are read-only, so this is the one place where a signer can keep its record of the last height, round and step it signed. The signer image must write that record there. Never discard, copy or restore this volume on its own; it belongs with the key.

A v5 validator refuses to start without that read-only view, so the v4 `compose.yaml` cannot run a v5 release.

**CometBFT writes a file validator key at start.** CometBFT 0.38.26 (`cometbft start`) loads or creates the key and state files of its own file validator before it looks at `priv_validator_laddr`, and panics when it cannot write them. The v5 configuration names files on the validator container's tmpfs (`/tmp`): CometBFT writes a random key there that is in no genesis and signs nothing (the remote signer replaces it), and it is gone when the container ends. The v4 configuration still names files on the read-only `/operator` mount, where CometBFT panics at start; v4 is left as it was.

**Running.** The app container runs `time-node-v5 --devnet --db /data/ledger/v5-state --listen 127.0.0.1:26658`. ABCI stays on loopback 26658 in the shared validator namespace. State lives in the ledger volume: snapshots in `/data/ledger/v5-state.v5state/` (the two newest), block history in `/data/ledger/v5-state.history/`. Optional settings, v5 only, each validated and passed to the node as its flag only when present: `snapshot_seconds` (5 to 86400; the node defaults to 120), `clock_tolerance_seconds` (below), `state_sync_snapshot_blocks`, `state_sync_snapshots_kept`, `state_sync_max_mib` and `keep_blocks` (see "Snapshots, replay, state sync and pruning"), and `stop_after_height` (see "Upgrades and exit code 4"). The guard refuses every one of them on a v4 release, and refuses a value the node would refuse. It also refuses a settings file that holds any key it does not know, and names the key: a mistyped optional setting must not pass as if it were absent.

**Volumes are bound to one engine and one network.** On first start the v5 launchers write `network-binding.json` (`{schema_version, engine, genesis_sha256, chain_id}`) into the ledger and the consensus volume. The file is created atomically and never overwritten: it is written to a temporary file, fsynced, then hard-linked to its final name. Before every start, each launcher refuses:
- a binding for another engine, genesis or chain;
- a damaged binding. The message names the file and the remedy: confirm out of band which network the volume belongs to, then remove the file, or use fresh volumes;
- the other engine's state in the ledger (v5 refuses `state.redb`/`state.history`, and v4 refuses `v5-state.*`, so a v4 rollback cannot start on v5 volumes);
- for v5, a consensus volume that holds blocks without a v5 binding;
- for v5, blocks in the consensus volume while the ledger has no saved snapshot (`v5-state.v5state/state-*.snap`), whatever the ledger's binding says. That is a lost or swapped ledger: restore it from the coordinated checkpoint. The kit never rebuilds it from the blocks automatically. The same refusal follows if the node crashed (not a clean stop) before its first snapshot; for a validator that new, start with fresh volumes and let it re-sync.

v4 writes no binding, so v4 volumes stay as they were. Each refusal ends with "start this release in a new Compose project: fresh ledger AND consensus volumes". Never reuse one of the two volumes with a fresh copy of the other. The validator writes CometBFT's `genesis.json` from the exact bytes the guard hashed, never by re-reading the file, so Comet runs the genesis the bindings record.

**Clock.** Every validator host must keep time with NTP. On AWS, run chrony against the Amazon Time Sync Service (`169.254.169.123`). `time-node-v5` checks the time of each proposal in ProcessProposal and refuses proposals further off than its clock tolerance, so a validator whose own clock is off refuses honest proposals. The optional setting `clock_tolerance_seconds` (an integer from 1 to 60) is passed as `--clock-tolerance-seconds N` only when present; without it the node uses 30 s. The cap is 60 s because CometBFT's `consensus.block_time_tolerance` defaults to 60 s, so a larger value would have no effect.

**One engine version per network, until the network itself changes it.** This kit builds and accepts `time-node-v5 0.10.0 protocol=4` for v5 (the version line is checked exactly at build). Do not run 0.5.0 or 0.6.0 on a network that runs 0.7.0 or later: 0.6.0 changed consensus rules against 0.5.0 (the clock check in ProcessProposal, automatic double-sign penalties), and 0.7.0 accepts the validators' upgrade signals (action kind 80), which 0.6.0 rejects, so a 0.6.0 node stops with an error at the first block that carries one. 0.9.0 knows genesis settings that 0.7.0 does not (`waits_survive_stops`, `protected_registration`, `service_records`; `v5/README.md`): a 0.7.0 node refuses a genesis that carries one, as every production genesis now does, and on a network without them the two follow the same rules. 0.10.0 knows one more genesis setting, `market` (`spec/market.md`), which a 0.9.0 node refuses at InitChain; the two programs have not been run together on one network. Programs that printed 0.8.0 were development builds and were never released: those built before the service records refuse a genesis that carries them, and the first of them counts a stop on the clock of the waits only beyond an hour, so on a network with `waits_survive_stops` it parts from this release at the first gap of more than five minutes. Never run one beside this release (the release id tells them apart). `protocol=4` names the protocol versions the program implements. A later release that also implements a version 5 prints `protocol=4..5`, before and after the network activates it; a kit that pins that line comes with that release.

**Snapshots, replay, state sync and pruning.** The node keeps state in memory and writes a checksummed snapshot every `snapshot_seconds` and on `SIGTERM`. After a restart it loads the newest valid snapshot and CometBFT replays the blocks after it. So CometBFT must keep every block since the oldest snapshot, and it does: CometBFT 0.38.26 deletes blocks only below the `retain_height` the application returns, and the node never names a block after its oldest snapshot. The generated v5 `config.toml` adds `[mempool] recheck = true` (v5 relies on re-check after every block) and `[storage] discard_abci_responses = false`. The second is needed for upgrades and must stay: when a node crashes between its own commit of a block and CometBFT's, the restart replays the stored answer of that block, and at the block that activates a new protocol version that answer carries the new version. The kit writes no `[statesync]` section and no pruning key; what is pruned and offered is decided by these node settings alone:

| Setting | Accepted | Node flag | Meaning |
|---|---|---|---|
| `keep_blocks` | 0, or 2,000,000 to 10^12 | `--keep-blocks` | Blocks CometBFT keeps. Without it, or with 0, every block is kept, as before. A lower number than 2,000,000 would change nothing: CometBFT needs that many blocks, and 14 days, to judge evidence. |
| `state_sync_snapshot_blocks` | 0, or 10 to 1,000,000 | `--state-sync-snapshot-blocks` | Write a snapshot for joining peers every N blocks. Use the same N on every node of a network, so that peers can fetch one snapshot from all of them. 0 or absent: none. |
| `state_sync_snapshots_kept` | 1 to 10 | `--state-sync-snapshots-kept` | How many of them stay on disk and on offer (the node keeps 2). Needs the setting above, not 0. |
| `state_sync_max_mib` | 4 to 400,000 | `--state-sync-max-mib` | The largest snapshot this node would restore, in MiB (the node allows 16,384). |

- With `keep_blocks`, CometBFT also deletes its stored answers for the deleted heights; the recent ones the restart needs stay. A pruning node cannot serve old blocks to a node that syncs from genesis, and cannot rebuild a lost ledger from its own blocks. Keep at least one node of the network without `keep_blocks`, and point gateways and shops' own nodes at a node that keeps everything (`v5/README.md`, "What this means for the gateway").
- A snapshot for peers costs one more full write of the state every N blocks and one file per snapshot kept, under `/data/ledger/v5-state.v5state/statesync/`. The ledger volume then needs room for the two restart snapshots, the snapshots kept for peers and the history.
- This kit does not make a node join through state sync: it writes no `[statesync]` section (that needs `enable = true`, two `rpc_servers`, and a `trust_height` and `trust_hash` the operator took from a source they trust). A validator started by this kit syncs every block from genesis and has checked every rule itself. Joining from a snapshot is a decision for a full node configured by hand, described in `v5/README.md`.
- State sync has run once under CometBFT 0.38.26, without this kit: on 2026-11-18, on a seven-validator laboratory network on AWS whose validators wrote a snapshot every 100 blocks and kept ten, a new node joined from a snapshot and had caught up 25 seconds after its start, on a chain of about 1,200 blocks with a very small state. Pruning (`keep_blocks`) has never run on a network: it needs two million blocks. Neither has run through this kit. `v5/README.md`, "State sync and pruning", "What ran on a network, and what did not", lists what that run showed and what it did not: a node that has executed blocks refusing a snapshot, a state of realistic size, a bad chunk, evidence about heights before a restore.

The Comet volume grows with every block unless `keep_blocks` is set.

**Upgrades and exit code 4.** A network changes its rules by a new protocol version that its validators schedule on the chain at least 21 days ahead (`docs/design/upgrade-mechanism.md`). No program is swapped at the switch: the release that implements the new version is installed before it and runs the old rules until then.

- *The order of work.* A node admits to its mempool and proposes a support signal only for a version its own program implements. Handed to any other node the signal is refused: `this node does not implement that version under that specification hash and neither admits nor proposes signals for it`. So no signal enters a block until validators that propose run the release that implements the version, and the work goes in this order:
  1. The release that implements the new version is published; each operator builds and verifies it.
  2. Validators install it, one at a time ("Before the start time", below). It runs the old rules until the start, so a network on both releases is the normal state from here on.
  3. Owners signal, each through a node that runs the new release. A signal waits in the mempools of such nodes until one of them proposes: one validator on the new release is enough for it to be included, and the more of them run it, the less it waits. Signal once enough validators run the release for the chain to go on at the start, not before.
  4. The plan is scheduled when its supporters reach four fifths, and the notice runs: at least 21 days between the block that schedules the plan and the start time the signals named. Validators that have not installed the release do it in that time.
- *How many must agree.* A plan is scheduled when its supporters hold at least four fifths of the voting power, and it stays scheduled only while they hold at least three quarters, in every block. With few validators the two numbers are close:
  - Seven equal validators: six to schedule and six to stay scheduled. After scheduling with six, one withdrawal cancels.
  - Twenty equal validators, as at the start of a production network: sixteen to schedule, fifteen to stay scheduled. Five that do not signal keep every plan from being scheduled. After scheduling with exactly sixteen, the second withdrawal cancels the plan, and a new one starts its notice from zero.
  - Once independent validators hold part of the power, each starting validator weighs less. If the twenty hold 90% of the power, eighteen of them schedule a plan without anyone else and seventeen keep it; at 85%, nineteen and eighteen; at 80%, all twenty and nineteen. Below 80% they cannot schedule alone, and below 75% they cannot keep a plan alone: independent validators must support it. At 55%, for example, it takes all twenty and 55.6% of the independent power, or every independent validator and thirteen of the twenty.
  - The starting validators can keep any plan from being scheduled while they hold more than a fifth of the power, and cancel one while they hold more than a quarter. Under the stake hand-over rule they hold more than half until the hand-over.
  - A signal does not count while its owner account is frozen or in a recovery, and a jailed validator is left out of both sums.
  - Blocks are another count. More than two thirds of the voting power must run the new release at the start (five of seven, fourteen of twenty equal validators), or the chain waits for them. Supporting a plan and running the release are two things: the chain cannot see which program a validator runs.
- *Which program runs.* `time-node-v5 --version` prints one line and opens nothing. This kit's release prints `time-node-v5 0.10.0 protocol=4 devnet-only publicLaunchAllowed=false`. The rehearsal build of the same source prints `time-node-v5 0.10.0 protocol=4 rehearsal=5 devnet-only publicLaunchAllowed=false`: this kit and the release tool refuse that line, and that build never runs on a network that matters. A release that implements a real version 5 will print `protocol=4..5`. On a running node, `upgrade.implemented` of its `/status` lists the versions and specification hashes of the program that answers (`operator.mjs probe` shows the versions as `upgrade.implemented_versions`), and the node logs `This program implements protocol version N (spec ...).` at start.
- *Seeing it coming.* The node's `/status` has a field `upgrade`: the versions the program implements, the scheduled plan, `implements_scheduled` and `stop_after_height`. `operator.mjs probe` and the monitor's `/ready` report it, the monitor's `/metrics` has `time_upgrade_scheduled` and `time_upgrade_not_implemented`, and `alerts.yaml` raises `TimeUpgradeNotImplemented` while the scheduled version is one this node does not implement. The node also warns in its log at start and every ten minutes. The version the chain is under is not in that field: it is `app_version` of the same `/status`, the version in force at the height the query asks for (at the head, when it names none, which is what `probe` asks). This kit's `probe` accepts `app_version` 4 only and reports anything else as not ready; the kit that comes with a release implementing a later version accepts that range. Do not monitor `node_info.protocol_version.app` of CometBFT's `/status`: it is the value at start and goes stale.
- *Before the start time.* Build and verify the release that implements the scheduled version, obtain signer leases for its `release_id` (a lease names the release, lasts five minutes, and is checked every five seconds, so no validator runs a release without leases for it; with the reference controller the operator approves the release first, `deploy/lease-controller/README.md`, "An upgrade: approving the next release"), stop cleanly, pin the new `release_manifest` and `release_id` in the settings, and start the whole stack on the same volumes. Do it well before the start: the new release runs the old rules until the block that activates the new ones.
- *Signalling support for a plan* is the validator owner's action. This kit holds no account key and never signs one.
  - The owner sends the signal from the wallet, in the tab "Validator signal", with the validator's owner account unlocked (`web-v4/wallet/README.md`, "Validator signal"). The tab is there only for an account that owns a validator. The owner types the version, the specification hash and the start time from the release announcement; the wallet fills in none of them. A key of the account that may spend signs: the payment key of a secured account, with the payment password.
  - First install the release on this host, then signal. A node admits a signal of support only for a version and hash its own program implements, so the wallet's gateway must stand in front of a node that runs the new release. A gateway in front of an older node refuses the signal; the wallet keeps the signed signal as pending and says so.
  - Check the hash on this host before signalling. The node's status lists what its program implements, each version with its hash (`upgrade.implemented`): it is the answer to the query `/status` of the node's local RPC (`http://127.0.0.1:26657/abci_query?path="/status"`, whose `response.value` is that status in base64). `operator.mjs probe` makes the same query and prints the versions without their hashes (`implemented_versions`). The hash must be the one in the release announcement.
  - To take support back, the owner uses "Withdraw your support" in the same tab. A validator's signal can change once every ten minutes.
  - A program can send the signal with the SDK instead (`client-v4/README.md`, "A validator's upgrade signal").
  - A signal the owner did not send means that someone else holds a key of the owner account that may spend. Put the owner account under the alert watch (`deploy/watch/README.md`): on a network whose trust data says that its nodes report upgrades it tells the owner of every new signal of the account (`upgrade_signal_changed`), with the plan and what to do. The wallet's tab warns too, while the wallet is open.
  - Not verified: the tab has not been run in a browser, and no signal has been sent from the wallet or the SDK on a live network. The upgrade rehearsal sent its signals from the test harness. The query above is described from the kit's code and was not run here.
- *A node that was not replaced* executes the activating block like everyone, stops answering CometBFT, saves its state, prints `STOPPED FOR UPGRADE` with the version, the spec hash and the height, and exits with code 4. `operator.mjs run app` exits 4 too, with a message that says what to install. The validator container then stops as well (CometBFT ends when the application is gone). Nothing is lost and nothing needs to be deleted or rolled back: install the release that implements the version and start it on the same volumes. Until validators with more than two thirds of the votes run it, the chain waits.
- *What that looked like when it ran.* In the rehearsal of 2026-11-18 (seven laboratory validators on AWS, the node and CometBFT started directly by the test harness, not by this kit), two validators were left on the old program on purpose:
  - Each printed, as its last two lines, `STOPPED FOR UPGRADE` and `This chain runs protocol version 5 (spec ...) from height 839. This program implements version 4. The state at height 838 is saved and valid. Install a release that implements version 5 with that specification and start it on the same data. Delete nothing.`, and ended with exit code 4.
  - CometBFT on those hosts ended by itself within a second, with exit code 0. Its own exit looks like a stop on request: go by the node's exit code and first line.
  - The other five went on. One block took 2.6 s instead of 0.3 s, a pause of about 2.3 s.
  - Started on the new program on the same data, the two had caught up and signed again after 7 and 9 seconds.
  - Before the start, replacing the program on a running validator (a clean stop, a start on the same data, caught up and signing) had taken 5 to 8 seconds each, one validator at a time. With this kit a replacement also stops and starts the containers and needs leases for the new release: allow more, and never have a validator down across the start time.
- *Exit code 4 has two more causes*, told apart by the first line the node printed:
  - `STOPPED AS ASKED`: the node was started with `stop_after_height` and has committed that block. This is the coordinated stop of an emergency: operators agree on a height H out of band, each sets `"stop_after_height": H` in the settings and restarts before H, and with more than a third of the votes stopping after H the chain stands at H for everyone. A node whose head is already at H stops at once; a node whose head is above H refuses to start (exit code 1, and `operator.mjs run app` then says that the settings carry `stop_after_height`). A start that fails prints its reason first and again as the last line of the node's output, after the usage text: `The node did not start: --stop-after-height H: this node is already at height N, above it. Nothing was changed.` In the rehearsal all seven validators were restarted with one height about two minutes ahead: each committed it and stopped with exit code 4, none committed the next block, all seven recounted the same root at that height, and started without the setting the chain went on about five seconds after the order. The setting is a whole number from 1 to 9,007,199,254,740,991. Remove it before any start that should run on. `TimeStopAfterHeightSet` fires while a node runs with it.
  - `STOPPED AT A SWITCH`: a decided block carries the emergency switch (action kind 81) of a fix release. This release does not execute that block; its state stays at the height before. Install the fix release the coordinators name and start it on the same volumes: CometBFT hands it that block again. No rollback and no file to delete. A fix release prints the same first line in two more cases, and its second line says which: the decided block at its switch height is not its switch block, or the state is already past that block under the old version. Then start the release the state was made by, and wait for a fix release built for the height the chain stopped at. `operator.mjs run app` names all three causes, since it cannot read the node's lines. The whole emergency procedure, with what must be ready beforehand and what an operator types with this kit, is `docs/emergency-fix.md`.
- In all three cases the policy stays "no automatic restart": a supervisor that restarted the same release would only stop again.
- Once the node has stopped, the monitor can no longer probe it: `time_private_devnet_ready` is 0 and `TimeOperatorNotReady` fires, whose summary names exit code 4. `time_upgrade_not_implemented` and `time_upgrade_scheduled` keep the node's last report (`/ready` shows it as `upgrade`, with `upgrade_observed_utc`), so `TimeUpgradeNotImplemented` stays raised until a release that implements the version runs.

**Stopping and exit code 3.** `SIGTERM` makes the node write a final snapshot and exit 0. The launcher handles SIGTERM from its first instruction: a stop before the node is spawned ends the launch cleanly, and after spawn it is passed to the node. Compose stops services in reverse dependency order, each within its own `stop_grace_period`:
1. monitor (10 s) and signer (30 s);
2. app (120 s, for the full final snapshot);
3. validator (30 s).

That is at most 180 s. `time-v5.service` therefore runs `down` without `--timeout` (which would override every grace period) and sets `TimeoutStopSec=240`. If a snapshot still takes longer, the node is killed and the next start uses the previous snapshot plus replay, which is safe because the node never lets CometBFT delete a block after its oldest snapshot. The launcher does not pass `--stay-after-disconnect`: when CometBFT disconnects, the node saves a snapshot and exits with code 3, and `operator.mjs run app` exits 3 too with a message saying so. The kit's policy stays "no automatic restart" (`restart: "no"`, `Restart=no`). An operator who sees exit 3 should:
1. find why the validator (Comet) container stopped (its log, a guard or signer-lease failure, a crash);
2. confirm the signer lease and fencing are healthy;
3. leave the process locks alone unless the former processes are verified stopped;
4. start the whole stack again.

Never wipe the ledger or Comet volume to "fix" a restart.

**The consensus launcher ends CometBFT within ten seconds of a stop.** On `SIGTERM` (Compose, systemd) the v5 consensus launcher passes `SIGTERM` to CometBFT and sends `SIGKILL` 10 s later (`GUARD_KILL_MS`) if CometBFT still runs; then it removes its process lock. In the kit rehearsal a CometBFT whose remote signer had already gone did not end on `SIGTERM`: it kept waiting for the signer (`SignerListener: ... accept ... i/o timeout`), Compose killed the whole container after its 30 s `stop_grace_period`, the launcher died with it, and the lock it left (`operator-process.lock` in the consensus volume) refused every later start with `Existing process fence`. That happened after an ordinary stop of the signer. Before this change the way out was the one this README gives for a crash: make sure the former process is stopped and its lease revoked, then remove the lock. With this change (rehearsal `tc-v5-kit-5`), after a signer was stopped and after one was killed with `SIGKILL`, CometBFT was killed about 10.2 s after its `SIGTERM`, no lock stayed, and the start after the 100 blocks below joined at its first attempt; the clean stop of seven validators left no lock. The signer container has no `init: true`: tmkms 0.15.0 runs as process 1 there and ignores `SIGTERM`, so every stop of the stack waits its 30 s and kills it (exit code 137). It keeps its state at each signature, so nothing is lost, but the stack takes 30 s more to stop (31 s against 1 s with Cosmos-KMS in `tc-v5-kit-5`). It also signs on during those 30 s: after a `docker stop` of its container, tmkms signed 18 more heights before Docker killed it, so stopping the signer is not a way to stop signing at once; stop the stack, or kill the signer. A unit whose CometBFT refused to start (below) stays `active` for the same 30 s.

**A start can end at once because the signer was late.** CometBFT waits a few seconds for the signer to connect and give its public key. If the signer has not answered by then, CometBFT ends with `can't get pubkey: send: endpoint connection timed out`, the stack stops, and nothing has been signed. Seen once in the kit rehearsal of 19 November, with Cosmos-KMS, on a start made right after a stop. In the rehearsal of 23 November (`tc-v5-kit-7`) three starts of validators on Cosmos-KMS, each made after a stop and once 100 blocks had passed, ended with "error with private validator socket client: can't …" (the report cuts the line there), and each time the next start joined. Start the stack again. (The same words appear when a signer container of an earlier run was left in the validator's network namespace; the unit's `ExecStopPost` removes it.)

**A validator starts again only 100 blocks after it last signed.** The kit's CometBFT configuration sets `double_sign_check_height = 100`: before it joins consensus, CometBFT looks for a signature of its own key in the last 100 blocks, and if it finds one it panics (`Failed to start consensus state: found signature from the same key`); the validator container ends with exit code 1, the node with 3, and Compose stops the stack. So after any stop of a validator that was signing (a lease that ended, a signer that stopped or was killed, a clean stop, a program replaced for an upgrade), wait until the chain is 100 blocks past the validator's last signature before starting the stack again: with blocks about a second apart, two minutes or more. The refusal is a guard against signing with a key that may still be signing elsewhere; do not lower the setting to restart sooner. **On a network of four or five validators of equal power a stopped validator never starts again this way.** CometBFT 0.38.26 leaves block sync at once, without syncing, when the local validator holds at least a third of the voting power in integer arithmetic (its power ≥ total / 3: 1 ≥ 4 / 3 with four validators of power 1). It then joins consensus at its own stored height, which is where it stopped, finds its own last votes there and panics, at every start. In the kit rehearsal one validator of four was refused nine times in a row, each time at its stored height, with the chain more than 200 blocks further. With six or more validators of equal power, and in the production profile of twenty, no validator holds that share, CometBFT block-syncs first, and the rule above is all an operator must wait for. The same holds for the upgrade runbook: a validator replaced this way is out for those 100 blocks, so replace validators one at a time, and never across the start time. Seen in the kit rehearsal (`campaign/README.md`, "The deployment kit, rehearsed").

The pinned CometBFT says the same of itself. Its `cometbft init` writes, above the setting: "When non-zero, the node will panic upon restart if the same consensus key was used to sign {double_sign_check_height} last blocks. So, validators should stop the state machine, wait for some blocks, and then restart the state machine to avoid panic." Its default is 0. The kit sets 100; the test harness, which starts CometBFT itself, keeps the default.

**A chain that stood.** After a coordinated stop (`stop_after_height`, `STOPPED AS ASKED`), after every node failed on one block (`FAILED ON A DECIDED BLOCK`), or after an upgrade that more than a third of the votes did not install in time, every validator signed the last blocks, and no new block comes. With the rule above no validator could start again: the 100 blocks never pass. For that one case the kit has a **resume order**:
- *What the operator types,* on the validator host, once the coordinators have announced the agreed height `H` and root `ROOT`, the settings pin the release to start, and `stop_after_height` is out of them: `node /opt/time-v5/context/deploy/operator.mjs resume-order /etc/time-v5/operator/settings.json H:ROOT`, then `systemctl start time-v5`. The command writes `resume.json` beside the settings (the containers read it as `/operator/resume.json`). It refuses to write over an order that is there: remove the old one on purpose.
- *What the next start does with it.* The node launcher passes `--expect-root H:ROOT`: the node goes on only on the agreed state, and on any other refuses to start, with exit code 1, and changes nothing. The consensus launcher starts CometBFT once with `double_sign_check_height = 0`, and the configuration it writes names the order. It marks the order used in the consensus volume (`resume-orders-used/`) before CometBFT starts.
- *Every later start* writes `double_sign_check_height = 100` again. Nobody has to remember anything: an order that was used never turns the check off again, and an order applies at all only while the node's saved state (its newest snapshot) is at or below `H`. Once the chain has gone on, `resume.json` may be removed; left behind, it changes nothing.
- *When the launchers refuse to start.* An order for another chain, genesis, consensus key or release than the settings pin; settings that still carry `stop_after_height` at or below `H`; and, for the consensus launcher, a node whose last run did not end by itself at a height (exit code 4) or on a failure (exit code 1). The node launcher records how each run of the node ended in the ledger volume (`node-last-exit.json`), with the height of the state it saved. An end by itself at a height or on a failure is kept while the saved state has not moved past it, so a start that CometBFT refused at the standstill does not wipe it; once the state moves on, the next end replaces it. A clean stop (exit code 0), a lost CometBFT or an ended lease (exit code 3) and a kill do not count. A validator that was stopped by hand while the chain stood: set `stop_after_height` to `H` and start the stack once. The node, already at `H`, stops at once (`STOPPED AS ASKED`); then remove the setting, write the order and start.
- *One start.* If that start fails before CometBFT joins (a signer that answered late, a lease that was not there), the order is used up: write a new one. The lease guard runs as at every start.
- *Who could misuse it, and what limits that.* The double-sign rule protects against one consensus key running on two machines, which gets the validator punished. A resume order turns it off for one start, so:
  - An operator who wants to skip the 100 blocks after an ordinary restart cannot: after a clean stop, a lost CometBFT or a lease that ended, the consensus launcher refuses the order. Doing it anyway takes deliberate steps (a stop at a height, a recount of the state, an order), and the configuration and the node's log then say what was done.
  - A second machine with the same key (a cloned or restored host) is what the rule exists for. If the clone also holds an unused order and a node that stopped at a height, as a copy made during the standstill would, nothing in the kit tells the two apart: both would start without the look and sign twice. The lease controller does not help either when the lease files are copied with the host. Never copy, clone or restore a validator host during an emergency, and write the order only on the one machine the key belongs to.
  - Whoever can write into the operator directory or the Docker volumes of a validator host can do this and worse already: the order adds no new way in.
  - The order cannot make a node go on from another state: the node checks the root itself. It cannot make a node skip a block: CometBFT still hands it every decided block.
- *Run once on real machines, by the test harness.* The order, both launchers and the documents are tested without Docker (`deploy/resume.test.mjs`). The kit rehearsal of the harness (`campaign/README.md`, "The deployment kit, rehearsed", "A chain that stood, with the kit") ran it on 23 November on seven validators in one region (`tc-v5-kit-7`): after a coordinated stop at 1,605 with this kit, every validator was refused without an order and the chain made no block; an order with another root was refused by the node and nothing was signed; with the agreed root, block 1,606 came 10 seconds after the starts and every validator signed again; and the next start had the check on again, with the order left in place. That run started again the release that had stopped, not a fix release, and no operator has done it.

**Backup and audit.** Stop cleanly (the final snapshot then matches Comet's height) and copy the Comet and ledger volumes as one checkpoint, including both `network-binding.json` files, `v5-state.v5state/` and `v5-state.history/`. Audit a preserved copy offline with `time-node-v5 --devnet --db COPY/v5-state --audit`. Restore checks, launch gates and the remote-signer boundary are unchanged; leases and attestations are scoped to the v5 `release_id` (and leases also to `engine`).

**What a local run cannot show.** The tests run the packager, guards, volume bindings, health logic and command construction without Docker. Still required:
- a real Docker build of `Dockerfile.v5`, including the offline compile steps;
- `verify.mjs --engine v5` on a Linux daemon;
- a multi-host run with a remote signer, covering the read-only ledger view, bindings on real volumes, snapshots, replay after a kill, exit code 3, and the probe against a live `/status` and `/v4/state`;
- an upgrade through this kit. One was rehearsed on 2026-11-18 on seven laboratory validators on AWS, with a build that carries a rehearsal version 5, by the test harness (`campaign/README.md`): it starts the node and CometBFT directly, with a key file, and one script operated every validator. That run showed the plan and `implements_scheduled` in each node's `/status`, the program replaced before the start, the nodes that were not replaced exiting with code 4 and resuming under the new program, and a coordinated stop with `--stop-after-height` (`v5/README.md`, "Upgrades", "What ran on a network, and what did not"). It did not show, and this kit still needs:
  - the same steps with the image, the remote signer and leases for the new release, and independent operators;
  - the monitor's metrics and the alerts `TimeUpgradeNotImplemented` and `TimeStopAfterHeightSet`, `operator.mjs run app` reporting exit code 4, and the `stop_after_height` setting;
  - a restart at the activating block after a crash, which is what `discard_abci_responses = false` is for (the rehearsal's restarts were clean);
  - a chain that waits because more than a third of the votes were not replaced, a plan postponed by a safety hold, a plan that could not activate, action kind 81, and the production notice of 21 days (the laboratory notice is 120 seconds);
- the start of a chain that stood through this kit with a fix release, by operators. The refusal of every validator without a resume order, and the start with one (`--expect-root`, `double_sign_check_height = 0` for one start, 100 again afterwards), ran once on seven validators in one region, by the test harness, on the release that had stopped ("A chain that stood", above);
- the node flags behind `keep_blocks` and the `state_sync_*` settings through this kit. The same run showed validators offering snapshots (`--state-sync-snapshot-blocks 100 --state-sync-snapshots-kept 10`) and one node joining from them; `keep_blocks` has never run on a network. The launch commands are checked here against a port of the node's argument parser, taken from the landed code of the node (0.7.0; 0.8.0 takes the same arguments), `--stop-after-height` included.
