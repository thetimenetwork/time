# Time API

Validators keep no index of payments, and nothing else lets a program look up an account, a payment or a block. This process does: it follows the chain from a CometBFT RPC, keeps an index in SQLite, and serves a plain JSON API under `/v1/` that any language can call. Exchanges, wallets and shops use it to detect deposits, send payments and confirm them; an explorer reads its pages from it.

It holds no key of any account and signs nothing. The integration steps, with `curl`, are in [`docs/integration-guide.md`](../../docs/integration-guide.md). The routes are described in [`client-v4/api/openapi.json`](../../client-v4/api/openapi.json), also served at `/v1/openapi.json`.

## Running it

Node 26 and this repository's `client-v4/`, `deploy/watch/start.mjs` (its lock and log code) and `web-v4/shared/verifier/` (the installed proof verifier) are all it needs. With `serve_explorer` it also needs `web-v4/explorer/` (the pages it then serves, read at start) and the menu of the public networks that the pages carry, `web-v4/shared/network-menu.` with `js` and `css`: without those files it does not start, and says which one is missing. It uses no npm packages. The gateway distribution carries the files of the first list.

```sh
cp deploy/api/config.example.json /etc/time-api/config.json   # then edit it, and chmod 600 it: it holds the webhook secrets
node deploy/api/start.mjs /etc/time-api/config.json
```

| Setting | Meaning |
|---|---|
| `rpc_url` | The CometBFT RPC of a node of the network: `https://`, or `http://` on this machine. An origin only, no path, no user name or password. Use a node you run: see "What it trusts". For a node on another machine see "A node on another machine". |
| `trust` | The trust manifest, the same object the SDK's `createClient({trust})` takes. Install it from a source independent of the RPC. If it says `nodes_report_upgrades: true` (a production network's does; `true`, `false` or absent), every state the service verifies also carries the question about scheduled upgrades. The start log repeats the value as `nodes_report_upgrades`. |
| `data_directory` | Holds `index.sqlite` (the index, the light clients' checkpoints and the webhook queues) and the lock file. One instance per directory. |
| `start_height` | The first block to index. Default 1. It may be below the trust anchor: older blocks are verified through the chain of block hashes. An index keeps its start height for good; another one needs a new data directory. An index knows nothing below its start: every indexed answer carries `index.start_height`, and a reader that comes with a cursor from below it is refused ("Routes", below the table) |
| `port`, `host` | Default `127.0.0.1:8930`. Put a TLS proxy in front for the public. |
| `hosts` | The names the API is reached under, as clients send them in `Host`: `"api.example"` (which also answers `api.example:443` and `:80`, since clients leave those ports out), or `"api.example:8443"` for another port. `127.0.0.1`, `localhost` and `[::1]` with the listening port always work; any other name gets 421, which stops DNS rebinding. |
| `cors_origins` | Origins whose web pages may call the API, exactly as the browser sends them (`https://explorer.example`). Default none: every request that carries another `Origin` gets 403. `["*"]` alone allows every origin; no route uses cookies or credentials. The explorer served by this process needs no entry: a request whose origin is the very address asked is the server's own, under `https://` for a name in `hosts` (behind your TLS proxy, which must pass the `Host` header on unchanged) and under `http://` on this machine. An explorer page that reaches this process under plain `http://` and a public name is refused: serve it under HTTPS. **The process cannot see a proxy that changes the `Host` header** (nginx does by default: set `proxy_set_header Host $host;`) or that serves HTTPS on a port its `Host` header does not carry: it starts all the same, and the explorer then loads in no browser, with 403 for its script. If you cannot change the proxy, list the page's own origin here (`https://api.example`), which works as for any other origin. |
| `rate_limit` | `{per_second, burst}`, per client. Default 20 and 60. Dearer routes take more than one from the budget: the table of routes says what each takes (1; 5 for an action by hash and for every answer that comes with a proof or from the node; 10 for a submission or a stream). The explorer's files take less: see "The explorer". |
| `trusted_proxies` | IP addresses of your own reverse proxies. Only for a request from one of them is the client taken from `X-Forwarded-For`: it is read from the right, past entries that are trusted proxies too, and the first other entry is the client (a port on an entry is ignored). Default none: the client is the peer address. An IPv6 client is its /64. |
| `webhooks` | `[{account, url, secret}]`: payments to `account` are POSTed to `url`, signed with `secret` (at least 16 characters, one per webhook). `url` is `https://` (`http://` only to localhost). |
| `max_lag_seconds` | `/v1/health` answers 503 when the newest indexed block is older than this. Default 120. |
| `rpc_timeout_seconds` | Each request to the RPC gives up after this long. Default 10. |
| `max_streams` | Event streams open at once. Default 100, at most 5 per holder (an IPv4 address, or an IPv6 /56). |
| `max_stream_seconds` | A stream is ended after this long; its reader reconnects and is sent what it missed. Default 900. |
| `serve_explorer` | `true` also serves the explorer's pages ([`web-v4/explorer`](../../web-v4/explorer/README.md)) under `/explorer/`. Default `false`: the service serves no page. See "The explorer". |
| `explorer_join` | Only with `serve_explorer`. This network's facts for the explorer's "Run a validator", served as `/explorer/join.json`: `{script_url, wallet_url, chain_id, min_self_bond_micros, files: {node_sha256, cometbft_sha256, genesis_sha256}, peers, pace}`. `script_url` is `https://`, a plain host name in lower case (and a port if needed) and the path `/join/join.sh`; `wallet_url` an `https://` origin with no path; `chain_id` the chain id of `trust`; `min_self_bond_micros` a decimal string from `"1"` to `"1000000000000000"`; each hash 64 of 0-9 and a-f; `peers` 1 to 8 entry nodes, each `<node id>@<IPv4 address>:<port>`; `pace` (optional) `"100ms"` to `"999ms"`, or `"1s"` to `"5s"`. Every value is checked at start, and a key that is not one of these is refused. Default none. |
| `reserved_stream_clients` | IP addresses that always get a stream: they do not count against `max_streams` and are never put out. **List every service that must not lose its stream here, an exchange's deposit reader first.** Everyone else can be put out when places run out. An address cannot be both here and in `trusted_proxies`. Default none. |

Unknown settings are refused, and a config error never quotes the file.

### A node on another machine

The RPC of CometBFT has no authentication and no encryption. Do not open it to a network; the service does not take plain `http://` to another machine either. Bring the node's RPC to this machine's own loopback address through a tunnel that authenticates both ends and encrypts, and give that address:

```sh
ssh -N -L 127.0.0.1:26657:127.0.0.1:26657 -l tunnel node.internal     # kept up by a service manager, with a key that may do nothing but this forward
```

with `"rpc_url": "http://127.0.0.1:26657/"`. A WireGuard link between the two machines, with the node's RPC bound to the link and a forward on this side, does the same. The other way is a TLS proxy in front of the node's RPC, with a certificate this machine trusts and access limited to this machine; `rpc_url` is then its `https://` origin.

What the tunnel is for: that the node can be reached, and that nobody on the way reads or drops what is sent to it. It is not what makes an answer true: every block and every state is checked against the trust anchor, whatever carried it ("What it trusts"). Neither a tunnel nor a TLS proxy has been run with this service: the check of 2026-11-18 reached a validator of its test network through a plain forward on the service's own machine.

## Routes

"Takes" is what one request takes from the caller's rate-limit budget.

| Route | Answers | From | Takes |
|---|---|---|---|
| `GET /v1/status` | Network id, chain id, fee, how far the index is | this service | 1 |
| `GET /v1/health` | 200 or 503 with reasons; counts only | this service | 1 |
| `GET /v1/openapi.json` | The description of the API | file | 1 |
| `GET /v1/blocks` | Recent blocks (`limit`, `cursor`, `order`) | index | 1 |
| `GET /v1/blocks/{height}` | One block | index | 1 |
| `GET /v1/blocks/{height}/actions` | Its actions, in block order (`limit`, `cursor`) | index | 1 |
| `GET /v1/blocks/{height}/proof` | The block and the next one in the history of the state, with that proof and their two signed headers: what checks an action of the block. Its age is no obstacle. The newest two blocks answer 404 `not_in_history` with a proof of how far the state reaches; a block from before the node joined by snapshot answers 404 `history_not_held` | state proof + node | 5 |
| `GET /v1/light-blocks/{height}` | The signed header and validator sets of a block, as the node gives them: what a caller's own light client verifies | node, unchecked | 5 |
| `GET /v1/validators` | Who validates now with what voting power, and the announced sets. `upgrade` only when the state was asked about its upgrade row (see below) | state proof | 5 |
| `GET /v1/actions/{hash}` | One action: decoded, its bytes, and the Merkle proof to its block | index | 5 |
| `GET /v1/accounts/{number or name}` | Current state with its proof; indexed totals; and whether the index already holds an action of the account that the proof does not count yet (`indexed.state_is_behind`) | state proof + index | 5 |
| `GET /v1/accounts/{number}/state` | The account with its security row, its stake and its validator, in one proof, and the clock the moments of the security row are on (`security_clock`, below) | state proof | 5 |
| `GET /v1/accounts/{number}/activity` | What the account sent and received, and requests that name it (`limit`, `cursor`, `order`) | index | 1 |
| `GET /v1/accounts/{number}/payments` | Payments to the account (`reference`, `from`, `limit`, `cursor`, `order`) | index | 1 |
| `POST /v1/transactions` | Checks the signature and passes a signed action to the node | node | 10 |
| `GET /v1/stream` | Server-sent events: `payment` and `block` (`account`, `direction`, `after`) | index | 10 |

- Amounts are decimal strings of microseconds. Heights, nonces and account numbers are decimal strings too.
- Every parameter has one accepted form. An unknown or repeated query parameter is refused with 400, so a misspelled `reference` never returns an unfiltered list. The address of a request is a plain path with an optional query: a fragment (`#`), another host, dot segments or a backslash are refused with 400.
- A page holds at most 200 rows (default 50). `next_cursor` goes back in as `cursor`. When a page is empty, `next_cursor` repeats the cursor that was given: a poller keeps it and asks again.
- **A cursor below the start of the index is refused:** 409 `cursor_below_index_start`, with `index.start_height`. This happens to a reader whose cursor is older than the index it now asks: the data directory was replaced and the new index starts later (a node restored from a snapshot has no earlier blocks to give), or the reader was pointed at another instance. What the chain holds between the cursor and the start is not in this index, and a list that simply began at the start would skip it without a word: a reader of deposits would never see those payments. The reader gets the missing heights from an index that holds them, and goes on here without a cursor. For `/v1/blocks` the block just before the start is still a good cursor (nothing lies between). A stream that resumes below the start (`Last-Event-ID`, `?after=`) gets a `gap` event naming the heights this index does not hold, and then what it does hold.
- Errors are `{"error": {"code", "message"}}`. `code` is stable. 429 and 503 carry `Retry-After`, which a page on an allowed origin can read (`Access-Control-Expose-Headers`). A page on an origin that is not allowed gets 403 without any allow header, so its browser reports a failed request, not the 403.
- `GET /v1/validators`, `GET /v1/blocks/{height}/proof` and `GET /v1/accounts/{number}/state` share a read of the state between identical requests for one second: many readers of the same page cost one proof, and an answer is at most that old.
- **The clock of a security row.** `GET /v1/accounts/{number}/state` gives, from the same proof as the row, `security_clock`: `{waits_survive_stops, stopped_micros, now_elapsed_micros}`. On a network whose genesis has `waits_survive_stops` the moments of the row (`ready_elapsed_micros` of what waits, `frozen_until_elapsed_micros`, `expires_elapsed_micros` of a waiting replacement, `allowance_elapsed_micros`) are on the clock of the waits, the chain's time less the total of its stops. Compare them with `now_elapsed_micros`, never with `state_time_micros`: after a stop of more than five minutes they lie before the time of the state and are still to come. Shown as a date, a moment is itself plus `stopped_micros` plus `genesis_time_micros`, and while it has not come that is the earliest it can come. On any other network `stopped_micros` is `"0"` and the clock is the chain's time. `null` means the state did not carry what the clock is read from.
- **A scheduled upgrade is never denied without proof.** The state says something about its upgrade row only when asked. Whether it is asked is decided by the trust data, for every state read alike: with `"nodes_report_upgrades": true` in `trust` the SDK's client asks with every read, and the answer of `GET /v1/validators` then has `upgrade` (the row, or null when the proof shows there is none). Without it nothing is asked (a node from before the question would refuse it) and the answer has no `upgrade` field, which means "not read", not "none".
- **What the proof of a block covers.** The state proves the history of its blocks up to its own height. The proof of a block stays when the state drops the block's own rows after fourteen days (`history_pruned_through` counts those rows), so `GET /v1/blocks/{height}/proof` answers for a block of any age. Two kinds of block it cannot prove, each said as what it is:
  - *The newest two.* A question about a block above the state's height cannot be answered at all. The route first learns how far the state reaches (from a state it has seen, or by reading the plain state) and answers 404 `not_in_history`, with the proof of that plain state, for a block beyond it.
  - *Blocks from before a snapshot.* A node that joined the network by state sync holds no block history at or below the height it was restored at, and refuses a question about it. The route then answers 404 `history_not_held`. Run the API against a node that has the history if old actions are to be provable here.

### What an action carries

`kind` and `kind_name` (the SDK's names), `sender`, `nonce`, and where they apply `recipient`, `amount`, `reference`. `transfers` is true when including the action moved `amount` to `recipient`. Only those are listed as payments:

- a transfer (3), a payment to a shop (10), a payment approved by several keys (73 with a `pay` operation);
- a completed payment above the daily limit (75 `execute`), when the index could tie it to its request: see below.

Further:

- **Fees.** `fee_rule` is what the action's bytes tell: `network_fee`, `none` (kinds 12 when consent is withdrawn, 14, 15, 40, 41, 42, 45), or `at_most_network_fee` (72, 74, 76 and a replacement of keys in 73, which cost the fee or what the account has left). `fee_micros` is filled in where the rule fixes it, once this service has verified a state of the network, which carries the fee.
- **Kinds the SDK does not decode** (the engine's 23 and 63, the reserved 81, and any added later) are stored opaque: hash, bytes, and kind and sender if the envelope has the usual frame. They never stop the indexer.
- **A validator's upgrade signal** is kind 80, `kind_name` `upgrade_signal`. It moves nothing and pays the network fee. `GET /v1/actions/{hash}` gives its `payload`: the plan it supports (`activate_elapsed_micros`, `spec`, `version`), or `{}` for a withdrawal. `POST /v1/transactions` passes one on like any signed action; a node takes a signal of support only for a version and specification hash its own program implements, and its refusal comes back as 422 `rejected`. An index that was filled by a service from before this kind was decoded keeps those rows opaque (`opaque: true`, no payload, `fee_rule` `unknown`); a new data directory reads them again. The explorer says of such a row that it is a signal, without its content, until the reader checks the action.
- **A registration that carries a set of keys** is kind 45, `kind_name` `register_protected` (on a network whose genesis has `protected_registration`). Like a reveal (2) it has no sender (`sender` is null) and pays nothing. It creates the account with its keys in their roles and its daily limit; `GET /v1/actions/{hash}` gives the name, the salt and the set (`security`: the keys with their roles and acceptances, and the policy). The new account's number is not in the bytes: read it from a state proof by name. `kind_name` takes one of the names listed in `GET /v1/openapi.json` (`KindName`), which are the SDK's.
- **`request_status`** is set on a request for a payment above the daily limit and says how it ended, as far as the index knows (next section). It is the one field of a stored action that changes later.
- **`results_checked`.** Validators of this application reject a block in which any transaction fails, so an action in a final block has executed. The header of the next block commits to the results; once it is verified and they are all successful, `results_checked` turns true (about one block later).
- **A reference does not name its payer.** The engine accepts a reference from any account whose next nonce is the one inside it. More than one payment can therefore carry the same reference: filter by `from` as well.

### Payments above the daily limit (kind 75)

A secured account asks for such a payment (`request`: recipient and amount, nothing moves), waits, and completes it (`execute`: only a number). The number is kept in the account's security row, which the actions do not carry, so the index cannot look it up. What the indexer does:

- **The request** is stored with its recipient and amount and `transfers: false`, and listed in the recipient's activity with `role: "pending"`. Anyone can make such a request to any account for one fee, and cancel it: it is a notice, never a payment.
- **The completion** is stored as a payment (recipient, amount, `request_hash`) when the actions of the chain make it certain which request it completes. After an account adopts the rules (70), is frozen (72), finishes a replacement of its keys (74) or asks for one (73 `replace`), nothing is waiting; from there on only a request adds a waiting payment, and each completion or cancellation in a block removed one. When exactly one request is waiting, a completion completes that one. An account that has had its rules from its first block (registered with kind 45, or protected in the genesis) is followed from its first request, which carries nonce 1: every request takes the account's next nonce, so nothing can wait before it. (The registration itself names no account number, so it cannot be that point.)
- **With more than one waiting, nothing is attributed** (`unattributed: true`): a wrong recipient would be worse than none. The completions and cancellations are counted, and once as many have been seen as requests, nothing is waiting and the next lone request is followed again. Also not attributed: an account that adopted the rules before `start_height` (until its next freeze or replacement of keys), and an account one of whose actions the SDK could not decode. The guide has the procedure for these deposits.
- **How a request ended** is written to it as `request_status`: `waiting`; `completed` or `cancelled` by a later action; `dropped` by a freeze or a replacement of the keys; `ended` when it was settled together with others and the index cannot tell which were completed and which cancelled; `unknown` when the index does not follow the sender.
- **Instances that answer under one name must have the same `start_height`.** What is attributed depends on where the index starts, so two instances with different starts list different payments for the same account.

The attribution rests on the indexer's reading of the engine's rules (`v5/src/security.rs`), which the tests check on synthetic actions; like the rest of the index it is not a proof.

### Submitting

`POST /v1/transactions` takes `{"tx": "<base64>"}`. The bytes must decode as an action of this network with a valid signature of the key in its envelope. They go to the node in the body of a JSON-RPC request, so the largest action fits.

- **What the signature check proves:** that the key named in the action signed exactly these bytes, not that the key is one of the account's. The account's keys are in its state, which the node checks; reading them here with a proof for every submission would cost more than the node's own refusal. So an action signed with a stranger's key reaches the node, once per submission and within the sender's rate limit, and is refused there (422).
- **The unsigned kind.** The relay of bitcoin headers (kind 40) carries no signature. It is taken in its one form only (no sender, nonce 0, epoch 0, no key), and only once a proof of the network's configuration has shown that the network has a bitcoin auction. On a network without one (all new time to validators), kinds 40 to 42 and 60 to 62 are refused with 400, as the engine refuses them.
- **Bytes that are in a block already.** Before the node is asked, and again whenever it did not take the bytes, the index is asked for their hash: the answer is then 200 `already_included` with the height, never the node's refusal.
- **A nonce that is used already.** At the same two moments the index is asked which action of the account carries the nonce of the submitted one. If there is one, the answer is 409 `nonce_used` with that action (`used_by`: hash, height, kind, recipient, amount) and `same_content`: true when that action has the same kind and payload. That is the same payment under another signature (a second key, a signer that was asked twice), or another payment of the same amount to the same recipient: the service cannot tell the two apart. One hash is one payment, so the sender's own records decide (`docs/integration-guide.md`, step 3), and the sender verifies `used_by.hash` before acting on the answer: it is the index's word. The node would only say "incorrect nonce". An action without a nonce (kinds 72, 73, 74 and 76 carry 0) is never answered this way.
- **A 400 judges the request, not the chain.** `invalid_action` means that the SDK of this service could not decode the bytes; a node with a newer engine may take a kind this service does not know. Nobody should conclude from a 400 that bytes can never be included.
- Both lookups see no further than `index.indexed_height`.

### Webhooks

Each payment to a configured account is POSTed as JSON, with the fields of a list item under the same names:

```json
{"id":"payment:<hash>","type":"payment","source":"index","proven":false,"hash":"…","height":"210","index":0,"time":"…","kind":10,"kind_name":"merchant_payment",
 "sender":"7","nonce":"42","recipient":"5","amount":"2500000","reference":"…","transfers":true,"request_hash":null,"results_checked":false}
```

They are sent with the security watch's own webhook code, so a receiver is written the same way (see `../watch/README.md`, "Webhooks"):
- headers `x-watch-event: <event id>` and `x-watch-signature: t=<unix seconds>,sha256=<hex>`, the HMAC-SHA256 under the secret of `t=<unix seconds>,id=<event id>.` followed by the raw body. `verifyWebhookSignature` in `client-v4/security-watch-service.mjs` checks it;
- answer 2xx when you have the event, 401 when the signature does not verify (it is retried), 410 only to give an event up (it becomes a dead letter);
- delivery is at least once: drop an event id you have seen.

Each webhook has its own queue, kept in the index file and filled in the same transaction that stores the block. A stop of this service, however long, loses no event: every block made after a webhook was configured is sent to it when it is indexed, however late.

**Where a webhook starts.** A webhook is told of payments from the height the chain had when the webhook was first configured: the first tip the light client verifies after that. Payments in earlier blocks are history to it: they are indexed and listed, not sent, so that building or rebuilding an index does not send every payment of the past. Each one left out is counted (`skipped_history` in `/v1/health`), and the log says once per run that it happens. Until that first tip is verified the webhook has no start (`awaiting_start` in `/v1/health`); blocks indexed meanwhile are history to it. A webhook whose address or account changes is a new webhook and starts anew; so does every webhook when the data directory is new. Read the payments list for what came before.

Once queued, events are delivered as follows. A receiver that is down delays only its own queue: its events are retried after 2 s, doubling up to 5 minutes. A queue holds at most 100,000 events (the oldest are dropped, with a log line). A webhook removed from the config has its queue removed at the next start. `/v1/health` counts queued events, dead letters and failing receivers.

A webhook is sent when the block is indexed, before its results are checked (`results_checked` is false in it). It is a hint, like everything from the index: verify the payment before crediting it, and keep polling the payments list as the source of truth.

### The event stream

`GET /v1/stream` sends `hello`, then for each new block its `payment` events (id `<height>.<index>`) and one `block` event (id `<height>`).

- `?account=<number>` keeps the payments **to** that account. `direction=out` gives those it sends instead, `direction=both` gives both. Blocks are always sent.
- A reader that reconnects with `Last-Event-ID` (browsers do it by themselves) or `?after=<id>` is sent what it missed, up to 256 blocks and 2,000 payments; beyond that it gets one `gap` event with the heights to read from the lists. The payments are read through the index of payments, so one request never reads more rows than it may send.
- The server ends a stream with a `bye` event after `max_stream_seconds`, and when its place is needed. The reader reconnects and misses nothing.
- **Places.** Streams are counted per holder: an IPv4 address, or an IPv6 /56. When every place is taken and a holder with fewer streams asks, a holder with more gives up its oldest, the one with the most first. A stream is not put out in its first 5 seconds. A stream that follows an account is never put out for one that follows none, and goes last in any case.
- **These rules make it harder to push a reader out, not impossible:** whoever has many addresses can still take places. The one guarantee is `reserved_stream_clients`. An exchange lists the addresses of its deposit readers there; a reader that is not listed must reconnect when it gets `bye`, and loses nothing when it does.
- A reader that does not keep up is disconnected.

## The explorer

With `"serve_explorer": true` the service also serves the explorer ([`web-v4/explorer/README.md`](../../web-v4/explorer/README.md)) at `/explorer/`: pages where anyone looks up a block, an action or an account, and checks an action or an account's state in the browser.

- **Only a fixed list of files** is served (`EXPLORER_FILES` in `client-v4/api.mjs`): the explorer's own files, and the SDK and verifier files they load. They are read once at start. A request is answered by looking its path up in that list, so nothing a caller sends names a file; a path with a query (an empty one too), dot segments, another spelling or an unknown name gets 404 or 400.
- **Headers.** The files go out with the Content-Security-Policy the wallet's gateway sends for the wallet, narrowed to what the explorer needs (scripts and styles from this origin only, WebAssembly for the verifier, requests to this origin only, no framing), and with `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options` and `Cross-Origin-Resource-Policy`.
- **Caching.** Each file has an `ETag` (the hash of its bytes). The page and its modules are `Cache-Control: no-cache`: a browser asks every time whether they changed, which a 304 answers without the bytes, so files of two releases never run together. `If-None-Match` is honoured as browsers and proxies send it (a list, a weak validator, `*`). Only the compiled verifier, a megabyte that the page loads at its first check, is kept for five minutes (`max-age=300`). The trust manifest, `join.json` and every refusal are `no-store`.
- **`/explorer/trust-manifest.json`** is the configured `trust` moved to the newest block this service's light clients verified. It is what the pages start their own checks from. A reader of pages served here trusts this service for that starting block, as for the pages themselves, and the pages say so in their footer; whoever wants to depend on nobody hosts the pages elsewhere with a manifest of their own (the explorer's README says how) and lists that origin in `cors_origins`. If the service's own trusted block has expired, so has the manifest, and the pages say that they cannot check.
- **`/explorer/join.json`** is the `explorer_join` setting, exactly as configured. It is for the section "Run a validator" of the explorer's Validators page, which tells a newcomer how joining as a validator works: with it the page also shows the commands that fetch and run this network's join script, a link to the wallet, and this network's files and entry nodes. Without the setting the address is a 404 like any unknown name, and the page shows the general explanation only. The page checks the file again by its own rules before it shows anything of it, and says that it does not check the script.
- **Rate limit.** A request for a file is charged by what answering it costs. A small file, and a "not changed" answer for any file, take a tenth of what an API request takes from the caller's allowance (a page is a dozen files), so that loading the page leaves the allowance for the API. A larger file takes more by its size: the compiled verifier takes about 4, so the default allowance of 60 gives one address 14 downloads of it, then 5 a second. The trust manifest (it reads the database) and a path that names no file take 1, like an API request; `join.json`, an answer fixed at start, takes a tenth like a small file. One load of the home page with its API requests and its stream takes about 14 of the default 60. The files are answered only under the service's own host names.
- **In a browser: Chrome, once, for a minute at a time.** On 2026-11-19 Chrome 158 opened the pages served by this process on a live test network (`campaign/README.md`, "The browser check"). The first run found that they loaded in no browser: the process refused the requests of its own page, because a browser names the page in `Origin` also then (see `cors_origins` above). With that fixed, the page loaded with no complaint of the browser, checked an action against validator signatures in a quarter of a second after "Check it yourself", and showed a block, an account found through the search field, a name nobody holds and the validators, each with what was checked. Not looked at: the live updates of the home page, what a browser keeps in its cache between two releases, a phone, a screen reader, the dark colours, any browser but Chrome. Before that, on 2026-11-18, the service had served them on a live test network (seven validators in two regions on AWS): every file of the list was fetched and compared byte for byte, with the headers above and with `If-None-Match`; and the explorer's own checker, run under Node, verified the four proof routes against the live chain (the validators, an account with its security row, an account that does not exist, an action through the history of the state, and an action in the newest blocks through its own signed header). That check asked without naming a page, which is why it did not see the refusal; it now asks as a browser does.

## What it trusts

- **Only the trust anchor.** The light client (the SDK's, with the verifier installed with this code) verifies the newest block against the anchor: validator signatures, validator-set changes, the trusting period. Every other header is tied to a verified one by the chain of block hashes, which the indexer recomputes from the header's own fields. The transactions of a block must hash to its header's `data_hash`. A block that fails any of this is not indexed, whatever the RPC says.
- **The RPC can withhold or delay.** It can answer nothing, or old blocks. The index then stops growing. `/v1/status` and `/v1/health` show it: the age of the newest indexed block by this machine's clock (`seconds_behind`, which needs no word of the RPC), the height the RPC reports, the last error. The log has one line for the first failed round and one every twentieth.
- **The RPC sees submissions.** `POST /v1/transactions` hands the bytes to it. It can drop them; it cannot change them.
- **The index is this server's word.** A caller cannot see that the server verified anything. Every indexed answer says `"source": "index", "proven": false` and names what verifies it; an action carries its bytes and its Merkle proof. Account state carries the proof this server checked (`"source": "state_proof"`).
- **The index can be behind the state.** Account state is proven at the newest block; the index follows. An account answer therefore shows `state_height` and `indexed_height` side by side, and every indexed answer its `index.indexed_height`. What the index does not show is absent only up to that height.
- **The state can be behind the index.** A state is proven one block behind the newest block, and the index can already hold that block. An account answer says when this matters: `indexed.state_is_behind` is true when the index holds an action that the account sent in a block above `state_height`. `indexed.newer_actions` lists those, oldest first, at most 16; `indexed.last_sent` is the newest of them, also when there are more than 16, and with none it is the action that carries the proven nonce (null when the index does not hold that one: it is below the start of the index, or in a block the index has not reached yet, which `indexed_height` below `state_height` shows). Every action the account sent counts, also one that carries no nonce (a freeze, a payment or a replacement of keys approved by several keys, a cancellation). The proven nonce may then be used already. This is the index's word, placed under `indexed`; and false says only that the index holds no such action up to `indexed_height`. An action that waits for a block, or one in a block the index has not reached, is in neither, which is why a signer counts its own nonces (`docs/integration-guide.md`, step 3).
- **Two faults stop the indexer** until an operator has looked, because they mean the verified chain contradicts the index: a block that does not continue the indexed one (`CHAIN_CONFLICT`), and a header that does not commit to successful results for the block before it (`RESULTS_MISMATCH`). Neither can happen while fewer than a third of the validators are faulty. `/v1/health` then answers 503 with `indexer_fault`.
- **The trust anchor must stay fresh.** The light client refuses an anchor older than its trusting period (seven days). While the service runs it keeps the newest verified checkpoints in the index file: the indexer's with every new block, the state reader's with every account request and at least once an hour. After a stop of more than seven days, install a newly authenticated trust manifest; the blocks in between are verified down from it.

## What the index cannot tell

- **Which request a completion of kind 75 pays, when more than one was waiting** (see above). The recipient's proven balance shows the money.
- **Rewards, stake and fees.** New time paid to validators, stake movements and fee payouts change balances without being actions to an account. Indexed totals are sums of the payments above, not a balance. The balance is in the account's proven state.
- **Whether an action is waiting.** A hash that is not in the index is 404, whether it is waiting, was refused, was never sent, or is in a block above `index.indexed_height`.
- **Anything before `start_height`.**
- **Names.** The index knows accounts by number. `GET /v1/accounts/{name}` resolves a name through a state proof; the list routes take numbers.

## Durability and limits

- **The index** is one SQLite file in WAL mode. Each block is stored whole or not at all, with its actions, its Merkle tree, totals and webhook events. After a crash the indexer continues at the next block. The file can be deleted and rebuilt from the chain, as long as the node still serves the blocks; webhooks then start at the height the chain has at that moment. A file written by an earlier version of the schema is refused: rebuild it in a new data directory.
- **The lock** is the security watch's (`watch.lock` in the data directory, same rules: see `../watch/README.md`). A second instance on the same directory refuses to start; one that loses the lock stops and exits with code 75.
- **Memory is bounded:** one block at a time (an RPC answer is at most 16 MiB), 20 headers at a time, a rate-limit table of 10,000 clients, 1 MiB of unsent events per stream, a request body of 768 KiB.
- **Work per request is bounded:** a list reads one page through an index; an action by hash reads its proof from the tree stored with the block; a reconnecting stream reads at most 256 blocks and 2,000 payments.
- **The rate limiter and the stream lifetime use the machine's clock.** A clock that is set back refills nothing and takes nothing away.
- **A single process, no replication.** If the host is down the API is down. Run two instances with two data directories behind a proxy if that matters; each then delivers its own webhooks.
- **Reading old history is one request per block.** A first run from height 1 on a long chain takes time; `/v1/status` shows `headers_to_verify` and the indexed height meanwhile.
- **Logs** are JSON lines on stdout. They hold counts, error codes and origins; never a secret, never the path or query of a webhook.
- **What has run against a live network, and what has not.** On 2026-11-18 the service ran once on a live test network (seven validators in two regions on AWS), started from this start script and a config file on one host and checked by the test harness's scripted client. The check took about two minutes; all its steps passed. What it showed:
  - the index was built from height 1 (1,518 blocks in 6.2 seconds: about 245 blocks a second; the report does not say how many of them held actions, and the network was minutes old) and then followed a chain that made about six blocks a second. Its newest block was a second old at most, and it was two blocks behind the node at the median, four at most;
  - a payment was on the event stream 42 ms after the paying wallet had its verified receipt, and its `results_checked` was true within half a second. The webhook for a deposit arrived 0.5 seconds after the block's time at the median, 0.8 seconds at most (six deposits, none delivered twice). The receiver of the run took 16 deliveries in all, from this service and from the watch together; each verified with its secret and none came twice;
  - lists and cursors, the proof of an action and of an account's state (verified with the check's own trust anchor), submissions (`already_included`, `already_submitted`, `nonce_used`, a refusal of the node), the stream and its resumption after a cut, the rate limits, and each of 297 answers against the OpenAPI description;
  - a stop and a `kill -9`: the service answered 12 ms after its start line and had caught up half a second later, with no block missing or twice, and the webhook of a payment made meanwhile delivered once;
  - the process held 116 MiB of memory on average, 164 MiB at most, and used 5% of one processor core on average.

  What has not run: more than a few minutes (nothing is known yet about hours and days, a long catch-up on a chain with full blocks, a disk that fills); load (there was one client and a few dozen actions); a TLS proxy, a tunnel or a second machine of an operator between the service and its node (the node was a validator of the test network, reached through a plain forward on the service's own host); a webhook receiver on another machine; an integration by an exchange. The answer field `indexed.state_is_behind`, the refusal of a cursor below the start of the index and the error for a missing file of the explorer were added after that run, and that run had one index, built from height 1. A second instance with a later start, and the refusal of a cursor below that start, ran in the harness's check on AWS later on 2026-11-18 (`docs/integration-guide.md`, "What has run") and again on 2026-11-23, on networks with the four genesis settings, one of them after a stop of the chain (`AUDIT-2026-11.md`, "Run on AWS and in a real browser (23 November 2026)"). The tests use real signed blocks and a real state proof served by a fake RPC.
