# V2 public-launch gates

Current status: [FIXES.md](../FIXES.md) tracks the implemented remediation and the separate protocol-3 lab. V2 remains preserved. The merchant and backup findings below describe the original v2 boundary; v3 now has nonce/expiry-bound per-payer orders and portable encrypted backups. Neither change enables public monetary operation.

V2 remains a private development network. The code's `--devnet`, loopback ABCI, development chain IDs, fixture isolation, and `publicLaunchAllowed: false` agree with that scope. Passing local tests or the million-account fixture does not open these gates.

## Concrete blockers in this implementation

| Area | What exists now | What must be resolved before a public network with valuable balances |
| --- | --- | --- |
| Earning and admission | Free account registration and synthetic, freely chosen auction bid weights. At most 256 pending commitments and 1,024 bids per epoch. The selected production direction is BTC revenue paid to the foundation; an offline treasury policy prototype exists. | Complete real Bitcoin verification, receipt/account/epoch/policy binding, one-use outpoint accounting and reorg rules before deriving weights from paid BTC. A bot can still create free lab identities and bids. The treasury policy prototype does not make this laboratory distribution Sybil resistant. |
| Consensus security | CometBFT runs a fixed genesis validator roster. Operator pools receive rewards, but delegations do not select validators or change consensus voting power; no consensus slashing/rotation implementation exists. | Choose and implement the production validator admission, voting-power, accountability, exit and upgrade rules, or explicitly launch a permissioned network. Stake-pool accounting alone does not make the current implementation permissionless proof of stake. |
| Operator independence | The demonstrated validator network runs on one machine. | Demonstrate independent operators, key custody and failure domains. Count voting power and correlated control; increasing the process count on one host does not provide that evidence. With four equal-power validators, losing two halts this quorum system. |
| Light-client trust | A locally generated genesis manifest pins one fixed validator set. Fresh selected-state proofs use H+1 quorum headers, a 45-second freshness window, a 10-second future bound and stored checkpoints. The verifier does not process changing validator sets or perform long-range recovery. | Define independently authenticated wallet/manifest distribution, validator transitions, checkpoint recovery after long absence, and compromised-key response. A fresh header from compromised pinned quorum keys is not made safe by its timestamp. |
| Recovery and custody | Random Ed25519 device keys are encrypted in the current browser with Argon2id/AES-GCM. New-device approval and preconfigured guardian recovery exist. The UI uses a 30-second laboratory recovery delay. | Set and review production recovery timing and notification/response policy. A guardian quorum can take control; an existing compromised managing device can repeatedly cancel recovery. Losing all devices before configuring recovery can lose access. A stolen vault permits offline password guessing, and compromised wallet JavaScript can request signatures or capture a typed password. |
| Portable username/password UX | The username is an on-chain identity index. The password unlocks a local encrypted vault. Portable encrypted-file backup/import is now implemented with strict format/network/key/authority checks and no overwrite. | Additional wallet vendors must implement and review the published format. Password-only fresh-wallet key recreation, WebAuthn/passkeys and hardware-wallet integrations remain unimplemented. A backup clones one device identity; independently revocable devices use enrollment. |
| Merchant payments | Legacy v2 has browser markers and merchant journaling. New v3 reserves a payer nonce and expiry in the signed order reference; direct native HTTP probes reject stale, expired and cross-device duplicate payments. | V3 same-payer reference reuse is fixed. Keep the merchant's account binding and durable fulfillment journal. A consumed nonce makes the old quote unpayable, requiring a newly approved quote; separate payer accounts are not globally deduplicated. Standing spending grants remain disabled. |
| Historical settlement | Current state/authority proofs use a 45-second freshness bound. Receipt verification instead accepts both certified H/H+1 headers up to 14 days old. An exact retained payment can be first settled after the order's three-minute expiry; fulfilled same-hash retries use the durable merchant journal. | Define archival transaction/header availability and durable receipt retention, plus a reviewed trust/checkpoint policy for independent verification beyond 14 days. The current verifier rejects older receipts even if their bytes are retained. A stored fulfillment record is not a fresh cryptographic re-verification. Current login/session authority remains a separate fresh-state requirement. |
| Public services | Wallet/merchant servers are loopback laboratory services with in-memory login sessions and bounded local request handling. Native state-snapshot restore/state sync is rejected. | Build and exercise public service deployment, discovery, peer/provider selection, authentication/origin/TLS configuration, durable service operations, synchronization/bootstrap, abuse resistance and rollback/recovery procedures. The current services are not production hosting templates. |
| Independent assurance | Tests exercise all sixteen actions, invalid transitions, authenticated membership/absence, supply recounts, crashes, replay and browser flows. Several client/storage integration defects were found and fixed during this work. | Obtain independent protocol and implementation review, sustained adversarial testnet evidence and an explicit release threat model. Differential agreement with reused v1 rules is useful but cannot rule out a shared design error. No formal proof that every attack is impossible is claimed. |

## The remaining capacity bottleneck

Authenticated storage no longer requires a whole-registry snapshot for each payment. That resolves the specific v1 storage/proof growth problem; it does not establish end-to-end network throughput.

The next technical capacity gate is the actual mempool/ABCI/consensus pipeline with many independent senders. Blocks have a 1 MiB transaction-body limit, and `CheckTx` validates against the committed next nonce. A preconstructed batch of 100 sequential nonces from one sender can execute in the offline engine benchmark even though submitting that sequence simultaneously through the current mempool would not be accepted as a future-nonce queue. The benchmark intentionally reports that distinction.

The completed million-account fixture also measured a concrete storage bottleneck: 100-transfer commits took 3.88–4.82 seconds during retirement of large imported history versions, producing only 20.68–25.73 component transactions/second in those samples. Commit includes synchronous pruning; separate pruning/fsync costs and post-drain transfer rates were not measured. Introduce a reviewed reclamation latency budget and backlog admission policy, then test history churn before treating compact-state storage as production-ready. The subsequent full authenticated audit took 42.45 minutes. See [EVIDENCE.md](EVIDENCE.md).

Measure sustained offered load, accepted/finalized throughput, queue growth, p50/p95/p99 user latency, overload behavior, bandwidth, CPU, memory, disk writes, retained history and recovery across independent WAN validators. Include account creation, name contention, auction saturation, recovery changes and ordinary wallet requests rather than only repeated transfers between two accounts. Batch execution is not a measurement of millions of concurrent wallets.

The primary adoption blocker is currently the earning/admission design, not the ability to store a million names: synthetic free bids and free identity creation provide no production allocation fairness or Sybil resistance.

## Limits that must remain visible

- Account count is configured at at most 10,000,000; only the reported fixture sizes have been exercised. A configured limit is not demonstrated capacity.
- Genesis is limited to 64 identities. The synthetic importer is a separately compiled offline fixture path, not a public signup endpoint.
- The 256-commit and 1,024-bid limits are global development bounds. Saturating them can deny other users access until slots clear; a million accounts cannot bid in one such epoch.
- Proof requests contain a selected view, automatic operator rows, and one guardian level for explicitly selected accounts. They are limited to 256 entries and 4 MiB at the client, with a 3 MiB raw native response budget. Large selections must be split.
- Historical receipt proofs do not expire at 45 seconds: both transaction H and following H+1 headers have a separate 14-day verifier age limit. Availability also requires the indexed transaction and both headers. The app currently returns `retain_height: 0`, requesting no Comet block pruning; long-run block/index storage and archival policy remain unresolved independently of JMT state-version pruning.
- A compact proof authenticates account data and aggregate counter claims. Only the separate streaming audit independently recounts all account balances, escrow and share ownership. It also checks both directions and cardinalities of name, registration-key and unbond indices, and rejects orphan recovery rows.
- Inactive recovery claims can remain physically stored until their target is touched, up to five per target. They provide no authority or freeze. Retained version garbage is pruned separately; long-run state growth still needs measurement.
- The million-account importer creates deterministic test identities with zero balances, then explicitly allocates existing accrued bank supply to a fixture sender. Results are component evidence, not real user adoption, earning fairness, public quorum operation or Bitcoin-equivalent security.

## Maintenance is part of the release design

The current fixed keys, short-lived local services, bounded proof history and unsupported state-sync path do not provide a maintenance-free autonomous network. Before launch, name responsible operators and establish upgrade, vulnerability response, key replacement, backup/recovery, monitoring and incident procedures. Automation can reduce routine work; this implementation has not removed those responsibilities.
